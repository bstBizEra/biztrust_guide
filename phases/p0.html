Delivery phases · P0

Identity and Tenant

P0 proves who performed what, under which tenant, with which authority, against which resource, before any real insurance-domain data is placed on the substrate. Nothing in this phase knows what a policy is. That is deliberate: a substrate proven on business data is a substrate whose proof leaked business data.

Rendered from BIZTRUST-PLAN-001.md §4, whose thirteen P0 epics are the previous plan's rows carried unchanged and whose mandatory proof is the previous plan's, with the authorization sequence from FLOWS.md §3 and the enforcement layers from AUTHORIZATION_BASELINE.md §5–§8. The hub's P0 card is the summary; this page is the manual.

THE RULE THIS PHASE EXISTS TO ENFORCE

Tenant A cannot read or mutate Tenant B protected data, and application authorization and PostgreSQL Row-Level Security enforce that independently of each other — INV-003 and INV-004. A gateway allow is not domain authorization, and an application allow is still constrained by RLS.

01

Preconditions

Entry criteria

BT-G0 is recorded

The architecture authority has recorded Architecture Ready after slice S11 of WP-ARCH-001A. P0 is not slice 12 of that package; it is a separate package that cannot be authorized until S11 passes.

Implementation authority is written down

The authority block of badf/current-state.json carries a production-platform implementation grant for the specific P0 package, with an expiry. Read the field; do not infer it from the gate.

The ADRs P0 builds on are accepted

ADR-001 (modular monolith), ADR-002 and ADR-003 (identity and organization-to-tenant mapping), ADR-004 (shared PostgreSQL with RLS) and ADR-005 (contract-first) — accepted per the register, not DRAFT_REQUIRED.

The first package has nowhere to land

The platform repository is P0.2's deliverable; before that package is accepted there is nowhere for a second package to land. Its Work Package is unusual: its deliverable is the repository, its AGENTS.md, its badf/ registries, the CI skeleton and the boundary tests — and a human repository administrator is a named role in it, because protecting main is not something an agent can do.

02

Epic to Work Package

Thirteen epics, each one or more packages

Each row is decomposed into Work Packages by the Plan stage under the plan's decomposition rule: one bounded outcome, an accountable owner, explicit exclusions, authority with expiry, acceptance criteria with an independent verifier, rollback, an evidence manifest and one next safe action. The identifiers are the plan's; a package cites its epic. An epic's engineering design, when it exists, lives in the P0 design pack: one file per epic with scope, interfaces, negative controls, the evidence contract and every technology as a candidate naming its ADR. A design is a proposal to review; it changes nothing said on this page about authority.

03

Execution order

Why this order and not another

The plan lists the thirteen epics and forbids opening all of them at once; it orders only P0.13, after the proof. This order is the track's proposal, derived from the dependency each step names. The plan's own rule is one primary next action, with the rest queued behind it in dependency order.

  1. P0.1 is the entry gate, not the first package. If it is not recorded, nothing below starts.
  2. P0.2 — the repository. Everything else needs somewhere to land, a CI that runs, and a boundary test that already fails on the first cross-module import. Protect main before the second package opens a branch.
  3. P0.3 — validate the token before anything trusts it. The negative cases are the deliverable; a spike that only shows the happy path has not answered the question.
  4. P0.4 — map organization to tenant, including the paths where the organization is valid and the tenant is not.
  5. P0.6 — the tenancy model, because RLS policies need a tenant_id to police and the ownership baseline to attach to.
  6. P0.7 — RLS. Write the bypass test first and watch it fail against a table with no policy. Then add the policy. A denial that was never observed to pass proves nothing about the policy.
  7. P0.5 — two tenants, repeatably. The negative matrix needs a Tenant B to be denied from, and a proof run on hand-made tenants cannot be re-run by the independent verifier.
  8. P0.10 — audit, before the proof rather than after it, because the proof is audit evidence: every denial in the matrix must produce an attributable record, or the matrix passed silently.
  9. P0.8 and P0.9 — contract conventions. Independent of the security chain; queued beside it once the repository exists, and taken as the primary action whenever the chain is blocked. Their proof is a broken contract failing CI.
  10. P0.11 — observability, so the proof run can be reconstructed from its own trace.
  11. P0.12 — secrets and configuration, last of the substrate, first thing the independent verifier checks.
  12. The mandatory proof, executed by someone who did not implement it, bound to a source revision — then BT-G1.
  13. P0.13 — the control-plane web surface, opened only after the proof has run. BT-G1 is recorded on the proof, not on this epic, and this epic is not part of the matrix: the matrix proves the substrate, and a screen that drives it is evidence that a human can exercise tenant selection and member administration, not evidence that isolation holds. A client, policy, claim or premium reaching this surface halts the package (stop conditions, below).
04

What the agent codes

Negative tests first, evidence fields always

The Build stage governs how a change is made: one package per branch, migrations expand-first, telemetry in the same change, contracts before implementations. P0 adds the content of the tests. The matrix below is the minimum; every row is a test with an API expectation, a database expectation and an audit expectation, and all three are asserted.

  • Never copy an untrusted tenant identifier into the database session. The authenticated organization, the tenant mapping and the requested resource scope are reconciled first; the session variable is set from the reconciled value, and the header is evidence of tampering, not input
  • RLS is default-deny. Enabling row security on a table with no matching policy denies everything; that state is the negative control for every policy written afterwards
  • The application role cannot bypass. Table ownership and BYPASSRLS stay with a role the application never connects as; the design of that split is part of ADR-004's evidence
  • Every mutation carries Idempotency-Key from the first endpoint, so the retry behaviour that binding and money will need later is a property of the baseline, not a retrofit
  • Every decision writes the full evidence record — decision, actor, tenant, membership, permission, resource and scope, conditions evaluated, approval reference, policy version, outcome, reason code, request and trace identifiers — and never a raw token, secret or unnecessary personal datum
  • The suite is proven able to fail. The bypass test is committed in its red state first, and the pull request quotes both runs

Stop signal: a green suite with no negative test

Every P0 package ships denial tests. A package whose evidence table shows only successes has tested the wrong property.

Stop signal: the bypass test is absent, skipped or cannot be made to fail

The row that proves RLS is independent of the application is the row the whole gate rests on. If it was never seen red, the policy has not been demonstrated.

Stop signal: insurance-domain data on the substrate

A P0 package that creates a policy, a client or a premium has left the phase. Send it back to Plan; do not accept it as an early P1.

Stop signal: the proof was run by the implementer

The plan says the proof passes independently. A self-run proof is a claim, and the gate is not recorded on claims.

Weekly

One primary next action, the rest queued; the repository's protection still in force; no secret in the tree; every candidate still marked IMPLEMENTATION_CANDIDATE until its ADR is accepted.

06

Transition

Exit gate · BT-G1 Security Ready (label B)

The seven lines of the plan's mandatory proof, plus the four conditions that make the proof a record rather than a report. No P1 authorization may be issued until every box is ticked.

07

Halt

Stop conditions

  • BT-G0 is not recorded, or slice S11 of the architecture package is not accepted — P0 has no entry
  • A package places insurance-domain data on the substrate before BT-G1
  • Any test, log or response exposes a Tenant B row to a Tenant A actor, however the request was formed
  • The bypass test cannot be made to fail against an unpoliced table — the instrument is broken, not the policy
  • Tenant provisioning is manual, or two runs produce different tenants
  • A candidate technology is used in code before its ADR is accepted
  • P0.13 carries any function that touches a client, policy, claim or premium
