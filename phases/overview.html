Delivery phases · Overview

From P0 to production

The nine stage manuals say how one Work Package moves from ENG-G0 to ENG-G8. This track says what the Work Packages are between architecture freeze and production — in what order, landing where, proven how — and what a human has to watch between one authorization and the next.

Every page on this track is a rendering of docs/architecture/DELIVERY_PLAN.md and the architecture pack behind it. The plan's phases, epics and gates are rendered exactly and held to the plan by a test; where they disagree, the plan is right and the page is a defect. What this track adds is its own and is labelled as such: an execution order within each phase, proposed recorders for each gate, and the how-to guidance in the What the agent codes and What the human monitors sections, which are the track's reading of the architecture pack rather than the plan's text. No page here states a current status. A page that restated status went false within hours of merging (#32); the ledger it duplicated did not.

THE RULE THIS TRACK EXISTS TO ENFORCE

A phase is a queue of Work Packages, never an approval state. Authority is granted per package, expires, and is recorded. Passing a capability gate authorizes only the next bounded planning step — not the phase, not production.

01

Two axes

Stages are how; phases are what

Every Work Package in every phase runs the full stage lifecycle. The phase adds three things the stages cannot know: the gate that must already be passed before its packages may be authorized, the epics its packages are decomposed from, and the proof its exit gate demands.

02

The capability gates

BT-G0 to BT-G6

Each gate names the evidence that blocks it. Test success does not self-approve a gate. The plan names the evidence and not the recorder; the last column is this track's proposal, drawn from the vocabulary of the hub's decision-rights table, which assigns decisions and not gates. It needs a decision-rights row per gate before it binds anyone.

Failure at any gate blocks dependent authorization

A red gate does not slow the next phase; it stops it. There is no partial pass.

A waiver is a decision, not a shortcut

It requires a named human risk owner, an expiry, compensating controls and recorded dissent. A waiver with no expiry is a permanent exemption nobody decided to grant.

The plan's day counts are estimates; the gates are the control

The hub's 90-day plan puts P0 in days 16–35. If BT-G0 has not been recorded on day 16, P0 has not started, whatever the calendar says.

The platform lands in one repository laid out as the hub's repository design shows. That repository is created by the first P0 package. This repository is not the platform

biztrust_guide is documentation and the governance ledger. Nothing here executes a policy, holds a tenant or moves money. A capability described on this site is not thereby implemented (AGENTS.md §12).

One identity follows the work end to end

Issue BIZTRUST-WP-<DOMAIN>-<NNN> · branch feat/<work-package-id>-<slug> · commit <type>(<scope>): <summary> [<work-package-id>] · pull request [<work-package-id>] <outcome>. The Build discipline shows worked examples.

Sibling repositories are not BizTrust

A sibling repository whose description names another product is that product, however similar its shape. The phase manuals name no sibling as a source.

04

Sources

What the code is built against, and what that does not mean

Two kinds of source. Standards set wire formats and are adopted by contract. Products are IMPLEMENTATION_CANDIDATE: they appear in the architecture diagrams, and no dependency is described as adopted merely because it appeared in one. Each product needs a bounded spike and its ADR before a package may build on it.

05

What the human monitors

Across every phase

Agents code; humans authorize, accept and merge. The monitoring job is to see the evidence before granting the next authority, and to notice when the recorded state and the observed state disagree. Each phase page adds the authorizations that phase reserves; this section is what does not change.

Read the ledger, not a rendering of it

Current state lives in badf/current-state.json, the active issue, and the CI run bound to a commit. A dashboard that restates them is a third source that no validator checks. The one built here drifted on eight facts within hours.

Authority is never inferred

Not from green CI, not from a merged pull request, not from an agent's report that the work is done. It is a record with a grantor, a scope and an expiry, and the human is the only actor who writes it.

One active slice, one next action

The plan's rule for packages is one primary next action with a dependency-ordered queue behind it. The foundation sequence's rule for architecture slices is stricter: two active slices mean RECOVERY_REQUIRED until someone reconciles them. Parallel drafts on different assumptions are how rework is manufactured.

06

Halt

Stop conditions across phases

  • A capability gate is reported passed and the blocking evidence in the table above is not attached to the record
  • Two phases are in progress at once, or there is no single primary next action
  • A page on this track states a current status instead of pointing at the ledger — treat it as a defect in the page
  • Anyone labels work after P3 as P4 or higher; the plan reserves that numbering until it is reviewed
  • A candidate technology is written as adopted, in code or in prose, without its ADR accepted
  • A waiver appears without a named risk owner, an expiry, compensating controls and recorded dissent
  • The authority for the active package has expired, or its scope no longer matches the work — this condition applies in every phase and is written only here
