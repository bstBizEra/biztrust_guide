Delivery phases · P2

Professional brokerage lifecycle

P2 expands the core into professional placement, servicing, claims advocacy and renewal. Its exit is not a feature list. The plan says P2 exits only when delayed, duplicate and conflicting external interactions have been exercised without corrupting broker state — so the phase is built around the failures, and the features are what the failures act on.

Rendered from DELIVERY_PLAN.md §5, with the placement, quote-revision, binding and claims machines from FLOWS.md §7–§11, the failure classification from §16, and the event and workflow contract from ARCH-001 §12.

THE RULE THIS PHASE EXISTS TO ENFORCE

Long-running workflows tolerate duplicate messages, delay, restart and partial failure — INV-013 — and a workflow coordinates modules without ever mutating their tables. Valid time and record time stay distinct, and a correction never erases the prior assertion — INV-017.

01

Preconditions

Entry criteria

BT-G2 is recorded

The broker core passed its trace and its domain UAT. P2 does not fix P1; a P1 defect found here goes back through the loop as a P1 package with its own authority.

The workflow runtime has an accepted ADR

ADR-010 decides which long-running operations need durable workflows and which runtime is suitable; its minimum acceptance evidence in the register is a replay and versioning spike. Until its row reads ACCEPTED, P2.4 has no runtime to be built on.

The servicing transactions are modelled

ADR-020 (endorsement, cancellation, refund basis, commission clawback and renewal as historical transactions) and ADR-015 (valid time, record time, correction) are accepted. ADR-016 is accepted before any placement that splits a risk by share or layer.

03

Execution order

Infrastructure first, the hard workflow second

The plan lists the ten epics unordered. This order is the track's proposal, derived from what each epic consumes from the ones before it.

  1. P2.10 — the event infrastructure. Every other epic emits and consumes. Building features on a transport that has not been made to fail is how a completed fact gets dropped in production for the first time.
  2. P2.4 — the durable binding workflow. The hardest epic, done early, because it is the one that exercises the runtime and decides whether ADR-010's choice holds. Take the P1 machine as it is; add durability, not features.
  3. P2.1, P2.2, P2.3 — placement. The natural sequence: open the market, send requests with evidence, receive and revise quotes. Multi-share and multi-layer placements wait for ADR-016.
  4. P2.5 — endorsement and cancellation. Needs the temporal model in place: effective time, record time, supersession. Do not build it on a single timestamp and promise to split later.
  5. P2.7 — renewal, which re-enters placement with the temporal rules from the previous step.
  6. P2.6 — claims. Two status fields from the first migration. The insurer's field is written only from sourced evidence.
  7. P2.8 — tasks, diary, SLA, on top of the flows that now exist to be tracked.
  8. P2.9 — the advice file, last, because it is assembled from everything above and should contain nothing new.
  9. The failure exercise — delayed, duplicate and conflicting external interactions against every workflow — then BT-G3.
04

What the agent codes

The failures, and the shortcuts that are prohibited

Each row below is a test in P2. The prohibited shortcut is what the test proves does not happen. A workflow that passes its happy path and has no test per row has not been built to this phase's contract.

Failure classification — rendered from FLOWS.md §16
FailureOwning responseProhibited shortcut
Provider timeoutRetry with a bounded policy; preserve the pending stateAssume success
Duplicate callbackReturn the prior idempotent resultRepeat a financial or binding mutation
Conflicting insurer messagesQuarantine and require reviewLast-write-wins coverage
Event transport unavailableRetain in the outbox and alert on backlogDrop completed facts
Consumer unavailableRedeliver and monitor ageEdit the consumer's tables directly
Ledger imbalanceReject the posting atomicallyPost a partial journal
Tenant context mismatchDeny before domain executionTrust the request's tenant identifier
Stale aggregate versionReject, or retry from fresh stateOverwrite a concurrent change
Workflow code upgradeVersion the workflow behaviour and test replayBreak in-flight cases
  • Activities are idempotent because they will be retried. The candidate runtime's own documentation says so; a business effect that is not safe to run twice is wrapped in an idempotency key before it is wrapped in an activity
  • A workflow coordinates; it does not own tables. Binding, policy and ledger each apply their own transition rules to the workflow's requests, and each may refuse
  • Consumers deduplicate by stable event identity and retain their processing outcome, because delivery is at-least-once unless a provider contract proves otherwise
  • Every servicing fact carries both times — effective_from, effective_to, effective_timezone, recorded_at, supersedes_id — from the first migration, using the expand-then-contract sequence if a P1 table must grow
  • Telemetry reports a breach; invariants prevent a transition. An SLA alert and a prohibited state change are different mechanisms and never the same code path

Stop signal: a workflow writes to another module's table

Convenient, fast, and the end of the module boundary. The workflow asks; the module decides.

Stop signal: conflicting insurer messages resolve automatically

The latest message winning is a coverage decision nobody made. Quarantine is the only correct automatic response.

Stop signal: a completed fact was lost while the transport was down

There is an outbox or there is not. If a fact can be dropped, P2.10 is not finished, whatever else has been built on it.

Stop signal: the broker's claim status changes the insurer's

Two fields exist because two authorities exist. A single field, or a broker write to the insurer's, is the failure claims advocacy exists to avoid.

Weekly

Workflow backlog and retry-age telemetry, read by a person; whether the failure rows are being written as tests or deferred; whether any P3 concept — an invoice, a payment, a journal — has appeared in a P2 branch.

07

Halt

Stop conditions

  • A workflow runtime is in use and ADR-010 is not accepted
  • A workflow mutates a module's table directly
  • A duplicate callback repeats a binding or financial mutation
  • Insurer claim state is written from anything other than sourced insurer evidence
  • A servicing fact is stored with one timestamp, with the split promised for later
  • Scope drifts into P3 — an invoice, a payment, a journal — inside a P2 package
