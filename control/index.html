CTL

Derived surface · not a record

The records as they are, assembled once

The guide is read; it is not operated. An agent resuming, or a human asking what is waiting on them, opens AGENTS.md, then badf/current-state.json, then badf/next-actions.json, then the tracker, and assembles the answer by hand every time. This page assembles it once, from those files and from the validator that reads them.

Every value below is copied from a source file in that file's own words. The panels do not re-word state, authority or resume_decision, and they add no status vocabulary of their own; whether the guide should adopt separate status axes is issue #302, which is open and an operator's. The page lists no map's tickets (#301), reads no tracker (#311), and offers no control that writes anything.

WHAT THIS PAGE IS, AND WHAT IT IS NOT

This page is derived and non-authoritative. It grants nothing, authorises nothing, accepts nothing and records nothing. The records under badf/ and the decisions on the issue tracker remain the only sources of truth; where this page and a record disagree, the record is right and this page is stale. Nothing on it may be cited as authority for doing anything.

Generated at build time, committed empty

The tracked control/index.html carries an empty, clearly-marked placeholder in every panel. The data is injected into the published copy by .github/workflows/pages.yml after the site artifact is staged and before it is verified, so nothing generated is ever committed. Run python scripts/build_control_page.py to project the records into your own working copy and look at it; a test holds the committed file to its placeholder state, so a regenerated copy must not be committed.

03

Step 8, performed

Reconciliation

The resume protocol's step 8 — reconcile observed state with recorded state — is performed by scripts/validate_continuity.py, which compares the recorded active Work Package and baseline against the observed main line and prints one of four words: CONSISTENT, LAG_EXPECTED, DIVERGED or UNKNOWN. This page invokes that validator and reads what it printed; it does not reconcile anything itself. The verdict is advisory there and advisory here: it cannot fail a build and it says nothing about whether the work is right.

An UNKNOWN here is expected, not a defect

The Pages workflow checks out with actions/checkout@v7 and no fetch-depth, so every published copy of this page is built from a shallow clone in which the history the reconciliation needs is simply absent. On the published page the verdict will normally read UNKNOWN with a reason naming the shallow clone, and that is the honest answer rather than a fault. To see one of the other three words, run the validator, or this projector, against a full clone.

This panel has not been generated. Run python scripts/build_control_page.py to invoke scripts/validate_continuity.py and project what it printed into it.

04

What is waiting on a person

Human action queue

The actions of badf/next-actions.json whose recorded authority waits on a human, in the record's own priority order. The filter, stated so that the count can be checked: an action is admitted when its recorded authority contains HUMAN or WAIT, or its recorded owner_role contains human. Those are substrings of strings the record already spells; the filter renames nothing and adds nothing. The actions it did not admit are listed under the table with the authority string each carries, because a count is only as good as its filter.

What the filter cannot do, and why every row shows its authority verbatim. The match is a plain substring test and it does not read negation. An authority of GRANTED_NO_HUMAN_REVIEW_REQUIRED contains HUMAN inside a phrase that denies human involvement, and this panel would admit it anyway; so would AWAITING_NOTHING_AUTOMATED, on WAIT. Both were run against the filter and both are admitted. Neither is a real authority string: no recorded action spells anything of the kind today, and this paragraph is the only place in the repository either of them appears. Teaching the filter to read negation would mean deciding what counts as one, which is a classification the records do not make and is not this page's to invent. What the page does instead is print the authority string on every row of both lists, so a reader meets the phrase itself and can see what a substring could not.

This panel has not been generated. Run python scripts/build_control_page.py to project badf/next-actions.json into it.

05

What is granted, and to what

Authority, grouped by the domain each key names

Every key of the record's authority block, with its value copied verbatim. The grouping rule: the key's first underscore-separated segment is the domain it names, and a key that is a single segment names no domain at all and renders under Unscoped.

Why a key can end up Unscoped

implementation sits beside production_platform_implementation in the live record, and in a flat list a reader can take the one for the other. That defect is issue #346 and it is open. A key that names no domain is not placed under a guessed one here: it renders under Unscoped and says so, because guessing which domain it meant is the whole of the defect. Fixing the key itself is a records edit and is not this page's to make.

This panel has not been generated. Run python scripts/build_control_page.py to project the authority block of badf/current-state.json into it.

06

Whether the records hold together

Integrity

The validator's own output, check for check, in the order it printed them. This panel counts nothing itself: every row is a line scripts/validate_continuity.py emitted, so a check that is added, renamed or removed there appears here without this page being edited. A failing run renders its ERROR lines as rows rather than being summarised away.

What a PASS here does and does not mean

Each row is a check that ran and recorded no error. The validator tests presence and shape — in its own words, a file that exists and parses satisfies its check — so a green table says the records are structurally intact, mutually consistent in the ways it checks, and readable by the tools that read them. It says nothing about whether their contents are right, whether the work they describe is any good, whether a Work Package is finished, or whether a gate has been met. A table of green rows is a count of checks that ran, not a verdict on quality; the reconciliation above is likewise advisory and cannot fail this run.

This panel has not been generated. Run python scripts/build_control_page.py to invoke scripts/validate_continuity.py and project its check list into it.

08

Limits

What this page does not do

  • It records nothing and grants nothing. There is no Authorize, no Accept, no Record Gate and no Close on it; a decision is recorded where the records and the tracker say it is recorded, and this page only says where that is
  • It adds no status vocabulary. state, authority and resume_decision are rendered exactly as the records spell them; whether the guide should carry separate status axes is #302, open and an operator's
  • It is not a second map index. It lists no map's tickets; #301 is open on whether maps stay issues at all
  • It fetches nothing. The projector calls git and the validator against the local checkout and nothing else, no script on this page reads any data source, and no tracker is synchronised at build time or in the browser — #311 is the open decision about whether anything should
  • It shows no completion percentage. A percentage needs a denominator and a metric stated beside it, and neither is settled: the completion matrix is #307, which waits on #302
  • It does not reconcile the record against itself. The verdict in panel 03 reads two recorded fields, the active Work Package and its baseline, and says nothing about whether the rest of the record agrees with them
  • It is not a phase, epic or evidence projection, and it changes no existing page. Those are the rest of BIZTRUST-GUIDE-DYN-001, each worth doing and none needed to prove this surface
