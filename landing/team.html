Whether to trust the delivery system comes down to who can say yes

Projects BIZTRUST-PLAN-001 1.0-draft, sections 12.1, 13 and 13.1, and BIZTRUST-ROADMAP-001 operator draft, sections 2, 8H, 9, 10 and 11; read at 04ae702, 2026-09-06.

BizTrust would be built largely by software agents, so the first question a reader should ask is not how good the agents are but what they are allowed to decide. The plan's answer is a model of three kinds. A seat is a human who holds authority: the seat grants implementation authority per Work Package, records a gate, accepts an architecture decision or a tenant's authority profile, and may be dissented from on the record. A role is a responsibility within one stage, held by a human or an agent as the stage says; a role holds no authority of its own and acts under a seat's grant. A persona is an agent identity under the orchestrator; a persona holds no authority, is granted implementation authority per Work Package by a seat, and never records a gate. The handbook's eight groups are lenses that seats, roles and personas share, not a fourth kind.

The roadmap binds every agent by eight things, copied here in its order. The plan's table says how each kind is bound by them; for a persona the answer is all eight, with authority granted and never held, evidence bound to a revision, independent review by a different persona or a human, a gate it never records, and human authorisation it requests.

  1. Identity
  2. Assigned Work Package
  3. Authority
  4. Permitted Tools
  5. Evidence Requirement
  6. Independent Review
  7. Gate
  8. Human Authorization when required

The loop every Work Package would run

The roadmap gives one loop for every Work Package in every phase, twenty-four steps from understanding to the next controlled iteration, and says it extends the handbook's nine-stage lifecycle. Four steps are worth a reader's attention because the mapping had to say where the handbook carries them. Threat and risk analysis was a gap with a proposed owner until the Architect manual was given a section for it. Security review is carried under another name, as the assurance stage's security reviewer. Evidence collection is carried by a rule rather than a step: evidence is bound to a revision at every stage. Feeding knowledge back is carried by records rather than a step: checkpoints and decision records, not memory. And step 18, gate evaluation, belongs to no single stage, because every stage ends in its own exit gate and the phase gates are a different namespace. The handbook renders the full mapping as its Work Package loop reference page.

When a Work Package is done, and why a gate is not part of it

The roadmap's rule is that a Work Package never reaches done from code completion alone, and it lists seventeen things that must be true. The handbook's Definition of Done has eight items. The plan reconciles them: the eight stand as the Definition of Done, and the roadmap's items are what each of the eight must show. The table is copied cell for cell.

Guide itemRoadmap items it carries
Acceptance criteria passRequirements satisfied; code complete; unit tests; deterministic business-rule tests
Contracts and docs updatedArchitecture conformant; contract tests; documentation
Negative tests includedTenant isolation validation; integration tests; web and mobile end-to-end where relevant; migration tested
Threat model reviewedSecurity validation
Telemetry implementedObservability implemented
Rollback validatedRollback strategy
Evidence manifest signedEvidence generated
Independent review completeIndependent review

One roadmap item is deliberately left out: gate passed. The plan's reason is the one a reader deciding whether to trust the system should hold on to. A gate closes a phase, not a package; a package is done when its eight items are shown, and a phase is closed when its gate's owner records it, so putting the gate inside the package's definition would let a package claim a phase. Read as a stage gate instead, passing it is the lifecycle the eight items feed, not a ninth item.

The doctrine sentence the contract does not yet carry

The showcase record reserves one place on this page for a sentence: the product doctrine, once the architecture contract carries it. The roadmap states the doctrine as its section 2: BizTrust should remain defined as a multi-tenant insurance brokerage, distribution and insurance API platform; it is not primarily an insurer's policy administration system; and the distinction between an insurer core, which holds underwriting authority, risk acceptance, authoritative pricing, policy issuance authority, claims adjudication and insurance liability, and the BizTrust broker core, which holds the client, the risk, placement, comparison, recommendation, binding coordination, the broker's policy record, servicing, claims advocacy, renewal, premium collection, commission, settlement and partner interfaces, should remain architectural, so that BizTrust never appears to be the risk carrier.

That is the operator's draft. The doctrine ticket on the Guide v2 map would carry it into the contract's first section, and it waits on the operator's waiver of the contract map's ordering. Until it lands, the contract's own position sentence is the definition of record, as the architecture page says, and this page carries no doctrine sentence of its own.
