P0 would prove who did what, under which tenant, with which authority, against which resource

Projects BIZTRUST-PLAN-001 1.0-draft, sections 4, 10 and 12.1, FLOWS.md 0.1-draft, section 3, and the P0 manual, sections 01 and 04 to 07; read at 965cdfe, 2026-09-06.

The first phase of the plan builds no insurance. Its objective, in the plan's words, is to prove who performed what, under which tenant, with which authority, against which resource, before any client, policy, claim or premium data exists on the platform. Everything later in the roadmap rests on that proof: a policy record is only trustworthy if the platform can already show, for every request, which person or service acted, for which tenant, with what permission, and on which resource.

The plan's label table names the phase's gate BT-G1, Identity and Tenant Proven, label B. The plan's rule for leaving it is one sentence: no P1 authorization may be issued until this proof passes independently. The rest of this page says what the proof is, what would be built to run it, what the evidence looks like, and who records the gate.

The sequence every protected request would walk

The flows record draws the tenant authorization sequence as one path with two ways to be refused. A request is refused before any data is touched when its context or authority is invalid, and refused by the database itself when an application check has been bypassed. Either way the refusal is written down. The six steps, in the order the record draws them:

1. Logto issues the tokenThe user or service requests an API token with organization context and receives a signed token carrying audience, organization and scopes.
2. APISIX admits the requestThe protected request reaches the edge, which passes a validated edge request to the BizTrust API.
3. The API checks the tokenSignature, issuer, audience and expiry are verified before anything else happens.
4. Business authorization resolves the authorityTenant, membership, scope and authority are resolved. If any is invalid, the denial is recorded and the caller receives problem details.
5. PostgreSQL enforces isolationThe API sets a trusted tenant context and executes the command; row-level security allows tenant-owned rows or denies, and a denial is recorded without cross-tenant disclosure.
6. Audit evidence records the outcomeDenied decisions, isolation denials and successful actions are all recorded before the response returns.

One rule in the record binds the fourth and fifth steps together: the API must not copy an untrusted tenant identifier from a request header straight into a database session variable. The authenticated organization, the BizTrust tenant it maps to, and the resource being asked for are reconciled first, so that the tenant context the database trusts is one the platform established and not one the caller supplied.

Source: FLOWS.md section 3, the tenant authorization sequence, for the participants, the two denial branches and what each branch records; the paragraph beneath it for the rule that an untrusted X-Tenant-ID is never copied directly into a session variable; the sentence after it, on why the rule holds, is this page's reading. The six steps are this page's grouping of that sequence, and the plan's section 10.3 names the same chain for Gate B: authenticated identity, validated tenant context, authorised operation, tenant-isolated data access, immutable audit evidence.

The negative proof, in plain words

Most software is shown to work by demonstrating what it does. P0 is shown to work by demonstrating what it refuses. The plan carries seven lines of mandatory proof, copied here word for word. Two tenants, A and B, would be provisioned. The first line says A reaches its own data; the other six say that everything else, from a missing token to a tampered identifier to a bypassed application check, is refused and recorded.

  1. Tenant A can access authorized Tenant A data.
  2. Tenant A cannot read, create, update or delete Tenant B protected data.
  3. Missing or invalid organization context is denied.
  4. Tampered URL, header, body and query tenant identifiers are denied or ignored safely.
  5. Wrong audience, expired token, inactive membership and absent scope are denied.
  6. An application-level authorization bypass test remains blocked by RLS.
  7. Every outcome produces tenant-safe audit evidence.

The flows record turns those lines into a minimum matrix of attempts. Each row is one thing an attacker, a bug or a careless integration might do, and each states three expectations: what the API answers, what the database is permitted to do, and what the audit trail must show afterwards. In plain words, row by row: a request with no token, or a token that has expired or been tampered with, is refused before the platform runs any query on business data, and the refusal is written down with a reason that gives nothing away. A token issued for some other service is refused the same way. A token that carries no organisation cannot open a tenant's routes at all. A member whose membership has been switched off can change nothing. Tenant A asking for Tenant B's address gets a refusal, no row of B's is read, and the record of the refusal contains none of B's data. Tenant A slipping B's identifier into the body or a header of its request has that value ignored or refused, and the database's own write check stops the write even if the application had let it through. And in a test path where the application's check is deliberately switched off, the database refuses on its own and the refusal is traceable to that test.

That last row is the one that makes the proof mean something. The manual keeps two failures from passing as successes: a suite whose evidence shows only successes has tested the wrong property, and a bypass test that is absent, skipped or was never seen to fail has not demonstrated the policy.

What every decision would write down

The proof only counts if the refusals can be read back later by someone who was not there. The P0 manual states what each authorization decision records: the decision itself, the actor, the tenant, the membership, the permission, the resource and its scope, the conditions evaluated, the approval reference, the policy version, the outcome, a reason code, and the request and trace identifiers that tie the record to the logs. It states equally what the record never holds: a raw token, a secret, or a personal datum the decision did not need.

Read as a question, that record is the phase's objective: who, under which tenant, with which authority, against which resource, and with what result. The gate below asks for that record on every row of the matrix.

Source: the P0 manual, phases/p0.html section 04, the rule that every decision writes the full evidence record and never a raw token, secret or unnecessary personal datum, restated here in this page's words; BIZTRUST-PLAN-001 section 4 for the objective the record answers.

Gate B would be recorded by a security risk owner, after someone else has run the proof

The plan's gate for P0 is BT-G1 Security Ready, label B, and its condition is that tenant isolation is mechanically proven by the P0 negative-test evidence. The P0 manual adds what turns that evidence from a report into a record, and proposes the seat that would record it: the plan names no role for it, and its own seat table is marked as a proposal.

BBT-G1 Security Ready: tenant isolation mechanically proven

The chain authenticated identity, validated tenant context, authorised operation, tenant-isolated data access, immutable audit evidence is mechanically demonstrated, and the mandatory proof passes independently of the implementer. The security risk owner, the seat the manual proposes, would record the gate having seen the full matrix executed by someone other than the implementer, bound to a source revision, with an audit record for every row.

The manual's gate section lists the seven proof lines and four further conditions: the proof was executed by someone who did not implement it; the evidence manifest binds the run to a source revision, workflow, environment and tool versions; ADR-002, ADR-003 and ADR-004 are accepted in the register; and the security risk owner has recorded the gate with a date. The manual permits no P1 authorization until every one of them is ticked; the plan's own rule is the sentence quoted at the top of this page, that the proof passes independently.

Where P0 stands

P0 has not startedThe manual's first entry condition is that BT-G0 Architecture Ready, label A, is recorded. The handbook's continuity state records architecture acceptance and production platform implementation as not granted.
The designs are a templateThe P0 design pack exists at 0.1-draft and states that no design is accepted by it. The design map for P0 is issue #128 on the repository.
