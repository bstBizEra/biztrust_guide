Reference · not a stage

Artifact catalogue

The nine stage manuals name 63 artifacts, 55 of them required at an exit gate. Until this page existed none of them had a stated format or a stated location, so “hand over the constraint register” was an instruction two engineers could satisfy in two incompatible ways and both be right.

This table is a lookup, not guidance. It restates no rule: for what an artifact must contain and why, follow the stage link in the first column. What it adds is the four facts a gate condition needs before it can be checked at all — what shape the thing is, where it goes, who writes it, and who accepts it.

WHAT THIS TABLE IS FOR

An exit-gate condition that names an artifact nobody can locate is not a condition. It is a sentence.

01

How to read this

Three kinds of location, and one warning

The Path column carries one of three answers, and the difference between them matters more than any single row. Guessing a path would have filled the column and taught a reader something false. One row — Build’s telemetry — belongs to none of the three, because it is instrumentation inside the implementation rather than a document with a location of its own.

A path in monospace

A file that exists in this repository today. Seven rows. Open it and you will find the artifact’s real shape.

A directory, marked target layout

A directory the guide’s own repository design assigns to that artifact, where that directory’s own comment names it. Fourteen rows. Nothing has created any of them.

NOT YET DEFINED

Forty-one rows. Nothing in the guide says what shape the artifact takes or where it lives. This is the finding, not an omission in the table.

The roles here are the stage manuals’ roles, and only those

The nine stage pages name 28 distinct roles. The guide’s front page names a separate nine — SARCHI, Product & Domain, Architecture, Engineering, and so on. The two vocabularies never meet: no page maps one onto the other, and no page says they are the same people. This table uses the stage vocabulary because that is where the exit gates are written. It does not merge them, and a reader should not assume a mapping that the guide has not made.

03

What the table makes visible

Six things that only show up once the rows are side by side

Eight artifacts are named and never gated

Architect’s bounded context map, state machines and integration boundaries appear in its outputs table and in no exit-gate condition. Five Operate artifacts — recovery objectives, capacity forecast, dependency inventory, secret rotation and the disclosure route — are named in the body and required by nothing. Producing none of them fails no check.

One gate condition has no artifact behind it

Architect’s gate requires that “deferred decisions are written down with their revisit triggers”, but the outputs table lists no deferred-decision register. The condition is gated and the thing it gates is unnamed — the exact inverse of the three rows above it.

Two stages once produced artifacts through no outputs section

Plan and Operate had none when this table was built. Plan’s Work Package was described field by field instead, and its four rows here were read off that description and off this repository’s two state files; Operate’s thirteen were reconstructed from its gate and its prose, which is why five of them turn out to be ungated. Both gained one — Operate under WP-033, Plan under WP-037 — naming the same rows and adding nothing. A stage with no outputs section cannot be checked for whether its gate names things it produces; every stage can be now.

Four artifacts have no named author

Define’s roles table gives the accepting authority the job of closing the open questions register and gives nobody the job of writing it. Operate’s alert definitions and escalation rota name a responder who answers them and no owner who sets them. Recorded here rather than resolved: assigning an owner would be a content decision, not a transcription.

Seven of 63 artifacts have somewhere to go today

Five live in the two GitHub templates this repository already ships — four of them are the same work-package form, read for different fields — and two in its badf/ state files. Fourteen more have a directory named in the guide’s repository design and nothing that creates it. The remaining 41 have no stated home at all — among them the constraint register, which Architect’s entry criteria require to be “known and written” before the stage may begin, and which therefore has to arrive from somewhere.

27 artifacts have no named accepter

Where a stage’s gate names an artifact and its owner but nobody who receives it, this table says not named rather than promoting the stage’s accepting authority into the gap. Discover is the clean case to copy: its gate ends with the problem statement signed by the accepting authority, dated and bound to the Work Package, so exactly one artifact carries the stage’s acceptance and the other six do not pretend to.

05

Method and limits

How this was derived, and what it does not settle

  • Every row was read off a stage page — its outputs section, its exit gate, or, where a stage has neither, its body. No artifact was added because it seemed necessary.
  • Role names are copied verbatim from the roles table of the stage that produces the artifact. Where a stage names no role for an artifact, the cell reads not named.
  • A path in monospace was opened and confirmed present. A target layout directory is quoted from the guide’s repository design, where the directory’s own comment names that artifact.
  • Format descriptions summarise what the stage page says the artifact must contain. Where the page says nothing about shape, the cell says what the artifact is, not what file type it should be.
  • This page does not decide any of the ambiguities it records — an unnamed accepter stays unnamed here, because filling it in would be an invented rule wearing a table’s clothes.
  • It does not reconcile the two role vocabularies, and nothing here should be read as evidence that they correspond.
  • A target layout directory is not a promise that anything writes there. Nothing in this repository creates any of the fourteen.
  • Nothing is checked mechanically. No test asserts that a stage page and this table still agree, so a stage that gains an artifact will silently fall out of step.
