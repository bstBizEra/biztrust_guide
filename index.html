02

Foundation

Operating principles

Authority ≠ capability

An agent may possess the technical capability to modify or deploy, but may act only within explicitly granted scope, budget and risk boundaries.

Observation ≠ decision

Agents gather facts; policy evaluates facts; authorized stakeholders make decisions. These records remain separate and independently auditable.

Evidence ≠ assertion

“Tests passed” is not evidence. The authoritative run, immutable source revision, environment, output and verifier identity form the evidence bundle.

Completion ≠ acceptance

Implementation completion starts assurance. A work package closes only after validation, review, authority and evidence gates pass.

Human stakeholders own purpose, risk appetite and approval. Agents own bounded execution, transparent reasoning, verification and escalation.

Canonical state machine
  1. DRAFTIntent captured
  2. READYContracts complete
  3. AUTHORIZEDAuthority granted
  4. IN_PROGRESSBounded execution
  5. VALIDATINGIndependent checks
  6. ENGINEERING_READYEvidence complete, awaiting a human
  7. ACCEPTEDEvidence approved
  8. CLOSEDKnowledge retained

Any failed invariant transitions to BLOCKED; any unknown authority transitions to WAIT_FOR_AUTHORITY.

These eight states, in this order, are the machine declared by AGENTS.md §8 and listed as the state enum of schemas/session-checkpoint.schema.json — a declaration the pages restate: since WP-035 a test validates every committed checkpoint against that schema (three that predate it are registered as failing), but no gate reads the state it finds. Every page that shows package states restates this one; where a page disagrees, this machine wins. ENGINEERING_READY is the state the running system actually records — it is the value in badf/current-state.json and in every session checkpoint. No checkpoint has yet recorded ACCEPTED or CLOSED: both are declared, neither is exercised.

The ENG-G* prefix is load-bearing. Two gate namespaces exist and must never be confused: ENG-G0…ENG-G8 are the Work Package lifecycle gates above, while BT-G0…BT-G7 are BizTrust platform capability milestones (architecture ready through production ready), named in docs/architecture/DELIVERY_PLAN.md §1, tabled in BIZTRUST-PLAN-001.md §10 and used across the architecture pack. An unprefixed gate number belongs to neither namespace and should not appear in either.

Stage manuals

Each stage expands into an executable manual page — entry criteria, artifacts produced, roles, evidence required and the exit gate. All nine stages are written. Each carries entry criteria, the artifacts it produces, roles, evidence, an exit gate and stop conditions — and a stage links another stage's guidance rather than restating it, which a cross-page duplicate detector enforces in CI rather than leaving to good intentions.

Phase manuals

The stages say how one Work Package moves; the phases say what the Work Packages are between architecture freeze and production — in what order, landing where, proven how — and what a human watches between authorizations. From architecture to production · P0 Identity and Tenant · P1 Broker core · P2 Lifecycle · P3 Financial and integration. The overview renders docs/architecture/BIZTRUST-PLAN-001.md; the P0 page renders its section 4; the P1, P2 and P3 pages still render docs/architecture/DELIVERY_PLAN.md v0.1 until their tickets move them; every page labels the track's own additions as additions and carries no current-status facts; a test holds each page's epic identifiers and labels to the plan section named for it (P0: PLAN-001 §4; P1 to P3: v0.1 §4 to §6) and gate identifiers to PLAN-001 §10.

Persistent execution

Agent continuity

Agents resume from versioned repository facts—not from chat memory. A dual ledger connects human coordination in GitHub with machine-readable execution state in the repository.

HUMAN LEDGER

GitHub Issue + Project

Outcome, accountable owner, priority, discussion, approval, risk and milestone.

↕
DELIVERY CONTRACT

Work Package

Scope, exclusion, authority, acceptance criteria, evidence and rollback.

↕
AGENT LEDGER

Current state + checkpoint

Exact branch, baseline, completed work, blockers, evidence and one next action.

Mandatory resume sequence

01Read

`AGENTS.md`, current state and next actions

02Resolve

Active Work Package, issue and authority

03Observe

Branch, HEAD, worktree and remote divergence

04Validate

Run deterministic continuity checks

05Reconcile

Compare observed and recorded state

06Decide

Continue, block, recover, wait or complete

First safe command for every new session
python3 scripts/validate_continuity.py
CONTINUITY INVARIANT

A new agent must be able to identify the authorized outcome, authoritative revision, verified evidence, blockers and exactly one next safe action without access to prior chat history.

Stable identity

One Work Package ID follows issue → branch → commit → PR → evidence.

Fresh checkpoints

Persist state at every coherent slice, blocker, authority boundary and handoff.

Explicit handoffs

Sender records; receiver independently verifies and acknowledges.

Fail-closed recovery

Missing or conflicting state becomes `RECOVERY_REQUIRED`, never implicit permission.
