# Mobile release pipelines and compatibility controls, from the store operators' own documentation

## Ticket

[#162](https://github.com/bstBizEra/biztrust_guide/issues/162), a research ticket on the [Guide v2.0 wayfinder map (#153)](https://github.com/bstBizEra/biztrust_guide/issues/153). It blocks [#169](https://github.com/bstBizEra/biztrust_guide/issues/169), the P3 manual, whose mobile-production section must source every definition from this file.

Every claim below is cited to a first-party page: Apple (developer.apple.com, support.apple.com) or Google (support.google.com/googleplay, developer.android.com, source.android.com). All URLs were checked on **2026-09-06**. Quotations are verbatim from the page as served that day. Anything the operators' pages did not state is listed under *Unverified items* and must not be cited as fact.

## Question

P3H (mobile production) and the P1 customer and agent mobile clients need the store pipelines stated from the store operators' own documentation: what each release stage is called, what it requires, how each platform lets a publisher control minimum OS versions and push forced updates, what the biometric-unlock and secure-storage APIs guarantee and do not, and what the operators say about review timing and rejection. The answer is a fact base, not a design; the design belongs to #169 and to `OPS-001`/`UX-001`.

## Pipeline table per platform

### Apple (App Store, App Store Connect, TestFlight)

| Stage | What Apple calls it | What it requires (as documented) | Source |
|---|---|---|---|
| Internal beta | TestFlight, **internal testers** | "up to 100 App Store Connect users with access to your content"; on the TestFlight product page: "Designate up to 100 members of your development team who hold the Account Holder, Admin, App Manager, Developer, or Marketing role as beta testers." No Beta App Review is stated for internal groups. | [S1](https://developer.apple.com/help/app-store-connect/test-a-beta-version/overview-of-testflight), [S2](https://developer.apple.com/testflight/) |
| External beta | TestFlight, **external testers**, gated by **Beta App Review** | "up to 10,000 people". "When you add the first build of your app to a group, the build gets sent to App Review to make sure it follows the App Review Guidelines. A review is required only for the first build. Subsequent builds may not require a full review." Testers install through the TestFlight app; public links are supported. | [S1](https://developer.apple.com/help/app-store-connect/test-a-beta-version/overview-of-testflight), [S2](https://developer.apple.com/testflight/) |

In Review: "App Review is reviewing your app. You can remove the build from review." | Accepted | *Pending Developer Release* / *Ready for Distribution* | Pending Developer Release: "Your app was accepted, but you still need to release it for distribution on the App Store." Ready for Distribution: "Your app has been accepted and is ready for distribution. To distribute your app, your agreements must be in effect." | [S4](https://developer.apple.com/help/app-store-connect/reference/app-and-submission-statuses) |
| Gradual production rollout | **Phased release** (for version updates) | "Selecting this option will release your app's update gradually over 7 days." Documented schedule: day 1 = 1%, day 2 = 2%, day 3 = 5%, day 4 = 10%, day 5 = 20%, day 6 = 50%, day 7 = 100%. "A random sample of users with automatic updates on eligible devices will receive the update, without any notification of their participation in the phased release." "apps and app updates in phased release can be manually downloaded from the App Store by anyone at any time." "you may pause the release for up to 30 days, with no limit on the number of pauses" (30 days total). "you can release it to all users at any time once it has the Ready for Distribution status." "If you remove your app from sale ... phased release will stop and won't be available for that version again." | [S6](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases) |

Apple's page documents no percentage other than the fixed seven-day curve, and no way to halt a phased release other than pausing it or removing the app from sale. There is no documented "rollback to previous version" step on any page checked.

## Minimum-version and forced-update mechanisms

### Apple

| Control | What Apple documents | Source |
|---|---|---|
| Minimum OS version | `MinimumOSVersion` (iOS, iPadOS, tvOS, watchOS, visionOS): "The minimum version of the operating system required for the app to run". "The App Store uses this key to indicate the OS releases on which your app can run." "Don't specify MinimumOSVersion in the Info.plist file for apps built in Xcode. It uses the value of the Deployment Target in the General settings pane." macOS uses `LSMinimumSystemVersion`. | [S18](https://developer.apple.com/documentation/bundleresources/information-property-list/minimumosversion), [S19](https://developer.apple.com/documentation/bundleresources/information-property-list/lsminimumsystemversion) |
| Currently shipping OS | Review Guideline 2.5.1: "Apps may only use public APIs and must run on the currently shipping OS." | [S20](https://developer.apple.com/app-store/review/guidelines/) |
| Forced update | **No first-party forced-update or in-app-update API is documented.** Distribution of a new version is by App Store automatic updates or manual download; phased release itself only reaches "users with automatic updates on eligible devices". Guideline 2.5.2 forbids self-updating outside the store: apps "may not ... download, install, or execute code which introduces or changes features or functionality of the app". A minimum-supported-version check is therefore the app's own responsibility, against a server-side value, with the App Store product page as the only update path. | [S6](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases), [S20](https://developer.apple.com/app-store/review/guidelines/) |

### Google

| Control | What Google documents | Source |
|---|---|---|
| Minimum OS version | `android:minSdkVersion`: "The Android system prevents the user from installing the application if the system's API level is lower than the value specified in this attribute." "Google Play uses the `<uses-sdk>` attributes declared in your app manifest to filter your app from devices that don't meet its platform version requirements." Play filters: a device below `minSdkVersion` gets "Google Play will not show the app to the user." `maxSdkVersion` is deprecated and "not recommended". | [S21](https://developer.android.com/guide/topics/manifest/uses-sdk-element), [S22](https://developer.android.com/google/play/filters) |
| Target API level (store-enforced floor) | "New apps and app updates must target Android 16 (API level 36) or higher to be submitted to Google Play" (from 31 August 2026, with Wear OS, Automotive, TV and XR exceptions). "Existing apps must target Android 15 (API level 35) or higher to remain available to new users on devices running Android OS higher than your app's target API level." Apps targeting API 34 or lower "will only be available on devices running Android OS that are the same or lower than your apps' target API level." Extension to 1 November 2026 may be requested. | [S23](https://support.google.com/googleplay/android-developer/answer/11926878) |
| Forced update, flexible update | **Play In-App Updates** (Play Core / `com.google.android.play:app-update`). Two flows. Immediate: "fullscreen UX flows that require the user to update and restart the app in order to continue using it ... best for cases where an update is critical to the core functionality of your app. After a user accepts an immediate update, Google Play handles the update installation and app restart." Flexible: "background download and installation with graceful state monitoring ... appropriate when it's acceptable for the user to use the app while downloading the update." Requirements: "supported on devices running Android 5.0 (API level 21) or higher" and "only supported for Android mobile devices, Android tablets, and ChromeOS devices"; "not compatible with apps that use APK expansion files (.obb files)". | [S24](https://developer.android.com/guide/playcore/in-app-updates) |
| Update priority and staleness | "Google Play uses an integer value between 0 and 5, with 0 being the default and 5 being the highest priority." Set with "the `inAppUpdatePriority` field under `Edits.tracks.releases` in the Google Play Developer API." "Priority can only be set when rolling out a new release and cannot be changed later." `clientVersionStalenessDays()` reports "the number of days since the update became available on the Play Store". An immediate update left in `DEVELOPER_TRIGGERED_UPDATE_IN_PROGRESS` must be resumed at every app entry point. | [S25](https://developer.android.com/guide/playcore/in-app-updates/kotlin-java) |
| Testing forced update | "In-app updates are only available to user accounts that own the app." Test build must have "the same application ID and signing key as the version available from Google Play" and "a lower version code than the update version code". "The `inAppUpdatePriority` field is not supported when uploading your app to internal app sharing." | [S26](https://developer.android.com/guide/playcore/in-app-updates/test) |
| Self-update outside Play | Device and Network Abuse policy: "An app distributed via Google Play may not modify, replace, or update itself using any method other than Google Play's update mechanism." "an app may not download executable code (such as dex, JAR, .so files) from a source other than Google Play." | [S27](https://support.google.com/googleplay/android-developer/answer/9888379) |

Note the asymmetry: only Google documents an in-app forced-update flow, and it is a *consent* flow ("when the user consents to begin the update"). Neither platform documents a way to push a version onto a device without user or automatic-update participation. A hard minimum-supported-version gate is app logic on both platforms; the in-app update API is Android's convenience for the update step, and Apple's equivalent is a link to the App Store.

## Biometric unlock and secure storage APIs

### Apple: Local Authentication and Keychain Services

| Topic | What the documentation guarantees | What it does not guarantee, or leaves to the app | Source |
|---|---|---|---|
| What the app receives | "To maximize security, your app never gains access to any of the underlying authentication data. You can't access any fingerprint images, for example. The Secure Enclave, a hardware-based security processor isolated from the rest of the system, manages this data out of reach even of the operating system." "Afterward, you receive only a Boolean result indicating authentication success or failure." | A Boolean from `evaluatePolicy` is not a cryptographic proof; it protects UI, not data. Data protection comes from keychain access control (next rows). | [S28](https://developer.apple.com/documentation/localauthentication) |
| Policies | `deviceOwnerAuthenticationWithBiometrics`: "User authentication with biometry." `deviceOwnerAuthentication`: "User authentication with biometry, Apple Watch, or the device passcode." Companion-device variants exist; Watch-specific ones are deprecated. | The `LAPolicy` page does not describe lockout thresholds or automatic fallback steps; failure modes are reported as `LAError` codes: `biometryLockout` "Biometry is locked because there were too many failed attempts", `biometryNotEnrolled`, `biometryNotAvailable`, `passcodeNotSet` "A passcode isn't set on the device", `userFallback`, `userCancel`, `authenticationFailed`. | [S29](https://developer.apple.com/documentation/localauthentication/lapolicy), [S30](https://developer.apple.com/documentation/localauthentication/laerror-swift.struct/code) |
| Enrollment-change detection | `LAContext.evaluatedPolicyDomainState`: "Compare the values you get from successive calls to this property to determine whether the authorized database changed." | "the value you get doesn't describe the nature of a change; it only lets you detect if a change happens." "The value of this property is different in different processes". **Deprecated as of iOS 18.0 / iPadOS 18.0 / macOS 15.0 / visionOS 2.0**; the supported mechanism is keychain access control with `biometryCurrentSet` (below). | [S31](https://developer.apple.com/documentation/localauthentication/lacontext/evaluatedpolicydomainstate) |
| Review-guideline constraint | Guideline 2.5.13: "Apps using facial recognition for account authentication must use LocalAuthentication (and not ARKit or other facial recognition technology) where possible, and must use an alternate authentication method for users under 13 years old." | | [S20](https://developer.apple.com/app-store/review/guidelines/) |
| Keychain storage | "store small bits of user data in an encrypted database called a keychain". Platform Security guide: "Keychain items are encrypted using two different AES-256-GCM keys: a table key (metadata) and a per-row key (secret key)"; the secret key "always requires a round trip through the Secure Enclave". | Keychain is for "small chunks of data"; not documented for bulk data. | [S32](https://developer.apple.com/documentation/security/keychain-services), [S33](https://support.apple.com/guide/security/keychain-data-protection-overview-secb0694df1a/web) |
| Accessibility classes | `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly`: "If the user hasn't set a passcode, you can't store an item with this setting. If the user removes the passcode from a device, any items with this setting are automatically deleted from the keychain. You can only access items with this setting if the device is unlocked." `WhenUnlocked` is the default; `AfterFirstUnlock` is for background access; "Always ... isn't recommended." `ThisDeviceOnly`: "the item can be restored to the same device that created a backup, but it isn't migrated when restoring another device's backup data." Platform Security guide: `WhenPasscodeSetThisDeviceOnly` items don't sync to iCloud Keychain, aren't backed up, and aren't included in escrow keybags. | "A device without a passcode is considered to always be unlocked." Without the `WhenPasscodeSet` class the keychain does not require a passcode at all. | [S34](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility), [S33](https://support.apple.com/guide/security/keychain-data-protection-overview-secb0694df1a/web) |
| Biometric-gated items | `SecAccessControlCreateFlags`: `userPresence` "Constraint to access an item with either biometry or passcode." `biometryAny` "Constraint to access an item with Touch ID for any enrolled fingers, or Face ID." `biometryCurrentSet` "Constraint to access an item with Touch ID for currently enrolled fingers, or from Face ID with the currently enrolled user." Discussion: "The item is invalidated if fingers are added or removed for Touch ID, or if the user re-enrolls for Face ID." `devicePasscode`, `and`, `or`, `applicationPassword` are documented. Sample project: "keychain services only provides the data after a successful user authentication event." | `userPresence` "request[s] biometric authentication, or to fall back on the device passcode": passcode fallback is on unless the flags exclude it. Invalidation on re-enrollment is only with `biometryCurrentSet`. | [S35](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags), [S36](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/biometrycurrentset), [S37](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id) |
| Secure Enclave keys | "Works only with NIST P-256 elliptic curve keys. These keys can only be used for creating and verifying cryptographic signatures, or for elliptic curve Diffie-Hellman key exchange (and by extension, symmetric encryption)." "Can't encode preexisting keys. You must use the Secure Enclave to create the keys." "You receive only the output of these operations". "Requires hardware support. Only iOS devices with an A7 or later processor, or a Mac with the Touch Bar and Touch ID or with an M1 or later processor support this feature." `privateKeyUsage` can be combined with `biometryAny` so the key is "available only when the system can authenticate the user with Touch ID or Face ID (or a fallback passcode)". | No RSA, no symmetric key import, no key export. Apple documents no remote attestation of a Secure Enclave key on these pages (App Attest / DeviceCheck are separate frameworks, not checked here). | [S38](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave) |

### The one guarantee both operators share

Neither platform ever hands biometric data to the app, and on neither platform does a biometric "success" callback protect data by itself. The documented pattern on both is the same: bind the secret (a keychain item or a Keystore key) to an access-control policy that requires user authentication, so that the secret is unavailable without it and is invalidated when the biometric set changes (`biometryCurrentSet` on Apple, `setInvalidatedByBiometricEnrollment(true)` on Android). Passcode fallback is the default on Apple's `userPresence` and must be chosen explicitly on Android via `DEVICE_CREDENTIAL`, with the API-level restrictions above.

## Decision-relevant facts for P3H and the P1 mobile clients

1. **The store review is the last gate on both platforms and its duration is not under the publisher's control**: Apple states 90% within 24 hours, Google states hours to seven days or longer and recommends a week's buffer. A mobile release calendar in P3H must carry a review window of at least seven days before any date-bound production step, and Apple's "one app-version submission per platform at a time" means a hotfix cannot be queued behind a pending release; it replaces it.
2. **Gradual rollout exists on both platforms but with different shapes and no rollback**: Apple's phased release is a fixed 1/2/5/10/20/50/100% seven-day curve, pausable for 30 days in total, reaching only automatic-update users, and any user can still download the new version manually; Google's staged rollout is a publisher-chosen percentage that never rises on its own, can be halted and resumed, and is unavailable for a first production release. Neither operator documents a way to revert installed devices to the previous version; the only documented remedies are pause/halt plus a new forward release. P3H's rollback definition for mobile must therefore be "halt and ship forward", with server-side feature flags as the actual reversal mechanism.
3. **Forced update is Android-only and consent-based; minimum-version enforcement is app logic on both platforms.** Android's in-app update API offers an immediate (blocking) and a flexible flow, with a 0-5 priority set only at release time through the Developer API and a staleness-days signal; Apple documents no equivalent, and both operators forbid self-updating outside the store. The P1 clients need a server-published minimum supported version checked at launch and a blocking screen that links to the store (using the Play immediate flow where available); the Android floor for that API is 5.0 (API 21), and the store's own floor for submissions is target API 36 from 31 August 2026 with API 35 for existing apps.
4. **Biometric unlock is a data-binding decision, not a UI decision.** Both operators give the app only a success/failure signal and never biometric data. The documented secure pattern is to bind the session or key material to hardware-backed storage with an authentication requirement: Apple keychain `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` plus `SecAccessControl` `biometryCurrentSet` (invalidated on re-enrollment; not backed up, not synced) or a Secure Enclave P-256 key; Android Keystore with `setUserAuthenticationParameters`, `setInvalidatedByBiometricEnrollment(true)` (default), `BIOMETRIC_STRONG` (Class 3), and optionally StrongBox and server-side key attestation at `TrustedEnvironment` or `StrongBox` level. `UX-001` must specify the fallback (passcode/device credential) and the re-enrollment behaviour explicitly, because Android restricts `DEVICE_CREDENTIAL` combinations below API 30 and Apple deprecated `evaluatedPolicyDomainState` in iOS 18.
5. **Regulated-financial submissions have named prerequisites on both stores that belong in the P3H evidence list, not in the launch week.** Apple 5.1.1(ix) requires the submitting account to be the legal entity providing the service, 2.1(a) requires a working demo account with the back end switched on (or a pre-approved demo mode), 2.3.1 requires specific release notes for review; Google requires the Financial features declaration with licence documentation tied to the developer account, the Data safety form on every non-internal track, reviewer access credentials including MFA handling, and, for personal accounts only, a 12-tester/14-day closed test before production access. Both stores' beta paths (TestFlight external, Play closed/open) are themselves reviewed; only Apple internal testers and Play internal testing are stated to bypass review, so the earliest "reviewed" build in the canonical pipeline is the first external beta, not the production submission.
