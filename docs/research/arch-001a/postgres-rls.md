## Question

ADR-004 proposes shared PostgreSQL with RLS as the default isolation tier. From PostgreSQL's official documentation: `BYPASSRLS`, table owner behaviour, `FORCE ROW LEVEL SECURITY`, policy evaluation for `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `RETURNING` and `ON CONFLICT`; how session variables used as tenant keys behave under connection pooling and `SET LOCAL`; interaction with views, functions marked `SECURITY DEFINER`, `COPY`, logical replication and `pg_dump`; and documented performance characteristics. State which cross-tenant leaks RLS does *not* prevent.

## Findings

### F1. What RLS enforces, and the default-deny rule

RLS is a per-row filter layered on top of the SQL privilege system, not a replacement for it: "tables can have row security policies that restrict, on a per-user basis, which rows can be returned by normal queries or inserted, updated, or deleted by data modification commands." It is off until enabled per table, and once enabled with no policies it denies everything: "When row security is enabled on a table (with `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`), all normal access to the table for selecting rows or modifying rows must be allowed by a row security policy. ... If no policy exists for the table, a default-deny policy is used, meaning that no rows are visible or can be modified." Whole-table operations are outside its scope: "Operations that apply to the whole table, such as `TRUNCATE` and `REFERENCES`, are not subject to row security." Disabling RLS leaves the policies in place but ignored: "Disabling row security does not remove any policies that are defined on the table; they are simply ignored. Then all rows in the table are visible and modifiable, subject to the standard SQL privileges system." Source: https://www.postgresql.org/docs/current/ddl-rowsecurity.html (checked 2026-09-05).

### F2. `BYPASSRLS` and superusers

Two classes of role are never filtered: "Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system when accessing a table." The attribute is set at role level and is off by default: "These clauses determine whether a role bypasses every row-level security (RLS) policy. `NOBYPASSRLS` is the default. Only superuser roles or roles with `BYPASSRLS` can specify `BYPASSRLS`." The `row_security` safety parameter (F9) does not touch these roles: "This variable has no effect on roles which bypass every row security policy, to wit, superusers and roles with the `BYPASSRLS` attribute." Sources: https://www.postgresql.org/docs/current/ddl-rowsecurity.html, https://www.postgresql.org/docs/current/sql-createrole.html, https://www.postgresql.org/docs/current/runtime-config-client.html (checked 2026-09-05).

### F3. Table owner behaviour and `FORCE ROW LEVEL SECURITY`

The owner of a table is exempt unless the table is explicitly forced: "Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`." The `ALTER TABLE` reference states the default: "These forms control the application of row security policies belonging to the table when the user is the table owner. If enabled, row-level security policies will be applied when the user is the table owner. If disabled (the default) then row-level security will not be applied when the user is the table owner." Ownership also controls the switch itself: "Enabling and disabling row security, as well as adding policies to a table, is always the privilege of the table owner only," and "You must be the owner of a table to create or change policies for it." Sources: https://www.postgresql.org/docs/current/ddl-rowsecurity.html, https://www.postgresql.org/docs/current/sql-altertable.html, https://www.postgresql.org/docs/current/sql-createpolicy.html (checked 2026-09-05).

### F4. Policy evaluation for `SELECT`, `INSERT`, `UPDATE`, `DELETE`

A policy has a `USING` expression that filters existing rows and a `WITH CHECK` expression that validates new rows: "Existing table rows are checked against the expression specified in `USING`, while new rows that would be created via `INSERT` or `UPDATE` are checked against the expression specified in `WITH CHECK`. When a `USING` expression returns true for a given row then that row is visible to the user, while if false or null is returned then the row is not visible. Typically, no error occurs when a row is not visible ... When a `WITH CHECK` expression returns true for a row then that row is inserted or updated, while if false or null is returned then an error occurs." The reference distinguishes "filter" (silent) from "check" (error): "'check' means that the policy expression is checked and an error is thrown if it returns false or null, whereas 'filter' means that the row is silently ignored if the policy expression returns false or null." `SELECT` policies also gate the read side of writes: "queries that require `SELECT` permissions, such as `UPDATE`, `DELETE`, and `MERGE`, will also only see those records that are allowed by the `SELECT` policy." For `UPDATE`, "The `USING` expression determines which records the `UPDATE` command will see to operate against, while the `WITH CHECK` expression defines which modified rows are allowed to be stored back into the relation," and "If only a `USING` clause is specified, then that clause will be used for both `USING` and `WITH CHECK` cases." For `DELETE`, "only rows that pass this policy will be seen by the `DELETE` command." `WITH CHECK` runs after `BEFORE` triggers: "For `INSERT`, `UPDATE`, and `MERGE` statements, `WITH CHECK` expressions are enforced after `BEFORE` triggers are fired, and before any actual data modifications are made. Thus a `BEFORE ROW` trigger may modify the data to be inserted, affecting the result of the security policy check. `WITH CHECK` expressions are enforced before any other constraints." Multiple policies combine as OR for permissive and AND for restrictive, and "If there are no `PERMISSIVE` policies, then access is denied." Policy expressions "cannot contain any aggregate or window functions." Source: https://www.postgresql.org/docs/current/sql-createpolicy.html (checked 2026-09-05).

### F5. `RETURNING`

`RETURNING` re-applies the `SELECT` policies to the written row and errors instead of filtering: "If a data-modifying query has a `RETURNING` clause, `SELECT` permissions are required on the relation, and any newly inserted or updated rows from the relation must satisfy the relation's `SELECT` policies in order to be available to the `RETURNING` clause. If a newly inserted or updated row does not satisfy the relation's `SELECT` policies, an error will be thrown (inserted or updated rows to be returned are never silently ignored)." Source: https://www.postgresql.org/docs/current/sql-createpolicy.html (checked 2026-09-05).

### F6. `INSERT ... ON CONFLICT`

`ON CONFLICT` switches several checks from filter to error. "If an `INSERT` has an `ON CONFLICT DO UPDATE` clause, or an `ON CONFLICT DO NOTHING` clause with an arbiter index or constraint specification, then `SELECT` permissions are required on the relation, and the rows proposed for insertion are checked using the relation's `SELECT` policies. If a row proposed for insertion does not satisfy the relation's `SELECT` policies, an error is thrown (the `INSERT` is never silently avoided). In addition, if the `UPDATE` path is taken, the row to be updated and the new updated row are checked against the relation's `SELECT` policies, and an error is thrown if they are not satisfied." `INSERT` policies are checked regardless of outcome: "an `INSERT` with an `ON CONFLICT DO NOTHING`/`UPDATE` clause will check the `INSERT` policies' `WITH CHECK` expressions for all rows proposed for insertion, regardless of whether or not they end up being inserted." On the update path the existing row is checked, not filtered: "unlike a standalone `UPDATE` command, if the existing row does not pass the `USING` expressions, an error will be thrown (the `UPDATE` path will never be silently avoided)." Source: https://www.postgresql.org/docs/current/sql-createpolicy.html (checked 2026-09-05).

### F7. Session variables as tenant keys: `SET`, `SET LOCAL`, `set_config`, reset

The documentation supports arbitrary two-part parameter names as placeholders: "Because custom options may need to be set in processes that have not loaded the relevant extension module, PostgreSQL will accept a setting for any two-part parameter name. Such variables are treated as placeholders and have no function until the module that defines them is loaded." They are read with `current_setting(setting_name, missing_ok)` and written with `set_config(setting_name, new_value, is_local)`: "If `is_local` is true, the new value will only apply during the current transaction. If you want the new value to apply for the rest of the current session, use false instead." Scope rules: "`SET` only affects the value used by the current session." "Once the surrounding transaction is committed, the effects will persist until the end of the session, unless overridden by another `SET`." "The effects of `SET LOCAL` last only till the end of the current transaction, whether committed or not." "Issuing this outside of a transaction block emits a warning and otherwise has no effect." A rolled-back transaction undoes a session-level `SET` issued inside it. `RESET` and `DISCARD ALL` restore defaults; `DISCARD ALL` "resets the session to its initial state" and "cannot be executed inside a transaction block." Sources: https://www.postgresql.org/docs/current/runtime-config-custom.html, https://www.postgresql.org/docs/current/functions-admin.html, https://www.postgresql.org/docs/current/sql-set.html, https://www.postgresql.org/docs/current/sql-reset.html, https://www.postgresql.org/docs/current/sql-discard.html (checked 2026-09-05).

### F8. Session variables under connection pooling

The PostgreSQL documentation does not describe the behaviour of external connection poolers (PgBouncer, application-side pools) with respect to session state; the only mentions of pooling in the client-connection chapter concern `idle_session_timeout` ("Be wary of enforcing this timeout on connections made through connection-pooling software or other middleware") and `session_preload_libraries`. What the documentation does establish is the primitive: a session-level `SET` survives until the session ends or is overridden (F7), so a reused backend retains it unless something issues `RESET`, `SET`, or `DISCARD ALL`. Whether any given pooler does so, and in which pooling mode, is UNVERIFIED from primary sources (see Unverified items). Source: https://www.postgresql.org/docs/current/runtime-config-client.html (checked 2026-09-05).

### F9. `row_security = off` as a fail-loud guard

The `row_security` parameter turns silent filtering into an error for non-bypass roles: "This variable controls whether to raise an error in lieu of applying a row security policy. When set to on, policies apply normally. When set to off, queries fail which would otherwise apply at least one policy. The default is on. Change to off where limited row visibility could cause incorrect results; for example, `pg_dump` makes that change by default." The tutorial chapter is explicit that it is not a bypass: "This does not in itself bypass row security; what it does is throw an error if any query's results would get filtered by a policy." Sources: https://www.postgresql.org/docs/current/runtime-config-client.html, https://www.postgresql.org/docs/current/ddl-rowsecurity.html (checked 2026-09-05).

### F10. Views

By default a view applies the view owner's policies, not the caller's: "If any of the underlying base relations has row-level security enabled, then by default, the row-level security policies of the view owner are applied, and access to any additional relations referred to by those policies is determined by the permissions of the view owner. However, if the view has `security_invoker` set to true, then the policies and permissions of the invoking user are used instead, as if the base relations had been referenced directly from the query using the view." `CREATE POLICY` repeats this: "permission checks and policies for the tables which are referenced by a view will use the view owner's rights and any policies which apply to the view owner, except if the view is defined using the `security_invoker` option." A plain view is not a row filter: "they cannot be used to reliably conceal the data in unseen rows unless the `security_barrier` flag has been set," and `security_barrier` costs: "Views created with the `security_barrier` may perform far worse than views created without this option." Sources: https://www.postgresql.org/docs/current/sql-createview.html, https://www.postgresql.org/docs/current/sql-createpolicy.html, https://www.postgresql.org/docs/current/rules-privileges.html (checked 2026-09-05).

### F11. `SECURITY DEFINER` functions

A `SECURITY DEFINER` function "is to be executed with the privileges of the user that owns it," and the RLS chapter names this as a deliberate escape hatch: "Policy expressions are run as part of the query and with the privileges of the user running the query, although security-definer functions can be used to access data not available to the calling user." The reference requires `search_path` hardening: "For security, `search_path` should be set to exclude any schemas writable by untrusted users ... A secure arrangement can be obtained by forcing the temporary schema to be searched last. To do this, write `pg_temp` as the last entry in `search_path`." New functions are executable by everyone by default: "by default, execute privilege is granted to `PUBLIC` for newly created functions." Role switching is not available inside them: "`SET ROLE` cannot be used within a `SECURITY DEFINER` function." Sources: https://www.postgresql.org/docs/current/sql-createfunction.html, https://www.postgresql.org/docs/current/ddl-rowsecurity.html, https://www.postgresql.org/docs/current/sql-set-role.html (checked 2026-09-05).

### F12. `COPY`

"If row-level security is enabled for the table, the relevant `SELECT` policies will apply to `COPY table TO` statements. Currently, `COPY FROM` is not supported for tables with row-level security. Use equivalent `INSERT` statements instead." The policy table lists `SELECT / COPY ... TO` as "Filter existing row." Server-side file `COPY` is separately privileged: "`COPY` naming a file or command is only allowed to database superusers or users who are granted one of the roles `pg_read_server_files`, `pg_write_server_files`, or `pg_execute_server_program`." Sources: https://www.postgresql.org/docs/current/sql-copy.html, https://www.postgresql.org/docs/current/sql-createpolicy.html (checked 2026-09-05).

### F13. Logical replication

On the publisher, RLS is applied only if the replication role is not exempt, and the documentation recommends failing loud rather than filtering: "If the role lacks `SUPERUSER` and `BYPASSRLS`, publisher row security policies can execute. If the role does not trust all table owners, include `options=-crow_security=off` in the connection string; if a table owner then adds a row security policy, that setting will cause replication to halt rather than execute the policy." Publications carry no access control of their own: "There are currently no privileges on publications. Any subscription (that is able to connect) can access any publication. Thus, if you intend to hide some information from particular subscribers, such as by using row filters or column lists, or by not adding the whole table to the publication, be aware that other publications in the same database could expose the same information." On the subscriber, writes run as the table owner: "when performing an insert, update, delete, or truncate operation on a particular table, it will switch roles to the table owner and perform the operation with the table owner's privileges." Publisher privileges "are only checked once at the start of a replication connection and are not re-checked as each change record is read." Source: https://www.postgresql.org/docs/current/logical-replication-security.html (checked 2026-09-05).

### F14. `pg_dump`

`pg_dump` refuses to produce a silently filtered dump: "By default, `pg_dump` will set `row_security` to off, to ensure that all data is dumped from the table. If the user does not have sufficient privileges to bypass row security, then an error is thrown. This parameter [`--enable-row-security`] instructs `pg_dump` to set `row_security` to on instead, allowing the user to dump the parts of the contents of the table that they have access to." A filtered dump must be in `INSERT` form: "if you use this option currently, you probably also want the dump be in `INSERT` format, as the `COPY FROM` during restore does not support row security." `CREATE ROLE` adds: "superusers and the owner of the table being dumped always bypass RLS." `--no-policies` omits the policies themselves from the dump. Sources: https://www.postgresql.org/docs/current/app-pgdump.html, https://www.postgresql.org/docs/current/sql-createrole.html (checked 2026-09-05).

### F15. Documented performance characteristics

Policies are inlined into the query: "Since policy expressions are added to the user's query directly, they will be run with the rights of the user running the overall query." The RLS chapter identifies the fast case: "the policy expressions consider only the current values in the row to be accessed or updated. This is the simplest and best-performing case; when possible, it's best to design row security applications to work this way. If it is necessary to consult other rows or other tables to make a policy decision, that can be accomplished using sub-SELECTs, or functions that contain SELECTs, in the policy expressions. Be aware however that such accesses can create race conditions that could allow information leakage if care is not taken." Row-share-lock workarounds have a cost: "heavy concurrent use of row share locks on the referenced table could pose a performance problem, especially if updates of it are frequent." Planner ordering is constrained by leakproofness: "The system will enforce conditions from security policies and security barrier views before any user-supplied conditions from the query itself that contain non-leakproof functions," and "an index scan cannot be selected for queries on security barrier views (or tables with row-level security policies) if an operator used in the `WHERE` clause is associated with the operator family of the index, but its underlying function is not marked `LEAKPROOF`. The psql program's `\dAo+` meta-command is useful to list operator families and determine which of their operators are marked as leakproof." No throughput or latency numbers are published in the documentation. Sources: https://www.postgresql.org/docs/current/sql-createpolicy.html, https://www.postgresql.org/docs/current/ddl-rowsecurity.html, https://www.postgresql.org/docs/current/sql-createfunction.html, https://www.postgresql.org/docs/current/rules-privileges.html (checked 2026-09-05).

## Leaks RLS does not prevent

Each item names the class of cross-tenant exposure and the documentation sentence that establishes it. "Leak" here means a path by which a query, role, or process can read, write, or infer rows belonging to another tenant despite policies being enabled.

1. **Superuser and `BYPASSRLS` roles read and write every tenant's rows.** "Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system when accessing a table." (ddl-rowsecurity.html)
2. **The table owner bypasses policies unless every RLS table is `FORCE`d.** "Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`." (ddl-rowsecurity.html) The owner can also switch RLS off at will: "Enabling and disabling row security, as well as adding policies to a table, is always the privilege of the table owner only." (ddl-rowsecurity.html)
3. **Whole-table commands are not filtered.** "Operations that apply to the whole table, such as `TRUNCATE` and `REFERENCES`, are not subject to row security." (ddl-rowsecurity.html) A tenant role with `TRUNCATE` privilege empties every tenant's rows.
4. **Existence of another tenant's values leaks through unique, primary-key and foreign-key checks.** "Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security to ensure that data integrity is maintained. Care must be taken when developing schemas and row level policies to avoid 'covert channel' leaks of information through such referential integrity checks." (ddl-rowsecurity.html) "If the insert fails then the user can infer that the value already exists. ... Existence can be determined by the user inserting values into the referencing table, where success would indicate that the value exists in the referenced table." (sql-createpolicy.html)
5. **Error-versus-filter differences on `RETURNING` and `ON CONFLICT` are observable.** These paths are documented to raise an error rather than silently drop a row: "an error will be thrown (inserted or updated rows to be returned are never silently ignored)" and "if the existing row does not pass the `USING` expressions, an error will be thrown (the `UPDATE` path will never be silently avoided)." (sql-createpolicy.html) Combined with item 4, an `ON CONFLICT DO UPDATE` against a conflicting row owned by another tenant is a documented existence signal. The documentation does not itself label this a leak; the classification is this ledger's.
6. **Plan shape, run time and optimizer statistics are covert channels.** Written for `security_barrier` views, which the documentation ties to the same mechanism as RLS tables: "they can see the query plan using `EXPLAIN`, or measure the run time of queries against the view. A malicious attacker might be able to infer something about the amount of unseen data, or even gain some information about the data distribution or most common values ... If these types of 'covert channel' attacks are of concern, it is probably unwise to grant any access to the data at all." (rules-privileges.html) The linkage sentence: "This affects how the system executes queries against views created with the `security_barrier` option or tables with row level security enabled." (sql-createfunction.html)
7. **`LEAKPROOF`-marked functions and argument-free functions run before the policy filter.** "functions and operators marked by the system (or the system administrator) as `LEAKPROOF` may be evaluated before policy expressions, as they are assumed to be trustworthy." (sql-createpolicy.html) "functions which do not take arguments or which are not passed any arguments from the security barrier view or table do not have to be marked as leakproof to be executed before security conditions." (sql-createfunction.html) A mis-marked `LEAKPROOF` function (superuser-only to set) sees unfiltered rows.
8. **Views owned by a privileged role apply the owner's policies, not the caller's.** "by default, the row-level security policies of the view owner are applied ... However, if the view has `security_invoker` set to true, then the policies and permissions of the invoking user are used instead." (sql-createview.html) A view owned by a `BYPASSRLS` role, the table owner, or a superuser exposes all tenants unless `security_invoker = true`.
9. **`SECURITY DEFINER` functions run with the owner's privileges and can reach rows the caller cannot.** "security-definer functions can be used to access data not available to the calling user." (ddl-rowsecurity.html) They are also public-executable by default: "by default, execute privilege is granted to `PUBLIC` for newly created functions." (sql-createfunction.html)
10. **Policies that consult other tables can be raced under `READ COMMITTED`.** "If it is necessary to consult other rows or other tables to make a policy decision ... such accesses can create race conditions that could allow information leakage if care is not taken." The worked example shows a user seeing a row after her privilege was revoked, because "the `users` row is read with the snapshot taken at the start of the query." (ddl-rowsecurity.html)
11. **A stale session-level tenant key on a reused connection is honoured as-is.** "Once the surrounding transaction is committed, the effects will persist until the end of the session, unless overridden by another `SET`." (sql-set.html) RLS evaluates whatever `current_setting()` returns; the documentation does not describe any pooler resetting it (F8).
12. **`BEFORE ROW` triggers can rewrite the row before the policy sees it.** "a `BEFORE ROW` trigger may modify the data to be inserted, affecting the result of the security policy check." (sql-createpolicy.html) A trigger that overwrites `tenant_id` moves a row across tenants inside the policy's blind spot; triggers are owner-controlled objects, so this is an owner-side leak, not a caller-side one.
13. **Backups, restores and replication run outside RLS by design.** `pg_dump`: "superusers and the owner of the table being dumped always bypass RLS." (sql-createrole.html) Logical replication: "There are currently no privileges on publications. Any subscription (that is able to connect) can access any publication." (logical-replication-security.html) A dump file or a replication stream produced by a bypass role contains every tenant's rows; RLS does not follow the data out of the database.
14. **Columns are not protected by RLS.** RLS restricts "which rows can be returned" (ddl-rowsecurity.html); the chapter's own example uses column-level `GRANT` for column hiding ("Users only get select access on public columns"). A cross-tenant column exposure inside a visible row is a `GRANT` problem, not an RLS one.
15. **`COPY FROM` cannot be used on an RLS table, so bulk loads are pushed to a non-RLS path.** "Currently, `COPY FROM` is not supported for tables with row-level security. Use equivalent `INSERT` statements instead." (sql-copy.html) Any import job that works around this with a bypass role is an unfiltered write path.

## Decision-relevant facts for ADR-004

- **The application role must be `NOSUPERUSER`, `NOBYPASSRLS`, and must not own the tenant tables (or every tenant table must be `FORCE ROW LEVEL SECURITY`).** All three exemptions are documented (F2, F3), and each one silently disables every policy for that role. The ownership split (a migration/owner role distinct from the runtime role) is the single most decision-relevant fact because owner bypass is the default and the owner can `DISABLE ROW LEVEL SECURITY` unilaterally.
- **RLS gives default deny only after `ENABLE ROW LEVEL SECURITY` on each table; a table created without it is fully open to any role holding `GRANT`s.** (F1) A schema-level control that every tenant-bearing table has RLS enabled, forced, and at least one permissive policy ("If there are no `PERMISSIVE` policies, then access is denied", F4) is a test, not an assumption. `row_security = off` on audit or backup connections turns silent filtering into an error (F9) and is the documented way to prove no filtering happened.
- **The tenant key must be transaction-scoped (`SET LOCAL` or `set_config(..., true)`), and the pooling mode must be proven, not assumed.** The documentation establishes that a session-level `SET` persists across transactions until the session ends (F7) and says nothing about external poolers (F8). ADR-004 can rely on `SET LOCAL` semantics; it cannot rely on any pooler resetting state without a test in the chosen pooler and mode.
- **Write paths behave differently from read paths: `RETURNING`, `ON CONFLICT`, and `MERGE` raise errors rather than filter, `COPY FROM` is unsupported, and `WITH CHECK` runs after `BEFORE` triggers.** (F4, F5, F6, F12) The cross-tenant proof plan must cover insert-with-conflict, update-with-returning, upsert against another tenant's key, and bulk import, because those are exactly the paths where the documented behaviour is an error or an unsupported operation, not a quiet denial.
- **RLS does not close existence inference, side channels, owner-side objects, or data leaving the database.** Unique/FK covert channels (leak 4), `EXPLAIN`/timing (leak 6), views and `SECURITY DEFINER` functions (leaks 8, 9), triggers (leak 12), and dumps/replication (leak 13) are all documented gaps. ADR-004 should therefore state that RLS is one enforcement layer among several (consistent with `AUTHORIZATION_BASELINE.md`, "No single layer substitutes for another"), require surrogate keys (the documentation's own mitigation for leak 4), require `security_invoker = true` on views over tenant tables, require an inventory of `SECURITY DEFINER` functions and `LEAKPROOF` markings, and place backup and replication roles under a separate control.

## Unverified items

- **Pooler behaviour.** Whether PgBouncer (in session, transaction, or statement mode), or any application-side pool, issues `DISCARD ALL`, `RESET ALL`, or otherwise clears a session-level `SET` before handing a backend to another client is not stated anywhere in the PostgreSQL documentation. UNVERIFIED from primary sources; must be established from the pooler's own documentation and a live test.
- **Whether a plain `SET` inside an aborted transaction under a pooler's transaction mode can ever be observed by the next client.** The rollback semantics are documented (F7) but the pooler interaction is not. UNVERIFIED.
- **Quantitative performance cost of RLS.** The documentation gives qualitative statements only (F15). No throughput, latency, or plan-regression numbers are published. UNVERIFIED; must be measured on the target schema.
- **Whether the `EXPLAIN`/timing covert-channel warning (leak 6) is intended to apply verbatim to RLS tables.** The warning is written in the `security_barrier` view section; the documentation states the two share the leakproof mechanism but does not restate the warning for RLS. Treated here as applicable; flagged as an interpretation.
- **The claim in leak 5 that error-versus-filter behaviour is a tenant-observable signal.** The error behaviour is documented; the documentation does not characterise it as a leak. This ledger's classification.
- **`MERGE`-specific behaviour beyond what is quoted.** The `MERGE` rows in the policy table were read but `MERGE` was not in the ticket's scope and is not analysed here.
