## Scope and non-scope

**In scope.** What every protected request has verified about its token before any business code runs, where each check runs, and the negative control that proves each:

1. **The token the API accepts**: Logto's organization-level API resource token, the one of Logto's three token models that carries both the API audience and the organization, for users and for machine identities alike.
2. **The validation chain** in the identity-access module: signature, issuer, audience, time, the organization claim, and the route's required scope, in that order, each with its failure recorded.
3. **What a gateway would prove and what the application re-checks**, so that the chain does not depend on a gateway being present or honest.
4. **The negative control for each check**, seen failing before the check exists, as the manual's row asks: token-validation evidence, positive and negative.
5. **The spike itself**: a lab Logto instance with one API resource, one organization per synthetic tenant, one user and one machine identity, against which the chain and its controls run.

**Non-scope**, each with its owner:

- The organization-to-tenant mapping, its lifecycle and the mismatch tests between a token's organization and the tenant a request is about: P0.4 and ADR-003. This design stops at "a valid token names organization X" and proposes what it hands over; P0.4 defines the resolver that says which tenant X is and whether the request may be about it.
- Active membership, suspension and offboarding: BizTrust Tenancy and P0.4; the research is explicit that membership is enforced at token issuance and that the token says nothing about a member removed since (gap 1, `UNVERIFIED`).
- Business authorization, resource scope, approval authority and the authority agreement that lets a permission represent cover: `AUTHORIZATION_BASELINE.md`, ADR-013 and P1.
- The row-level security outcome: P0.6 and P0.7; this design hands a resolved organization to P0.4 and nothing to the database.
- The audit record's shape: P0.10; this design names the fields a denial gives the record and leaves the record's shape, storage and controls to P0.10.
- Logto's deployment, Cloud against OSS, and its exit strategy: ADR-002; the design assumes OSS in the lab (Open questions, question 5).
- The choice of a gateway at all, and its rate limiting, TLS termination and routing: no ADR row exists (question 2); this design says what a gateway of the researched shape would add and never relies on it.
- Multi-factor authentication, single sign-on and session lifecycle: Logto's, under ADR-002.

## Authorization-sequence step

P0.3 is the fourth step of the tenant authorization sequence in [`FLOWS.md`](../FLOWS.md) section 3, "Verify signature, issuer, audience and expiry", and the first half of the fifth, the resolution of tenant and scope that P0.4 completes:

| Sequence step | What P0.3 does there |
|---|---|
| Organization token from Logto | Says which token model the API accepts and refuses the other two |
| APISIX edge, validated edge request | Says what a gateway of the researched shape can prove and that the application treats nothing it forwards as authenticated |
| API verifies signature, issuer, audience and expiry | The chain's first four checks, each with its control |
| Business authorization resolves tenant, membership, scope and authority | The chain's last two checks, the organization claim and the route's scope; the resolved organization is handed to P0.4 |
| Deny with problem details, and the audit record | Every failed check answers with problem details that name the check and never the token, and writes the denial with a reason code (P0.10) |

The contract's section 8 lists eight things every protected request must verify; this design covers the first four (signature, issuer and expiry; audience; `organization_id`; required scopes) and names where the other four live.

## Interfaces and data shapes

### The token the API accepts

Logto documents three token models; the research names the third as "the one that lets a resource server enforce tenant context" (F4): a JWT for a registered API resource that "will contain both the API audience (`aud` claim) and the organization context (`organization_id` claim), with scopes filtered to those granted by the user's organization roles" (F6). The API accepts that model only:

| Token | `aud` | `organization_id` | The API's answer |
|---|---|---|---|
| Organization-level API resource token (model 3) | The registered API resource identifier | Present | Accepted into the chain |
| Global API resource token (model 1) | The API resource identifier | Absent | Refused on every route in P0, which has no tenantless route; a later design that declares one says how it is accepted there |
| Organization token (model 2) | `urn:logto:organization:{id}` | Absent as a claim; the organization is the audience | Refused: the audience is not the API |

A user obtains the token with the refresh-token grant, `resource` and `organization_id` (F6); a machine identity obtains it with `client_credentials`, `organization_id` and `resource`, and Logto refuses an application not associated with the organization with a 403 (F8). Both arrive at the API the same way and pass the same chain. The research records that "every organization-context token is a JWT, never opaque" (decision-relevant facts), so the chain never introspects; a token that is not a JWT fails the first check.

### The validation chain

Owned by the identity-access module, the registry's name for the capability map's Identity & Access (the P0.2 design); the manual's row places the epic under `modules/identity/`, an earlier name for the same module; invoked by the API service's request pipeline before any module's contract is called; no module may call a contract on behalf of a request that has not passed it. The checks run in this order and stop at the first failure:

| # | Check | What is compared | Source of the expected value | Failure reason code |
|---|---|---|---|---|
| 1 | Bearer | The `Authorization` header carries one bearer token and nothing else authenticates | The chain itself | `token_missing` |
| 2 | Signature | The JWT's signature against Logto's JSON Web Key Set, selected by the token's `kid`, "a hint indicating which key was used to secure the JWS" [J2]; the token's `alg`, which "identifies the cryptographic algorithm used to secure the JWS" [J2], must be one of a configured set of asymmetric algorithms, because "Libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms" [J3] and the attack that set prevents is the one where a value "can be changed into 'HS256'" and "the RSA public key [is used] as the HMAC shared secret" [J3] | The key set fetched from the configured key-set location, which the P0.12 design lists as versioned configuration and which the issuer's discovery document publishes as `jwks_uri`, "the OP's JWK Set document ... the signing key(s) the RP uses to validate signatures from the OP" [O1], cached; the algorithm set is configuration | `token_signature` |
| 3 | Issuer | `iss` equals the configured issuer, exactly | Configuration, versioned (the P0.12 design) | `token_issuer` |
| 4 | Audience | `aud` equals the registered API resource identifier, exactly; an organization audience or an absent audience fails | Configuration | `token_audience` |
| 5 | Time | `exp`, "the expiration time on or after which the JWT MUST NOT be accepted", is in the future and `nbf`, "the time before which the JWT MUST NOT be accepted", is in the past [J1], with the bounded leeway the specification allows, "usually no more than a few minutes, to account for clock skew" [J1] | The API's clock; the tolerance is configuration (Open questions, question 6) | `token_expired` or `token_not_yet_valid` |
| 6 | Organization | `organization_id` is present and is one identifier | The token | `organization_missing` |
| 7 | Scope | The route's required permission, declared in the API contract, is among the space-separated `scope` values | The route's declaration under ADR-005 | `scope_missing` |

After check 7 the chain hands `organization_id`, the subject (`sub`, a user or an application identifier) and the scope list to P0.4's resolver, which answers whether the organization maps to an active tenant, whether the subject's membership is active, and whether the request's tenant matches; the chain never reads a tenant identifier from the URL, a header or the body, which the contract calls "requested context only".

Each failure answers with problem details naming the reason code and never echoing the token, and writes an audit record with the reason code, the route, the subject if check 2 passed, and the request and trace identifiers (P0.10's fields), so that the P0 manual's rule, every outcome produces tenant-safe audit evidence, holds for denials as well as successes.

### What a gateway would prove, and what the application re-checks

The APISIX research settles the division. A gateway of the researched shape, in bearer-only mode, can prove the signature against the issuer's key set, the issuer against a configured list, the audience if and only if its audience check is switched on, and the listed required scopes (research F1); it has no documented way to require an arbitrary claim, so it cannot be relied on to require `organization_id` (F2, and the research's U2: absence in the documentation, not confirmed against the plugin's source); and what it forwards about identity is the decoded-claims header, which "carries no cryptographic signature" (F2), and the userinfo header, a plain header (the research's decision-relevant fact 3). The research's third decision-relevant fact is therefore this design's rule: the application verifies the forwarded access token itself and never accepts an organization header as authenticated context.

| Check | A gateway of the researched shape | The application |
|---|---|---|
| Signature, issuer | Can prove, as first-line rejection | Re-checks; the gateway's proof is not forwarded in any signed form |
| Audience | Can prove only if its audience validation is configured on; off by default (F1) | Checks regardless |
| Expiry | Not stated for the researched plugin's JWKS path (research U1) | Checks |
| `organization_id` | No documented way to require it (F2, U2) | Checks |
| Scope | Can prove the listed required scopes (F1) | Checks the route's own declaration |
| Membership, tenant match, authority, RLS | Cannot; no database session and no business state (research's table) | P0.4, business authorization, P0.7 |

The research's exit path is the design's rule: if the gateway is removed, "the application loses only what the gateway added at the edge" and "nothing it was required to do anyway". A deployment with a gateway therefore runs the same chain as one without, and the spike measures both.

### The lab

The spike runs against a Logto instance the P0.12 design's local and shared development environments can reach, holding synthetic data only. The lab's owner is the P0.3 Work Package's engineering role; its objects are created by hand for the spike and never by P0.5's provisioning command, and it is torn down with the package's record:

| Object | Synthetic value |
|---|---|
| API resource | `https://api.biztrust.invalid` as the registered identifier and audience |
| Organizations | One for Tenant A, UniTrust, `org_a_synthetic`; one for Tenant B, the travel scheme, `org_b_synthetic` |
| Users | One member of Tenant A only, `user_a_synthetic`; one member of both, `user_ab_synthetic` |
| Machine identity | The API's own application, associated with Tenant A's organization only, with one M2M organization role |

Nothing in the lab is a client, policy, claim or premium; the routes read and write the tenancy schema's synthetic rows of the P0.6 design.

## Negative controls

Each control is seen failing before the check exists and passing after; every control feeds the `BT-G1` matrix's token rows and is run by a verifier who is not the implementer.

| # | Threat or defect | Condition | Expected denial or failure | Seen failing at |
|---|---|---|---|---|
| 1 | No token | A request to a tenant route with no `Authorization` header, and one with only the gateway's decoded-claims header forged by hand | Refused, `token_missing`; no business query; the denial audited | Before check 1: the header-only request reaches business code |
| 2 | Tampered signature | A valid token with one payload byte changed; a token signed by a key the issuer's key set does not hold; a token whose header names a symmetric algorithm with the issuer's public key as its secret | Refused, `token_signature`, in all three cases | Before check 2 and its algorithm allow-list: the third case is accepted by a verifier that trusts the header's algorithm |
| 3 | Wrong issuer | A token from a second lab issuer with a valid signature under that issuer's keys | Refused, `token_issuer` | Before check 3: accepted, since the signature is valid |
| 4 | Wrong audience | A plain organization token (model 2) for Tenant A; a token for a different registered API resource | Refused, `token_audience`, both | Before check 4: the organization token is accepted |
| 5 | Expired and not yet valid | A token past `exp` by more than the tolerance; a token with `nbf` in the future | Refused, `token_expired` and `token_not_yet_valid`; a token inside the tolerance is accepted and the tolerance recorded | Before check 5: both accepted |
| 6 | No organization | A global API resource token (model 1) for the same user on a tenant route | Refused, `organization_missing` | Before check 6: accepted, the request proceeds with no tenant |
| 7 | Absent scope | `user_a_synthetic` with the `tenant:read` role calls the `tenant:write` route | Refused, `scope_missing`; the audit record names the route and the subject | Before check 7: the write proceeds |
| 8 | Not a member | `user_a_synthetic` requests a token with Tenant B's `organization_id` | Logto refuses issuance with 403, as the research reads in source (F7); no token exists to present; the spike records the refusal | This control is a measurement of Logto, not a check of the chain, and is recorded as a baseline rather than seen failing; its BizTrust-side protection, the membership check for a token issued before the member was removed, is P0.4's control |
| 9 | Machine identity outside its organization | The API's application requests a token with Tenant B's `organization_id` | Logto refuses with 403 "app has not associated with the organization" (F8); recorded | As control 8: a measurement, recorded, not seen failing |
| 10 | The gateway's proof trusted | With the gateway in front, a request that bypasses the gateway and reaches the application listener with the gateway's forwarded headers but a tampered token | Refused by check 2; if the listener requires the gateway's client certificate, refused at the connection | Before the application's own chain: accepted on the strength of the headers |

Controls 1 to 7 and 10 are the `BT-G1` matrix's missing-token, expired-or-malformed-token, wrong-audience, missing-organization-context and absent-scope rows; controls 8 and 9 are the research's issuance-time facts, measured so that the record is the spike's and not the research's.

## Evidence contract

A spike run or a control run records, per [`AGENTS.md`](../../../AGENTS.md) section 9; a record missing a field is not evidence:

| Field | Content for P0.3 |
|---|---|
| Repository and commit SHA | The platform repository and the commit whose chain and configuration ran |
| Command or workflow identity | The workflow file and run identifier for the security test job, or the spike procedure's step numbers |
| Execution time and environment | Start and end, environment name, Node.js version, the Logto version and its deployment shape (OSS in the lab), the gateway's version and mode if present |
| Exit status | Per control |
| Artifact or output reference | For each control the request, the token's decoded header and claims with the signature and any secret redacted, the response's problem details, and the audit record written; for controls 8 and 9 Logto's response |
| Verifier role | The named role that ran or observed each control, not the implementer; the security reviewer role for the `BT-G1` rows |
| Declared coverage | Which checks, token models, routes and, if present, gateway mode the run covered |
| Declared non-coverage | Membership changes after issuance (P0.4), the mismatch between token organization and request tenant (P0.4), and any gateway mode not measured |

## Open questions and dependencies

1. **ADR-002 and ADR-003 decide the issuer and the mapping.** Waits on: [#104](https://github.com/bstBizEra/biztrust_guide/issues/104) on the contract map, behind the waiver (#92). `ASSUMED` meanwhile: the contract's proposed decision, Logto with organization context as the tenant security context, and the organization-level API resource token as the only accepted model.
2. **The gateway has no ADR.** The register's rows do not include one, and the contract's section 4.2 lists the gateway among the "replaceable infrastructure behind adapters". Waits on: a decision ticket on the [ARCH-001A map](https://github.com/bstBizEra/biztrust_guide/issues/91), which waits on the waiver. `ASSUMED` meanwhile: the chain runs identically with or without a gateway; the spike measures both shapes; a gateway of the researched shape, if chosen, runs bearer-only with audience validation on and the listed scopes, and the application listener accepts connections from it alone.
3. **The mismatch convention.** The research's gap 2: how the request conveys the tenant it is about (path, header, subdomain) and the mismatch tests ADR-003 requires. Waits on: P0.4's design. `ASSUMED` meanwhile: the chain hands `organization_id` to P0.4 and reads no request identifier.
4. **The token library.** No research names one. Waits on: the P0.3 Work Package's own review, under ADR-001, whose ticket carries the stack decision. `ASSUMED` meanwhile: a library that verifies against a fetched key set, refuses algorithms outside an allow-list, and exposes `exp` and `nbf` checks with a tolerance; the controls, not the library, are the proof.
5. **Cloud or OSS, and the version.** Waits on: ADR-002 ([#104](https://github.com/bstBizEra/biztrust_guide/issues/104)). `ASSUMED` meanwhile: OSS in the lab, since the research records that OSS carries organizations in its free tier and the operator owns its database; the version is pinned in the spike's record.
6. **The clock tolerance.** No record states one. Waits on: the security reviewer role's acceptance in the P0.3 package. `ASSUMED` meanwhile: a tolerance of at most sixty seconds, recorded in configuration and in control 5's evidence.
7. **Key rotation and cache behaviour.** How the chain behaves when the issuer rotates a key: `UNVERIFIED`, not in either research. Waits on: a spike step in P0.3-A that rotates the lab issuer's key and measures. `ASSUMED` meanwhile: the key set is re-fetched on an unknown key identifier with a bounded rate, and a token under a retired key fails check 2.
8. **Tokens after membership removal.** The research's gap 1, `UNVERIFIED`: whether a token already issued survives the member's removal or the organization's deletion. Waits on: P0.4's control. `ASSUMED` meanwhile: it does, until `exp`, which is why active membership is P0.4's check and not this chain's.
9. **Gateway-to-application transport.** The research reads mTLS upstream as needing APISIX-Runtime, with upstream server-certificate verification documented only for Kafka (F7). Waits on: question 2. `ASSUMED` meanwhile: if a gateway is present, the application listener requires the gateway's client certificate; control 10 measures the bypass.

No item is `UNKNOWN_BLOCKING`: the design proceeds on its assumptions and each is reversible by the decision it names.
