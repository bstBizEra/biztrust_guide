## Scope and non-scope

**In scope.** The one code path that turns a provisioning request into a usable tenant, and the proof that it is one path:

1. **The request**: what the command takes, who may submit it, and the identifier it is idempotent on.
2. **The steps**, in order: the tenant row, the Logto organization, the API's machine-to-machine association, the first administrator's membership, the synthetic seed, activation; each step's check before its act, so that a rerun converges instead of duplicating.
3. **The provisioning record**: a platform-level account of every run, one row per run with its last step, which is what "same result" is measured against.
4. **Partial failure**: what a run stopped at any step leaves behind, what a rerun does with it, and what an operator does to abandon it.
5. **Two tenants, twice**: the acceptance the manual's row states, as a test with a recorded digest, and the check that the two runs differ only in their inputs (INV-011).
6. **What a tenant is under the default tier**: a row, a mapping, a membership and seed rows; no schema object and no database role per tenant (ADR-004's proposal, the P0.6 design), which the ticket's "schema objects, roles" resolves to.

**Non-scope**, each with its owner:

- The tables the command writes, their template and ownership tests: the P0.6 design.
- The resolver, what a token gets during and after provisioning, and the status vocabulary's meaning at request time: the P0.4 design; this design fixes when a tenant becomes `active` and nothing about how the resolver reads it.
- The organization's policies and the tenant key: the P0.7 design; the seed rows are written through them, which is a proof this design borrows, not a mechanism it owns.
- Where the Management API credential is held and how it is rotated: the P0.12 design; this design fixes only when the command reads it.
- Business units, branches, tenant configuration, domain and branding after provisioning: P0.13, as the manual's tenancy note assigns them. Invitations and just-in-time joining, which the note does not name: this design leaves them with P0.13 as the nearest owner, writes the first administrator's membership, and says nothing about how later members join.
- The authority profile's content and acceptance: ADR-013 and slice S01 ([#93](https://github.com/bstBizEra/biztrust_guide/issues/93)); the command records a reference to an accepted profile and never a profile's text.
- Re-creation of an organization for an existing tenant and closure: the P0.4 design's lifecycle names both; this design gives the command the record they write into and leaves their runs to a later version (question 6).
- A dedicated-schema or dedicated-database tier: ADR-004's exit path; a tenant on that tier would add a step this design does not write (question 8).

## Authorization-sequence step

P0.5 occupies no step of the tenant authorization sequence in [`FLOWS.md`](../FLOWS.md) section 3: it runs before the sequence's first step can happen for the tenant, and the sequence's rules constrain it in two places.

| Sequence step | What P0.5 does there |
|---|---|
| Before "Request API token with organization context" | Creates the organization the token will name, associates the API's machine-to-machine application with it, and makes the first administrator a member with a role from the shared template; until the last step no token for the organization resolves to a usable tenant, because the tenant's status is `provisioning`, which this design asks the P0.4 design's next version to count among the statuses its resolver denies as disabled (question 10) |
| Set trusted tenant context and execute command | The membership row and the seed rows for the new tenant are written as `app_role` with the tenant key set to the new tenant's identifier, so that the first tenant-owned rows a tenant ever has pass the P0.7 design's `WITH CHECK` like any later row; the tenant row and the mapping are written as `provisioning_role`, the platform-level tables' only writer |
| Record action and outcome | Every run and every step writes to the provisioning record, and the audit record (P0.10) carries the run's identifier, the actor's platform-level authority, and the outcome |

The contract's rule that "A branch is not automatically a tenant" and that a separately licensed broker or delegated agency "normally is" (ARCH-001 section 7) is the command's first refusal: it provisions a tenant and nothing beneath one; a business unit arrives through the tenant's own commands after activation.

## Interfaces and data shapes

### The request

The command is `provisionTenant`, a command of the tenancy module under the P0.2 design's registry, callable only under platform-level authority, which the P0.4 design fixes for every write to the mapping. It is not a route of the tenant API: it runs as an operator-invoked job in the platform repository, because it needs the Management API credential, which the P0.12 design classes as administrative, permits "read only during an exercise, never by a running process", and confines to the rotation exercise. A provisioning run is a second use of that credential, which the P0.12 design does not permit as it stands; this design asks that design's next version to admit the run under the same log evidence (question 4), and until then the departure is this design's.

```text
ProvisionTenantRequest {
  request_reference   text, the idempotency key; supplied by the caller, unique
  tenant_id           uuid, the tenant's identity; supplied by the caller
  name                text, 1 to 128 characters, the organization's name too
  authority_profile_ref  text | null, an accepted profile's identifier, never its text
  administrator_subject  text, the Logto user identifier of the first administrator
  seed                text, the name of a seed set under db/seeds/, or none
  actor               text, the platform-level actor's resolved identity, never a free string
  submitted_at        timestamp with time zone, as the actor's surface recorded it
}
```

Three rules about the request:

- **The caller names the tenant.** `tenant_id` is an input, not an output, so that two runs for the same tenant can be told apart from two tenants with the same name; the fixtures use the P0.6 design's identifiers, `...00a` for Tenant A and `...00b` for Tenant B. A name is never a key: the Management API reference documents no uniqueness rule for an organization's `name` [L1], and control 9 records that two organizations may carry the same name.
- **Idempotent on the reference, convergent on the tenant.** A second run with the same `request_reference` returns the first run's result and performs nothing. A run with a new reference for an existing `tenant_id` converges: every step checks its state and acts only where the state is absent, so a rerun after a failure completes what remains. A run whose immutable inputs, `tenant_id` and `administrator_subject`, differ from the record's is refused, not applied, so that a rerun cannot re-point an existing tenant (control 5). `name` and `authority_profile_ref` are not immutable, and a differing value is a refusal too until a later version defines a rename (question 6).
- **The administrator exists first.** `administrator_subject` is a Logto user the command adds as a member; creating the user is an identity act, not a tenant act, and the research reads that members join "by admin assignment, by email invitation ... or by JIT provisioning" (F10), of which the command uses the first (question 5). For the fixtures the subject is `user_a_synthetic` and `user_b_synthetic`, created by the identity fixture before the run.

### The provisioning record

A platform-level table in the tenancy schema, `tenancy.provisioning_run`, registered platform-level like `tenancy.tenant`, written by `provisioning_role` alone, one row per run whose `status` and `step` are updated in place as the run advances, with every step's outcome also written to the audit record (P0.10), and the third table this design asks the P0.6 design's next version to list; `provisioning_role`'s `INSERT` and `UPDATE` on it are an addition to the privileges the P0.7 design lists for that role, which this design asks the P0.7 design's next version to carry:

| Column | Content |
|---|---|
| `id` | The run's identifier, a uuid |
| `request_reference` | The caller's reference; unique across runs |
| `tenant_id` | The tenant the run is for |
| `request` | The request as submitted, for the immutable-input comparison of a later run and for the reconciliation report |
| `status` | `running`, `succeeded`, `failed`, `refused` |
| `step` | The last step reached, one of the six below, and its outcome |
| `result_digest` | On success, a hash over the tenant's identifier, the organization's identifier, the membership's identifier, the seed rows' identifiers and the statuses, in a fixed order; what "same result" compares |
| `actor`, `recorded_at` | The platform-level actor and the record time, as the baseline |

One rule the table enforces: at most one running run per tenant, by a unique partial index over `tenant_id` where `status = 'running'`, which "enforces uniqueness among the rows that satisfy the index predicate, without constraining those that do not" [G5]; a second concurrent run for the same tenant is refused at its first write (control 3).

### The steps

Each step is a check followed by an act, and each writes its outcome to the record before the next begins. The Management API calls are the reference's [L1] [L2]; the fixture identifiers are invented.

| # | Step | The check | The act, when the check finds nothing | Role |
|---|---|---|---|---|
| 1 | The tenant row | `tenancy.tenant` has a row for `tenant_id` | Insert the row with `status = 'provisioning'`, the name and the profile reference; the identity column null | `provisioning_role` |
| 2 | The organization | The tenant row carries an `identity_organization_id`, and `GET /api/organizations/{id}` finds it; failing that, and only when this tenant's last run stopped inside step 2, `GET /api/organizations`, whose one filter is "a partial ID or name" [L5], is read in full for an organization whose `customData` carries `biztrust_tenant_id = tenant_id` and whose `name` is the request's, which the run adopts by writing its identifier. This is the one code path that reads `customData`, a departure from the P0.4 design's rule that none does, confined to finding what a run of this command created and never to deciding a tenant's identity, which stays on the BizTrust side as that design and the research's gap 3 settled it; this design asks the P0.4 design's next version to admit the read (question 10) | `POST /api/organizations` with `name` and `customData: { biztrust_tenant_id }`, the reference's fields [L1]; write the returned `id` to the tenant row. The `customData` write is the research's "for storing internal organization mappings" (F11) used for reconciliation only: the BizTrust-side mapping is authoritative, as the P0.4 design fixes | The Management API credential, then `provisioning_role` |
| 3 | The API's application | `GET /api/organizations/{id}/applications` lists the API's machine-to-machine application, and its organization roles include the resolver's role | `POST /api/organizations/{id}/applications` with the application's identifier, then `POST /api/organizations/{id}/applications/roles`, "Assign roles to applications in an organization", with the application and the role [L2]; without the association a token request for the organization is refused, "app has not associated with the organization" (F8); then the application's membership row, `subject` the application identifier, `status = 'active'`, `source = 'provisioning'`, as the P0.4 design's question 8 assumes | The Management API credential, then `app_role` with the tenant key set to `tenant_id` |
| 4 | The first administrator | `GET /api/organizations/{id}/users` lists `administrator_subject` with the administrator role, and `identity_access.membership` has an active row for the subject and the tenant | `POST /api/organizations/{id}/users` with the subject, `POST /api/organizations/{id}/users/roles`, "Assign roles to organization user members", with the subject and the administrator role from the shared template, which "Every organization created in your Logto tenant automatically inherits" (F3) [L2], then the membership row, a tenant-owned row of the P0.4 design, with `status = 'active'`, `source = 'provisioning'` | The Management API credential, then `app_role` with the tenant key set to `tenant_id` |
| 5 | The seed | The seed set's rows exist under the tenant, by their fixed identifiers | Insert the seed set's rows, for Tenant A one legal entity and two business units, for Tenant B one and one, as the P0.6 design's fixtures state, each row carrying `tenant_id`; a row the seed carries for another tenant errors at the P0.7 design's `WITH CHECK` and fails the run (control 6) | `app_role`, with the tenant key set to `tenant_id` for the transaction |
| 6 | Activation | This run's record is `succeeded` with a digest, which a fresh run never finds | Set `status = 'active'` where it is not; compute and write the result digest; close the run as `succeeded` | `provisioning_role` |

Two properties hold across the steps. The organization's identifier is never a name and never guessed: it is what step 2 wrote or adopted, and "The organization id is a unique identifier for each organization" [L3]. And activation is last: a token for the organization between steps 2 and 6 resolves to a tenant whose status is `provisioning`, which the P0.4 design's resolver, once its next version counts that status as disabled (question 10), denies without reading a tenant-owned row (control 4).

### Partial failure

A run stops at the first step that fails, records the step and the error, and closes as `failed`; it compensates nothing. What it leaves behind, per step, and what the rerun does:

| Stopped after | Left behind | The rerun |
|---|---|---|
| Step 1 | A tenant row in `provisioning`, unreachable by any token | Finds the row; continues at step 2 |
| Step 2's call, before its write | An organization in Logto carrying the tenant identifier in `customData`, unmapped | Adopts it by the `customData` search; continues (control 2) |
| Step 2 | The mapping | Continues at step 3 |
| Step 3 or 4 | An association or a membership in Logto, and possibly the BizTrust membership | Each check finds what exists and adds what does not |
| Step 5, mid-seed | Some seed rows | The seed's rows have fixed identifiers, so the rerun inserts the missing ones and touches no other |
| Step 6 | The tenant active, the run without a digest | Computes and writes the digest; the tenant is already active |

Abandonment is an operator act, not the command's: the tenant is set `closed` through the lifecycle the P0.4 design names, the organization's deletion in Logto is a separate administrative act whose cascade the research reads in the schema (F12) and whose effect on issued tokens is `UNVERIFIED` (gap 1), and the run's record stays as it was. The command never deletes an organization, a membership or a row (question 7).

One case the rerun refuses rather than repairs: the mapping names an organization that `GET /api/organizations/{id}` no longer finds. The command does not create a replacement, because that is the P0.4 design's re-creation event, with the old identifier retired into the history table by one command with one audit record; it stops with the finding for an operator (control 10).

### The reconciliation report

The P0.4 design places with this design the reconciliation between Logto's memberships and BizTrust's. It is a read-only report, run by P0.5-B as the operator's job with the same credential rule as a provisioning run, and it changes nothing: every difference is a finding for an operator. It reads `GET /api/organizations` in full [L5] and, for each mapped organization, `GET /api/organizations/{id}/users` and `GET /api/organizations/{id}/applications` [L2], and compares:

| Comparison | Finding |
|---|---|
| Organizations carrying `biztrust_tenant_id` in `customData` against `tenancy.tenant` | An organization with no mapping, or a mapping whose organization is not found |
| Each organization's members against `identity_access.membership` for the mapped tenant | A member with no active membership row, or an active row with no member, per subject |
| Each organization's applications against the API's application | An application other than the API's, or the API's application absent |
| Each mapped organization's `name` against the tenant's | A differing name, recorded and not acted on, since neither is a key |

The report's record carries the same evidence fields as a run's, and the P0.4 design's control 9, Logto's behaviour after removal, is measured beside it.

### Two tenants, twice

The acceptance the manual's row states is a test in `tests/security/`, beside the P0.7 design's bypass package, and its record is what `BT-G6` later reads for "Tenant #2 provisioning and isolation proof"; it is not that gate, which the plan judges inside `BT-G7` (label E):

1. Run `provisionTenant` for Tenant A with the fixture request; record the digest and the run's two traces, the Management API calls and the database statements.
2. Run it again with a new `request_reference`; the digest is equal, the Management API trace holds only `GET` calls, and the statement trace holds no insert or update outside the run's own record.
3. Run it for Tenant B; then again; the same two properties.
4. Diff the two tenants' traces, both kinds, with the inputs masked; the diff is empty. That is INV-011's "without a tenant-specific core-code fork" (ARCH-001 section 7's invariant candidate) as a measurement: the code path is one, and what differs is the request and the seed set.
5. Run the P0.7 design's controls 1 to 5 against the two provisioned tenants, so that isolation is proven on tenants the command made, not on rows a test typed.

## Negative controls

Each control is seen failing before the protection exists and passing after; the verifier is not the implementer. The environment holds Logto with the shared organization template, the synthetic users, and a database with the P0.6 design's tables and the P0.7 design's policies.

| # | Threat or defect | Condition | Expected denial or failure | Seen failing at |
|---|---|---|---|---|
| 1 | The command duplicates | Tenant A provisioned, then run again with a new reference | Equal digests; no `POST` in the second trace; one organization in Logto carrying Tenant A's identifier | Before the checks: a second organization, a second membership |
| 2 | The double-create window | A fault injected after step 2's `POST` and before its write; then a rerun | The rerun adopts the organization found by `customData`; one organization | Before the adoption search: two organizations, the first orphaned |

| 5 | A run re-points a tenant | A request carrying Tenant B's `tenant_id` with Tenant A's name and administrator | Refused: immutable inputs differ from the record; Tenant B unchanged | Before the immutable-input check: Tenant B renamed and its administrator replaced |
| 6 | A seed crosses tenants | Tenant A's seed set given a business unit row with Tenant B's `tenant_id` | The P0.7 design's `WITH CHECK` errors; the run fails at step 5; Tenant A stays `provisioning` | On the P0.7 design's baseline database: the row is written under Tenant B |

## Open questions and dependencies

1. **ADR-003 decides what Management API access the platform holds and which organization roles the template carries.** Waits on: [#104](https://github.com/bstBizEra/biztrust_guide/issues/104) on the contract map, behind the waiver (#92). `ASSUMED` meanwhile: one machine-to-machine application with the built-in Management API role, of which the documentation says "Before accessing Logto Management API, make sure your M2M app has been assigned with M2M roles that include the `all` permission from this built-in \"Logto Management API\" resource." [L4], held as the P0.12 design's administrative credential; two template roles the command assigns, the resolver's role for the API's application and the administrator role for the first member; the research's gap 4, template-wide roles against per-tenant authority, is ADR-003's and ADR-013's.
2. **Who submits a request, and from where.** Platform-level authority is the P0.4 design's phrase; which human role holds it and through which surface is P0.13's and the operator's. Waits on: the P0.13 design ([#185](https://github.com/bstBizEra/biztrust_guide/issues/185)) and the operator's instruction on the seat. `ASSUMED` meanwhile: an operator-invoked job in the platform repository, run by the engineering role with the security reviewer named, from a request file reviewed like code; no route of the tenant API submits one.
3. **The authority profile at provisioning.** A real tenant carries a reference to an accepted profile; the fixtures carry null. Waits on: slice S01 ([#93](https://github.com/bstBizEra/biztrust_guide/issues/93)) and ADR-013. `ASSUMED` meanwhile: `authority_profile_ref` nullable in P0, and a later version refusing activation of a tenant without one once a profile exists to reference.
4. **The Management API credential's class and the run's read.** The P0.12 design permits the administrative credential "read only during an exercise, never by a running process" and confines its use to the rotation exercise. Waits on: the P0.12 design's next version, which this design asks to admit a provisioning run as a second use, with the same log evidence; until then this design departs from that design's row. `ASSUMED` meanwhile: the run reads the credential from the store at its start and holds it for the run's duration only, and control 7 measures it.
5. **The first administrator's origin.** The command adds an existing user; how that user comes to exist for a real tenant, invitation or an operator's creation, is P0.13's. Waits on: the P0.13 design. `ASSUMED` meanwhile: the synthetic users exist before the run, created by the identity fixture.
6. **Re-creation, rename and closure as runs.** The P0.4 design's lifecycle names re-creation as "one provisioning command with one audit record" and closure as a status change. Waits on: the P0.4 design's control 8 and 9 records, and the operator's decision on the map (#128) to chart a ticket for the lifecycle runs, which this design's later version would resolve. `ASSUMED` meanwhile: neither is a mode of this command; a differing name is a refusal; re-creation and closure are written by the operator through the lifecycle with their own record rows.
7. **Abandonment and deletion.** The command deletes nothing. Waits on: the runbook P0.5-B writes and the P3 disaster-recovery epic reviews, and the research's gap 1 for what a deleted organization's tokens do. `ASSUMED` meanwhile: a failed tenant is `closed`, never deleted from BizTrust; the organization's deletion is a separate act with its own audit record.
8. **A dedicated tier.** ADR-004's exit path adds schema objects per tenant. Waits on: ADR-004 ([#105](https://github.com/bstBizEra/biztrust_guide/issues/105)). `ASSUMED` meanwhile: no per-tenant schema object or database role; the ticket's "schema objects, roles" are the organization's roles of steps 3 and 4.
9. **Rate limits on the Management API.** Logto Cloud "applies tenant-level runtime rate limits" [L4]; for the self-hosted edition no limit is documented, `UNVERIFIED`. Waits on: ADR-002's hosting decision. `ASSUMED` meanwhile: runs are few and sequential, and the acceptance test records the calls per run so that a limit, if met, is seen.
10. **Two asks on the P0.4 design's next version.** Its resolver denies as disabled on `suspended` or `closed` and names no outcome for `provisioning`; and its rule that no code reads `customData` has one exception here, the adoption read of step 2. Waits on: the P0.4 design's next version, which this design asks to count `provisioning` as disabled and to admit the read as reconciliation, not authority. `ASSUMED` meanwhile: both; control 4 is the check for the first, and the adoption read decides nothing but which organization a run of this command created.

No item is `UNKNOWN_BLOCKING`: the design proceeds on its assumptions and each is reversible by the decision it names.
