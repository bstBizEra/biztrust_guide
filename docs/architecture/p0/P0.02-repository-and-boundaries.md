## Scope and non-scope

**In scope.** The platform repository as the place every later package lands, shaped so that the modular monolith's boundaries are tested rather than intended:

1. **The workspace and its layout**: one repository, one package manager workspace, the top-level directories the hub's repository design names, and a module registry that is the single list of modules the boundary rule is generated from.
2. **The module list**, taken from the contract's capability map as candidate modules, grouped as the contract groups them, with each module's owner role and schema name.
3. **The dependency rule**: what a module may import, what it may not, and the one place a module exposes its contract.
4. **One schema per module** and the rule that a module's SQL touches only its own schema.
5. **The build-time check** that enforces the rule, the **boundary tests** that prove the check, and what a violation looks like in CI.
6. **The CI skeleton**: the jobs every pull request runs, each a required check.
7. **`AGENTS.md` and `badf/`** carried from this repository: the charter, the continuity records, their schemas and the validator that fails CI when a record does not conform.
8. **The repository administrator**, a human role, because protecting `main` is not something an agent can do (the P0 manual's entry section).

**Non-scope**, each with its owner:

- The internals of any module: each epic's design (P0.3 to P0.13). This design gives a module a place and a boundary, not code.
- Row-level security policies and the tenancy schema's tables: P0.7 and P0.6. This design fixes only that a module owns one schema and touches no other.
- API and event conventions and where their contract files live in detail: P0.8 and P0.9; this design reserves `openapi/` and `events/` as the hub's tree does.
- Security scanning, SBOM, signing and the full pipeline: the hub's security track and P3B.1. The skeleton here has the jobs a boundary needs; P0.12 adds the scanning gate.
- Whether a candidate module is a bounded context, subdomain or aggregate: `BIZTRUST-DOMAIN-001` and the bounded context map ticket ([#113](https://github.com/bstBizEra/biztrust_guide/issues/113)); the contract says its list "must not be used to justify premature service extraction" and this design uses it only as a list of boundaries to test.
- The extraction criteria for a module and the deployment trade-off: ADR-001.
- The UI: the stack decision said P0 ships no UI before ticket #157 added P0.13 to the plan; at `0.2` `apps/` holds the control plane after the proof, the P0.13 design's, and nothing else in P0.
- Hosting of the repository and its CI runners: the map's fog item on hosting; this design assumes the host this guide uses (the open question on the host).

## Authorization-sequence step

P0.2 is outside the tenant authorization sequence of [`FLOWS.md`](../FLOWS.md) section 3; it protects three of its steps by making their modules unreachable except through their contracts:

| Sequence step | What P0.2 protects there |
|---|---|
| Organization-to-tenant resolver and business authorization | The tenancy and identity-access modules' internals cannot be imported by any other module, so a business module cannot resolve a tenant or a permission by its own reading of another module's tables; it asks through the contract, which is where P0.4's mapping and the authorization decision live |
| Row-level security in PostgreSQL | A module's SQL touches only its own schema, so the trusted tenant context P0.7 proves is set and read in one place per module; a cross-schema query is a lint failure before it is a policy question |
| Audit | The audit module's write interface is its contract; no module inserts audit rows directly, which is what makes the audit record's controls (P0.10) enforceable |

## Interfaces and data shapes

### The workspace

One repository, one pnpm workspace ("A workspace must have a `pnpm-workspace.yaml` file in its root" [P1]); local packages depend on each other through the workspace protocol, under which "pnpm will refuse to resolve to anything other than a local workspace package" [P1]. The top-level layout starts from the hub's target repository architecture so that the two repositories read alike, with the departures listed under the tree:

```text
biztrust/
├── AGENTS.md            the charter, carried from this repository and revised for a platform
├── apps/                broker, admin and partner experiences; in P0 the control plane after the proof (P0.13) and nothing else
├── services/            API and worker entry points
├── modules/             one workspace package per module; the boundary the rule is enforced on
│   └── modules.yaml     the module registry (below)
├── packages/            shared contracts and observability, as the hub draws it; no domain code and, in this design, no UI
├── openapi/             contract-first API specifications (P0.8)
├── events/              versioned event contracts (P0.9)
├── db/                  migrations per module schema, policies, seeds, RLS tests (P0.6, P0.7)
├── badf/                lifecycle, authority, gates, agents and skills registries; the continuity records
├── docs/                architecture, adr, product, security, operations, decisions
├── work-packages/       authorised delivery units
├── evidence/            manifests bound to a revision
├── sessions/            checkpoints and handoffs
├── schemas/             the machine-readable shape of every badf/ and evidence record
├── scripts/             deterministic validators, run by CI
├── tests/               unit, contract, security and end-to-end
└── .github/workflows/   the CI skeleton in P0; the hub's CI, security and release enforcement arrive with the security track and P3B.1
```

Departures from the hub's drawing, each deliberate: `modules/modules.yaml` is added as the registry below; the UI the stack decision places as a separate package in the same repository lives under `apps/` as an experience, not under `packages/`, because rule 5 below lets an experience import modules' contracts and rule 4 forbids a package to; `badf/` holds the hub's five registries and, beside them, the continuity records this repository keeps; `docs/` keeps the hub's six children, collapsed in the drawing; and `.github/workflows/` carries only the skeleton until later epics add to it. `openapi/` and `events/` are reserved for the contract-first rule of ADR-005, which P0.8 and P0.9 fill.

The owner of the layout is the repository's charter; a directory is added by a Work Package that says why, never by a package that needed somewhere to put a file.

### The module registry

`modules/modules.yaml` is the one list of modules. The boundary rule, the schema list and the migration lint are generated from it, so a module that is not in the registry cannot import, be imported, or own a table. One entry per module:

| Field | Meaning |
|---|---|
| `name` | The package name, `@biztrust/<module>`; also the PostgreSQL schema name, with hyphens as underscores |
| `group` | `platform`, `brokerage`, `financial` or `integration`, the contract's four groups |
| `owner_role` | The role that answers for the module's contract and schema |
| `contract` | The path of the module's public entry, `src/public/index.ts`; the only path another package may import |
| `schema` | The PostgreSQL schema the module owns, derived from `name` unless the entry says `none` for a module with no persisted state |
| `epic` | The P0 or later epic whose design fills the module; a module with no epic yet is a registry row and nothing else |
| `source` | `contract`, for a candidate module of the contract's capability map, or the design that introduced the module, so that an addition to the map's list is visible as one |

The initial entries are the contract's candidate modules, grouped as its capability map groups them:

| Group | Modules, as the contract lists them |
|---|---|
| Platform | Tenancy, Identity & Access, Distribution, Compliance, Audit |
| Brokerage | Party, Client, Risk, Distribution Product, Submission, Placement, Quote/Indication, Recommendation, Binding, Policy, Claims, Renewal |
| Financial | Billing, Payment, Ledger, Commission, Settlement, Reconciliation |
| Integration | Insurer, Payment Provider, Bank, Partner API, Documents, Notifications |

Every candidate module of the map is a row with `source: contract`; the platform-configuration module the P0.12 design names is a row with `source: design:P0.12` under the Platform group, an addition to the map's list that the registry shows as one. P0.2 creates package directories only for the modules P0 builds, Tenancy, Identity & Access, Audit and platform-configuration; every other row is a registry entry with no directory until an epic's design needs one, and the rule set still covers every group from the first commit because the rules are generated from the rows. No module, package or path is ever named for a tenant: tenant variation is configuration under ADR-011, and a tenant's name in the registry is a review finding. Whether each candidate is a bounded context or an aggregate is not decided here (the open question on what a candidate module is).

### The dependency rule

Seven rules; the first six and rule 7's import half are generated from the registry into the checker's configuration, and rule 7's allow-list is a check of its own:

1. **A module's internals are private.** Anything under a module's `src/internal/` may be imported only from inside that module. The package's `exports` field exposes `src/public/` and nothing else, so an import of an internal path fails at resolution as well as at the check: "When the `"exports"` field is defined, all subpaths of the package are encapsulated and no longer available to importers", and the import throws `ERR_PACKAGE_PATH_NOT_EXPORTED` [N1]; the same page notes it "is not a strong encapsulation" against an absolute path, which is why the check exists as well.
2. **Modules depend on contracts.** A module may import another module only through `@biztrust/<module>`, which resolves to that module's `contract` path. What a contract exports is the module's commands, queries, published event types and identifier types; never a repository, a table or a connection.
3. **No cycles.** The module dependency graph is acyclic. A pair of modules that need each other is one module or a missing contract; the check says which pair.
4. **Shared code is not domain code.** `packages/*` may be imported by any module and may import no module. A package that needs a module's type has found domain code in the wrong place.
5. **Entry points and experiences see contracts only.** `services/*` and `apps/*` import modules' contracts and `packages/*`; nothing imports `services/*` or `apps/*`.
6. **Test packages stay in tests.** Anything under `tests/` may be imported only from `tests/`; no module, package, service or experience imports it, and the build excludes it from every deployable artifact. The rule exists so that the P0.7 design's bypass entry point, a test-only package that runs a statement as the application role with a key set and no authorization, cannot reach a running service (the P0.7 design's question 8).
7. **The control plane sees packages only.** `apps/control-plane` imports `packages/*` and no module's contract, a narrower rule than rule 5 for that one experience, because a contract call runs in the calling process and would pass the P0.3 chain, the P0.4 resolver and the audit by; the surface reaches the platform through the admin API alone. Its outbound hosts are an allow-list, Logto's sign-in endpoints and the admin API, checked in CI and at runtime as the P0.13 design's control 9 has it, by a check that design's question 8 asks this design to carry (the P0.13 design's question 8).

The check runs at build time on every pull request. Two candidates from the stack decision are named under Technology candidates; both express these rules as forbidden or allowed dependencies between path patterns, which is why the registry, not the checker, is the source of the rules.

### The boundary test suite

The negative controls below are the first runs; the suite keeps running them. Under `tests/boundaries/` a fixture workspace holds one deliberately violating import per rule, one per line of the controls table, and one conforming import per rule; a test runs the checker over the fixture with the rules generated from a fixture registry and asserts that each violating import is reported with its rule's name and each conforming one is not. A second test runs the migration lint over fixture migrations the same way. The suite fails when a rule is loosened, when the generator drifts from the registry, or when the checker's output changes shape, which is what turns a one-time observation into a boundary that is tested.

### One schema per module

Every module with persisted state owns one PostgreSQL schema, named in the registry, and no other; ADR-001's ticket names one schema per module and no cross-module table access among what that ADR decides, so this section is a proposal to it as much as to ADR-004. The rules a migration lint enforces, drawn from the contract's data-ownership section ("Every authoritative datum has one owner ... Cross-module direct table mutation is prohibited. The owning module changes its state through a command and publishes resulting facts through contracts.") and the domain model's aggregate rules ("An aggregate has exactly one owning module. Only the owner executes its commands and persists its invariant-bearing state. Other modules reference stable identifiers or consume versioned facts."):

- A migration under `db/migrations/<module>/` creates, alters or drops objects in that module's schema only.
- No foreign key crosses a schema boundary; another module's aggregate is referenced by its stable identifier, and the reference's integrity is the owning module's contract to keep.
- Every tenant-owned table carries the tenant-owned record baseline of the domain model's section 6, `tenant_id` first; whether `tenant_id` is physically repeated on child rows is `BIZTRUST-DATA-001`'s decision and P0.6's to carry.
- A module's runtime SQL names only its own schema; the lint over migrations is the build-time half, and P0.7's negative controls are the runtime half.

### The CI skeleton

One workflow, every job a required check on `main`, in this order; a later job does not run if an earlier one fails:

| Job | What it runs | What a failure looks like |
|---|---|---|
| Install | The package manager with a frozen lockfile | A changed lockfile that the pull request did not commit |
| Validate records | The continuity validator over `badf/` and `sessions/`, carried from this repository, and the security proof's manifest validator over `evidence/security-proof/` (the proof's question 9) | A state file, action, checkpoint or manifest that does not conform to its schema, named by path and field, or a manifest the proof's validator refuses for the reasons that design lists |
| Typecheck and lint | The compiler and the linter across the workspace | The first error with file and line |
| Contract lint | The P0.8 design's rules L1 to L10 over `openapi/`, L10 being that design's candidate `oasdiff breaking` against the base, and the P0.9 design's gates E1 to E10 over `events/`; then the same rules, L10 and E8 excepted since a fixture has no base, over `openapi/fixtures/` and `events/fixtures/`, where a fixture that passes is itself a failure; the job owned by the data reviewer role, as the P0.8 design names it (the P0.8 design's lint section and the P0.9 design's) | The rule and the file, one line per violation; on the fixture run, the fixture that did not fail |
| Observability tests | The P0.11 design's reconstruction test and its controls under `tests/observability/` (the P0.11 design's question 9) | The missing join or the attribute outside the allow-list, named |
| Boundary check | The checker's rules generated from the registry | The rule's name, the importing file and the imported path, one line per violation, and a non-zero exit |
| Migration lint | The schema-per-module rules over `db/migrations/`; on an audit table, a refusal of `UPDATE`, `DELETE`, `TRUNCATE`, `DROP`, a column drop or a type change, with a column add allowed (the P0.10 design's protection table); on any table in P0, a refusal of the four names the security proof's control 6 lists, policy, client, claim and premium | The migration file and the object it creates outside its schema, mutates in the audit schema, or names from the domain list |
| Unit and boundary tests | The test runner, including the boundary test suite, the negative controls above, and the security proof's suite, run as one suite by its matrix file over `tests/security/`, `tests/boundaries/` and `tests/observability/`, on every pull request without a manifest (the proof's question 7) | The failing test's name and assertion |
| Build | Every package builds | The package and the error |

A violation therefore reads, in the pull request's checks, as one named rule broken by one file, and the pull request cannot merge until the check is green. This design proposes no override label: a rule that must be relaxed is changed in the registry by a pull request that says why. The protection itself is the administrator's record to write.

### `AGENTS.md` and `badf/`

The platform repository's charter is this repository's charter revised for code: the same precedence order, resume protocol, sources of truth, checkpoint and handoff contracts, state transitions, evidence requirements and stop conditions, with the work constraints rewritten for a repository that ships software. The five registries the hub names, `lifecycle.yaml`, `authority.yaml`, `gates.yaml`, `agents.yaml` and `skills.yaml`, sit under `badf/` beside the continuity records, each with a schema under `schemas/` and each validated by the same job that validates the records. The authority registry is where a Work Package's implementation grant, with its expiry, is recorded before any code lands, which is the rule this guide's manuals state and the platform's CI can then read.

### The repository administrator

A human role, named in the P0.2 Work Package, holding what no agent may: protection of `main` with the nine checks above required and force-push and deletion blocked, with one independent approval per merge proposed as this repository's own practice; the repository's secrets for CI, held per P0.12's inventory; and the recording, in the authority registry, of the business authority seat's implementation grant for P0.2 with its expiry, since the grant is the business authority's to give and the administrator's to record. The plan's seat table gives the administrator seat pages, the governing Work Package issue and protection of `main`; who holds it is the review-seat register's (#94).

## Negative controls

Each control is seen failing before the protection exists and passing after; the verifier is not the implementer.

| # | Threat or defect | Condition | Expected denial or failure | Seen failing at |
|---|---|---|---|---|
| 1 | A module reaches into another's internals | A file in the Tenancy module imports `@biztrust/audit/src/internal/...` | The package resolution refuses the path and the boundary check names rule 1, the file and the import; the pull request cannot merge | Before the `exports` field and the rule: the import resolves and CI is green |
| 2 | A cycle between two modules | Identity & Access imports Tenancy's contract and Tenancy imports Identity & Access's | The boundary check names rule 3 and the pair | Before the rule: both imports resolve |
| 3 | An entry point bypasses a contract | A file in `services/api` imports a module's internal repository class | The boundary check names rule 5 and the file | Before the rule: the import resolves |
| 4 | A migration writes outside its schema | A migration under `db/migrations/tenancy/` creates a table in the `audit` schema | The migration lint names the file and the object | Before the lint: the migration applies |
| 5 | A foreign key crosses a schema | A migration adds a foreign key from a tenancy table to an audit table | The migration lint names the constraint | Before the lint: the migration applies |
| 6 | Code lands without the checks | A push straight to `main`, and a pull request merged with a failing boundary check | The host refuses the push and the merge; the refusal is the administrator's evidence | Before protection: the push lands |
| 7 | A module exists outside the registry | A package is added under `modules/` with no registry entry | The boundary check's generation step fails, naming the package | Before the generation step: the package builds |
| 8 | A record drifts from its schema | A checkpoint is committed with a missing field | The validate-records job fails, naming the file and the field | Before the validator runs in CI: the commit is green |
| 9 | A test package reaches a service | A file in `services/api` imports the P0.7 design's bypass package | The boundary check names rule 6 and the file; the build excludes the package and the import fails to resolve | Before rule 6: the import resolves and the entry point ships |
| 10 | The control plane imports a contract or reaches another host | A page under `apps/control-plane` imports `@biztrust/tenancy`; separately a fixture build of the surface fetches a host outside the allow-list | The boundary check names rule 7 and the file; the allow-list check names the host, in CI and at runtime | Before rule 7: the import resolves under rule 5 and the page reads the module in-process; before the allow-list: the fetch succeeds |
| 11 | A domain table in P0 | A migration under `db/migrations/tenancy/` creates a table named `policy` | The migration lint names the file and the word | Before the rule: the migration applies and the phase has been left |
| 12 | A mutation of an audit table | A migration issues `DELETE FROM audit.decision` | The migration lint names the file and the statement | Before the rule: the migration applies |

## Open questions and dependencies

1. **ADR-001 decides the style, the boundary rule and the extraction criteria.** Waits on: [#103](https://github.com/bstBizEra/biztrust_guide/issues/103) on the contract map, behind the waiver (#92). `ASSUMED` meanwhile: the contract's proposed decision, a modular monolith behind explicit module contracts, with the seven rules above as the boundary rule and one schema per module as the storage rule; if the ADR narrows or widens them, this design is revised under a new version.
2. **Whether a candidate module is a bounded context, a subdomain or an aggregate.** Waits on: `BIZTRUST-DOMAIN-001` and the bounded context map ([#113](https://github.com/bstBizEra/biztrust_guide/issues/113)). `ASSUMED` meanwhile: the capability map's candidate modules are the registry's entries, one package each, and a merge or split of two candidates is a registry change under the map's decision.
3. **One schema per module against the physical tenant-key decision.** Waits on: ADR-004 ([#105](https://github.com/bstBizEra/biztrust_guide/issues/105)) and `BIZTRUST-DATA-001`. `ASSUMED` meanwhile: one schema per module with `tenant_id` on every tenant-owned table, as the domain model's baseline lists it first.
4. **Which checker.** Waits on: ADR-001, whose evidence names boundary tests but not the tool. `ASSUMED` meanwhile: dependency-cruiser for the shape of the generated rules, since its `forbidden` entries map one to one onto rules 1 to 6 and rule 7's import half; the registry keeps the switch cheap.
5. **The migration lint.** No research names a tool that checks a migration's objects against a schema list, and at `0.2` the lint also carries the audit-schema rules and the domain-name list. Waits on: ADR-004 ([#105](https://github.com/bstBizEra/biztrust_guide/issues/105)), whose evidence is the RLS design and owner analysis the lint enforces half of, and the P0.6 design, which fixes the schema rules the lint reads. `ASSUMED` meanwhile: a deterministic script under `scripts/`, parsing migration SQL for `CREATE`, `ALTER`, `DROP` and `REFERENCES` targets and, at `0.2`, for `UPDATE`, `DELETE` and `TRUNCATE` on the audit schema and for the four domain names, in the pattern of this repository's continuity validator; a tool that does the same is a later candidate under ADR-004.
6. **Where durable workflows live.** Waits on: ADR-010 ([#109](https://github.com/bstBizEra/biztrust_guide/issues/109)). `ASSUMED` meanwhile: a workflow is a module's code that calls other modules' contracts; a workflow runtime, when chosen, is infrastructure behind `packages/`, and no module imports the runtime's internals.
