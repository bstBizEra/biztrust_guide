## Scope and non-scope

**In scope.** The shape every tenant-owned table takes and the tests that hold it:

1. **The mandatory `tenant_id` rule** and the tenant-owned record baseline the domain model lists, as a table template every module's schema follows.
2. **The tenancy module's own schema**: tenant, legal entity and business unit, the minimum hierarchy the contract draws, with the column the organization-to-tenant mapping lands on; at `0.2`, the tables later designs asked this design to list beside them.
3. **The tenant key**: how a transaction carries the tenant it acts for into PostgreSQL, and why it is transaction-scoped.
4. **Table ownership**: the split between the role that owns tables and the role the application connects as, with the attributes each holds and does not.
5. **The enablement rule**: every tenant-owned table has row-level security enabled and forced before it holds a row; the policies' content is P0.7's.
6. **The migration tool and convention**: SQL-file migrations, one directory per module, expand-first, each step stating whether it reverses.
7. **Naming**, so that a catalogue query can tell a tenant-owned table from a platform table and a policy from an index.
8. **The ownership tests**: catalogue queries that fail when any of the above is violated, run after every migration in CI.

**Non-scope**, each with its owner:

- The policies themselves, their `USING` and `WITH CHECK` expressions, and the cross-tenant proof matrix: P0.7 and the security proof (`P0.SECURITY-PROOF.md`). This design makes a table policy-ready; P0.7 proves the policy.
- The organization-to-tenant mapping's lifecycle, mismatch handling and the membership tables: P0.4 and the identity-access module. This design reserves the column the mapping lands on.
- The bitemporal representation, ranges against assertion rows: ADR-015. The baseline carries the columns the domain model lists; the research's candidates are named in section 7 and the switch is a per-table change under that ADR.
- The physical repetition of `tenant_id` on child rows: `BIZTRUST-DATA-001`, as the domain model's section 6 says; this design assumes repetition (section 8, question 3).
- Tenant packs, dedicated schemas or databases per tenant, and the second tenant's onboarding proof: ADR-011, expansion streams E1 and E5, and `BT-G6`.
- Residency, retention, legal hold and deletion rules: ADR-019 and the data-governance track; the domain model's rule that deletion is a lifecycle operation, not a table operation, is kept and not designed.
- The authority profile's content for either tenant: slice S01 and the broker sheet (#93). The tenancy schema holds a reference to a profile, never its text, as the domain model's section 2.1 requires.
- Backups, restores and replication: P3's disaster-recovery epic; this design records only that they run outside row-level security by design (the research's leak 13) and so belong, at `0.2`, to `backup_role`, as the P0.7 design restated the path.

## Authorization-sequence step

P0.6 gives two steps of the tenant authorization sequence ([`FLOWS.md`](../FLOWS.md) section 3) the shape they bind on:

| Sequence step | What P0.6 provides there |
|---|---|
| Organization-to-tenant resolver | The tenant table's organization column, the one place a Logto organization identifier is written, so that P0.4's resolver reads a tenant and never a claim; and the rule that the resolved tenant, not any request header, becomes the transaction's tenant key |
| Trusted tenant context and row-level security in PostgreSQL | The transaction-scoped tenant key, the `tenant_id` column on every tenant-owned table, the enablement rule that makes a table default-deny until P0.7's policy allows, and the ownership split without which every policy is bypassed for the role that runs the application |

The step is only as strong as the research's first decision-relevant fact: the application role must be `NOSUPERUSER`, `NOBYPASSRLS` and must not own the tenant tables, or every tenant table must be forced; each exemption "silently disables every policy for that role". This design proposes all three, and proposes them as one layer among several: the authorization baseline's rule is that "No single layer substitutes for another. A gateway allow is not domain authorization, and an application allow is still constrained by RLS."

## Interfaces and data shapes

### The tenant-owned record baseline

Every tenant-owned table in every module's schema carries the domain model's baseline, in the domain model's order with one rename said here, as a template the migration convention copies:

| Column | Type and rule | Why |
|---|---|---|
| `id` | The domain model's `aggregate_id`, written `id` because every table's key is its aggregate's; a surrogate key, uuid, primary key | The research's own mitigation for existence inference through unique and foreign keys (leak 4): natural values are never the key |
| `tenant_id` | uuid, `NOT NULL`, foreign key to `tenancy.tenant(id)`; first column after the key | The mandatory tenant key the policies compare; `NOT NULL` so no row is tenantless |
| `legal_entity_id` | uuid, nullable, foreign key to `tenancy.legal_entity(id)` including `tenant_id` | Where legal-entity ownership matters (domain model section 4) |
| `aggregate_version` | integer, `NOT NULL` | The domain model's version reference |
| `effective_from`, `effective_to`, `effective_timezone` | date, date, text; present when the fact has valid-time effect | The domain model's baseline; the representation is ADR-015's (section 8, question 2) |
| `recorded_at` | timestamp with time zone, `NOT NULL`, set by the database | Record time, never supplied by the caller |
| `supersedes_id` | uuid, nullable, self-referencing foreign key including `tenant_id` | Correction and supersession as appends (the bitemporal research, candidate A) |
| `created_at`, `created_by`, `updated_at`, `updated_by` | timestamps and actor identifiers, `NOT NULL` | The baseline's audit columns; the actor is the resolved identity, not a free string |

Three rules follow from the research and apply to every table built on the template, the first two under the open question on the physical tenant key, with which they would be revised: every unique constraint includes `tenant_id`, so a conflict never reveals another tenant's value (leak 4); every foreign key between tenant-owned tables includes `tenant_id` in both key and reference, so a row cannot point across tenants; and no `BEFORE ROW` trigger writes `tenant_id` (leak 12).

### The tenant key

A transaction carries exactly one tenant, set by the application after the resolver has resolved it and before any query, through `set_config('app.tenant_id', <uuid>, true)`, which the research quotes as applying "only during the current transaction" (F7). The rules:

- **Transaction-scoped, never session-scoped.** A session-level `SET` "will persist until the end of the session, unless overridden" (F7), which on a reused pooled connection is a stale key honoured as-is (leak 11). The application never issues a session-level `SET` for the key.
- **Read with `missing_ok`.** Policies read `current_setting('app.tenant_id', true)`; with `missing_ok` true, "NULL is returned" for a setting that does not exist [G4], the policy's `USING` yields null, and "if false or null is returned then the row is not visible" (F4), so a transaction with no key sees no tenant-owned row.
- **Never copied from a request.** The key is the resolved tenant of the flows record's fourth step; an untrusted tenant identifier from a header or body is never written to it, which is the flows record's own rule and P0.4's control.
- **The pooling mode is proven, not assumed.** The research's decision-relevant fact is that the documentation "says nothing about external poolers" (its reading of F8); control 4 measures the chosen pooler in its chosen mode before any pooled deployment, and the record is the answer (section 8, question 4).
- **Fail loud where filtering would be wrong.** A dump is produced by `backup_role` alone, the one `BYPASSRLS` role, on which `row_security = off` has no effect (F2); any other role's dump errors rather than filters under `pg_dump`'s default, which "turns silent filtering into an error" for a non-bypass role (F9); the owner's dump on a forced table is expected to error too, since a forced table applies its policies to the owner (F3), which the P0.7 design marks `UNVERIFIED` against the `pg_dump` page's sentence that the owner always bypasses (F14) and measures in its control 9. The `0.1` sentence had the owner run backups with `row_security = off`, which under forcing errors on every tenant-owned table; the P0.7 design found this and this revision restates the path as that design has it. The application role never sets `row_security`.

### Table ownership

The roles are the P0.12 design's four and, at `0.2`, two more the P0.7 design asked for, `backup_role` and `provisioning_role`; the P0.12 design defines the four by purpose and the P0.2 design's registry names them by schema; this design proposes their PostgreSQL attributes, which the P0.12 design does not state, and agrees with it on every attribute both name. The attributes outside the research are cited to PostgreSQL's pages: `NOCREATEROLE` and `INHERIT` are the defaults [G1]; `TRIGGER` "Allows creation of a trigger on a table, view, etc.", `REFERENCES` "Allows creation of a foreign key constraint referencing a table", `TRUNCATE` "Allows `TRUNCATE` on a table", and for databases `CREATE` "allows new schemas and publications to be created within the database" [G2].

| Role | Owns | Attributes | Grants on tenant-owned tables | Never |
|---|---|---|---|---|
| `migration_role` | Every schema, table, policy, view and function; runs every migration | `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEROLE`; the only role with `CREATE` on the database | All, as owner | Serves application traffic; is used by a person outside a migration run |
| `app_role` | Nothing | `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB`, `NOCREATEROLE`; `NOINHERIT` from any owning role | `SELECT`, `INSERT`, `UPDATE`, `DELETE` per table as the module's contract needs; `USAGE` on the schema; on the audit tables `SELECT` and `INSERT` and nothing else, the P0.10 design's ask | `TRUNCATE`, `REFERENCES`, `TRIGGER` (whole-table commands "are not subject to row security", leak 3); ownership of anything; `BYPASSRLS` |
| `audit_writer` | Nothing | As `app_role` | `INSERT` on audit tables only | `UPDATE` or `DELETE` on audit tables; reading business tables, as the P0.12 design states |
| `store_root` | Nothing | `NOSUPERUSER`, `NOBYPASSRLS`; what it needs to rotate `app_role`'s credential is the P0.12 design's exercise to state | None on tables | Anything else; reading any tenant-owned table |
| `backup_role` | Nothing | `NOSUPERUSER`, `BYPASSRLS`, the one role that holds it; connects only from the backup job; every session audited (P0.10) | `SELECT` on every table, the read a dump needs, which its bypass makes unfiltered; no `INSERT`, `UPDATE` or `DELETE` anywhere | Serving application traffic; being used by a person; holding any application privilege beyond that read (the P0.7 design's ask) |
| `provisioning_role` | Nothing | `NOSUPERUSER`, `NOBYPASSRLS` | `INSERT` and `UPDATE` on `tenancy.tenant`, `INSERT` on `tenancy.tenant_organization_history`, `INSERT` and `UPDATE` on `tenancy.provisioning_run`, `INSERT` on `tenancy.platform_outbox`, and nothing else | Reading or writing any tenant-owned table; serving application traffic (the P0.7 and P0.5 designs' asks) |

Ownership by `migration_role` alone is not enough: "Table owners normally bypass row security" (F3) and the owner "can also switch RLS off at will" (leak 2). Every tenant-owned table is therefore `FORCE ROW LEVEL SECURITY` as well as enabled, so that a migration run under the owner that queries tenant rows is filtered like any other session, and control 3 proves it.

### The enablement rule

A tenant-owned table is created by one migration that, in the same step, enables and forces row-level security and creates its `tenant_id` column with its foreign key. Until P0.7's policy exists the table denies everything: "If no policy exists for the table, a default-deny policy is used, meaning that no rows are visible or can be modified" (F1), and "If there are no `PERMISSIVE` policies, then access is denied" (F4). A table with rows and no policy is therefore a failed deployment, not an open one, and the ownership tests say so before the rows arrive. The exceptions are the platform-level tables, `tenancy.tenant` and, at `0.2`, the history, run, outbox and inbox tables; the P0.7 design writes the policies of the first two, and its next version (#271) is asked to write the others in the same shape.

Views over tenant-owned tables carry `security_invoker = true`, because by default "the row-level security policies of the view owner are applied" (F10, leak 8). No `SECURITY DEFINER` function is created in a tenant-owned schema; the one review path for an exception is P0.7's, with `search_path` hardened as the research quotes (F11).

### What this design hands to P0.7's matrix

The research's fourth and fifth decision-relevant facts are not closed by a data model, and this design names them so that P0.7 and the security proof carry them: the write paths behave differently from the read paths, `RETURNING` and `ON CONFLICT` raise errors rather than filter, `COPY FROM` "is not supported for tables with row-level security" (F12), and `WITH CHECK` runs after `BEFORE` triggers, so the cross-tenant matrix must cover insert with conflict, update with returning, upsert against another tenant's key and bulk import; `app_role` is granted none of `pg_read_server_files`, `pg_write_server_files` or `pg_execute_server_program`, so no bulk load runs as the application (leak 15); and the covert channels the research lists, existence inference, plan shape and timing (leak 6), views and `SECURITY DEFINER` functions, triggers, dumps and replication, are recorded as what row-level security does not close, with the surrogate keys, `security_invoker` views, the trigger rule and the backup role's path as this design's part of the answer and the rest P0.7's. Row-level security is one layer; the baseline's tests and the application's authorization are the others.

### The migration tool and convention

Migrations are SQL files, reviewed as SQL, under `db/migrations/<module>/`, the layout the P0.2 design fixes; the tool is a candidate pending ADR-001's stack row (Technology candidates). The convention, which the Build stage's checklist already requires ("Migrations are expand-first, and each step states whether it can be reversed"):

- **Expand first.** A change adds before it changes: a new column or table arrives in one step, a backfill in a second, the switch of reads and writes in a third, and the removal of the old shape in a later package, so that the running version and the next both work against the same database.
- **One file, one statement of reversibility.** Each file's header states `reversible: yes` with the reversing statements, or `reversible: no` with the reason and the compensating migration.
- **The template is copied, not retyped.** A tenant-owned table's migration starts from the baseline template; the ownership tests catch a hand-typed omission.
- **Run twice in CI.** Against an empty database, and against a database holding the Tenant A and Tenant B fixtures, with the ownership tests after each run; a migration that passes only on an empty database has not been tested.
- **Run as the owner, never as the application.** The migration role's credential is issued per run, as the P0.12 design's inventory records.

### The ownership tests

A test suite of catalogue queries, run after every migration in CI and again by the independent verifier before the P0.12 check the manual's execution order puts first, one assertion each:

| # | Assertion | Catalogue it reads |
|---|---|---|
| T1 | Every table in a module schema, unless registered as platform-level, has `tenant_id` `NOT NULL` with a foreign key to `tenancy.tenant` | columns and constraints |
| T2 | Every such table has row-level security enabled and forced | the table's `relrowsecurity`, "True if table has row-level security enabled", and `relforcerowsecurity`, "True if row-level security (when enabled) will also apply to table owner" [G3] |
| T3 | Every such table has at least one permissive policy per command it grants, and an audit table has no update and no delete policy at all; owned by P0.7, which creates the policies, and reported as not yet applicable until it lands (the audit half is the P0.10 design's ask) | policies |
| T4 | Every such table is owned by `migration_role` | the table's owner |
| T5 | `app_role` is `NOSUPERUSER` and `NOBYPASSRLS`, owns no relation, and holds no `TRUNCATE`, `REFERENCES` or `TRIGGER` privilege on any tenant-owned table | roles and privileges |
| T6 | Every unique constraint and every foreign key on a tenant-owned table includes `tenant_id` | constraints |
| T7 | Every view over a tenant-owned table has `security_invoker = true`; no `SECURITY DEFINER` function exists in a tenant-owned schema; no function is marked `LEAKPROOF` except by a reviewed migration, since a leakproof function "may be evaluated before policy expressions" (leak 7) | views and functions |
| T8 | No `BEFORE ROW` trigger on a tenant-owned table references `tenant_id` in its function body | triggers |
| T9 | Every role but `backup_role` is `NOSUPERUSER` and `NOBYPASSRLS`, T5 extended to every role as the P0.7 design's leak 1 asks; `backup_role` holds `BYPASSRLS` and `SELECT` and no other privilege (the P0.7 design's ask) | roles and privileges |
| T10 | On the audit schema, `app_role` holds `SELECT` and `INSERT` only, `audit_writer` holds `INSERT` only, and no runtime role holds `UPDATE`, `DELETE`, `TRUNCATE` or `REFERENCES` (the P0.10 design's ask) | grants |

## Negative controls

Each control is seen failing before the protection exists and passing after; the verifier for any control that feeds the `BT-G1` matrix is not the implementer.

| # | Threat or defect | Condition | Expected denial or failure | Seen failing at |
|---|---|---|---|---|
| 1 | A tenantless table | A migration creates a table in a module schema without `tenant_id` | T1 fails, naming the table; the CI job fails | Before T1: the migration applies and the job is green |
| 2 | The application role can bypass | A migration grants `BYPASSRLS` to `app_role`, or makes it owner of one table | T4 or T5 fails; as `app_role`, a query on Tenant B's rows with Tenant A's key returns rows in the measurement before the fix | Before T4 and T5: the grant applies; Tenant B's rows are visible to Tenant A's key |
| 3 | The owner reads across tenants | As `migration_role`, with Tenant A's key set, select from `legal_entity` on a table enabled but not forced | Rows of both tenants are returned; T2 fails on the unforced table | Before forcing: both tenants' rows returned; after: only Tenant A's |
| 4 | A stale key on a pooled connection | Two transactions on the chosen pooler: the first sets the key session-level for Tenant A and ends; the second sets nothing and queries | The second transaction sees Tenant A's rows through the pooler's reuse; the measurement records it, and the transaction-scoped rule makes the second transaction see nothing | Before the rule: rows visible; the pooler and mode are named in the record |
| 5 | Existence inference through a unique constraint | A unique constraint on `legal_entity.registration_reference` without `tenant_id`; Tenant A inserts Tenant B's reference | The insert fails with a conflict that reveals the value exists; T6 fails on the constraint; with `tenant_id` in the constraint the insert succeeds in Tenant A | Before T6: the conflict leaks; the constraint is accepted |
| 6 | A view exposes every tenant | A view over `business_unit` created by the owner without `security_invoker` | Tenant A's key reads Tenant B's units through the view; T7 fails | Before T7: the view returns both tenants |
| 7 | A migration is not expand-first | One file drops the old column in the same step that switches reads to the new | The convention check fails the file for a drop in a switch step; the header lacks its reversibility line | Before the check: the file applies |
| 8 | A whole-table command escapes the filter | As `app_role`, `TRUNCATE legal_entity` | Refused for want of the privilege; T5 holds | Before the grant is withheld: the table is emptied for both tenants |

Controls 2, 3, 5, 6 and 8 feed the `BT-G1` matrix's cross-tenant rows and are run by a verifier who is not the implementer.

## Open questions and dependencies

1. **ADR-004 decides the isolation tier.** Waits on: [#105](https://github.com/bstBizEra/biztrust_guide/issues/105) on the contract map, behind the waiver (#92). `ASSUMED` meanwhile: the contract's proposal, shared PostgreSQL with a mandatory `tenant_id` and row-level security, forced, with a transaction-scoped key.
2. **ADR-015 decides the temporal representation.** Waits on: [#112](https://github.com/bstBizEra/biztrust_guide/issues/112). `ASSUMED` meanwhile: the baseline's columns as the domain model lists them, which are the bitemporal research's candidate A; a table that needs the two-range shape changes its columns under that ADR.
3. **Whether `tenant_id` is physically repeated on child rows.** `BIZTRUST-DATA-001`'s, as the domain model's section 6 says. `ASSUMED` meanwhile: repeated on every tenant-owned table, because a policy that "consider[s] only the current values in the row" is the research's "simplest and best-performing case" (F15) and a policy that joins to a parent is the research's leak 10.
4. **The pooler and its mode.** No ADR and no research; the documentation is silent (F8). Waits on: the map's Not yet specified item on hosting and environment, and the first pooled environment. `ASSUMED` meanwhile: a transaction-scoped key through `set_config(..., true)` regardless of pooler, and no pooled deployment before control 4's record exists for that pooler and mode.
5. **The organization link.** ADR-003 ([#104](https://github.com/bstBizEra/biztrust_guide/issues/104)) and P0.4 decide the mapping's lifecycle. `ASSUMED` meanwhile: one nullable, unique `identity_organization_id` column on `tenancy.tenant`, written only by P0.4's mapping and never by a request.
6. **Residency, retention and deletion.** ADR-019, `BLOCKED_BY_S01`. `ASSUMED` meanwhile: no retention or deletion rule is carried by the schema; the domain model's rule that deletion is a lifecycle operation stands, and a `closed` tenant status is a state, not a deletion.
7. **The migration tool.** ADR-001's stack row and the stack decision, which names two. `ASSUMED` meanwhile: either runs the same SQL files; the convention is written for files, not for a tool.
8. **The legal entities' real fields.** The authority profile and slice S01 (#93) say what a tenant's acting legal entity is. `ASSUMED` meanwhile: the two fixture entities carry invented names and references; nothing real enters the repository.

No item is `UNKNOWN_BLOCKING`: the design proceeds on its assumptions and each is reversible by the decision it names.
