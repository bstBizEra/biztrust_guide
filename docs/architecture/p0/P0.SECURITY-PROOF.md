## Scope and non-scope

**In scope.** The matrix `BT-G1` requires, row by row, and what makes a run of it a record rather than a report:

1. **The rows**: the ticket's list and the plan's seven lines, each mapped to the negative controls the landed designs already define, by design and control number, so that the proof adds no test of its own and every row is a test that exists.
2. **The row's shape**: for each row, the negative control, the evidence fields, and the verifier role, "who is not the implementer".
3. **The runner**: one suite that executes every row's controls in one run against one pinned revision and writes one manifest.
4. **The manifest**: the evidence binding of the manual's condition, "the run to a source revision, workflow, environment and tool versions", as a file under `evidence/` with a schema under `schemas/` and a validator that refuses a manifest that binds less.
5. **Independence**: how "executed by someone who did not implement it" is made mechanical, the verifier's identity in the manifest compared with the revision's authors, and what the runner refuses.
6. **The four conditions and the stop signals**: which the runner checks, which it reports, and which only a human can settle.

**Non-scope**, each with its owner:

- The controls themselves, their conditions and their failing baselines: the landed designs; this design names them and changes none.
- Recording the gate: the security risk owner, per the manual's section 05 and PLAN-001 section 12.1; the runner writes a manifest, never a gate record.
- Accepting ADR-002, ADR-003 and ADR-004: the accountable architecture owner "after the security lens", the manual's section 05; the proof reports the register's statuses on the run date and cannot proceed to a gate without them.
- Signing the manifest: no ADR row names a mechanism; the manifest's integrity in P0 is the repository's, a committed file under a protected branch, and a question below.
- The control-plane screen through which a human exercises tenant selection: P0.13 ([#185](https://github.com/bstBizEra/biztrust_guide/issues/185)); the manual says that epic "is not part of the matrix: the matrix proves the substrate".
- Insurance-domain data of any kind: the manual's stop signal; a row that needs a policy, a client or a premium has left the phase, and control 6 below refuses one.
- The pooler, the gateway and the observability stack: each unchosen, each a measurement in its design, each declared non-coverage here until chosen.

## Authorization-sequence step

The proof is the whole of the tenant authorization sequence in [`FLOWS.md`](../FLOWS.md) section 3 run against the two synthetic tenants, and the matrix beneath it made a suite: "every row is a test with an API expectation, a database expectation and an audit expectation, and all three are asserted", as the manual's section 04 reads.

| Sequence step | What the proof does there |
|---|---|
| Request API token with organization context; signed token | Rows 3 and 5 request tokens for the synthetic users and applications the P0.3 design's lab holds, valid and each kind of invalid |
| Verify signature, issuer, audience and expiry; resolve tenant, membership, scope and authority | Rows 3, 4 and 5 drive the P0.3 chain and the P0.4 resolver through every refusal the designs define, and row 1 through the one acceptance |
| Set trusted tenant context and execute command; RLS denies | Rows 2 and 6 drive the P0.7 policies through the real API and through the bypass path, on the two tenants' seed rows the P0.5 design's command made |
| Record action and outcome; record denied decision; record isolation denial | Rows 7, 9 and 11 read every row's record back through the P0.10 design's contract and assert the evidence contract's fields and what they never carry |

The manual's rule for the whole gate is the runner's first rule: "The suite is proven able to fail. The bypass test is committed in its red state first, and the pull request quotes both runs."

A row is passed when every control it names has been seen failing where its design says and passing on the pinned revision, with the row's evidence recorded; a control its design marks as a positive control or a measurement is recorded as that design records it and has no red state to be seen; a row with one protection missing, skipped or never seen red is failed, whatever the others did.

**The verifier role.** The role that executes every row is the security reviewer role, a role in PLAN-001 section 12.1's sense, "Whoever the Work Package names to it, human or agent", holding no authority of its own; the seat that observes the run and records the gate is the security risk owner, who "Records or accepts" `BT-G1`. Two names, two duties: whoever executes must not have implemented, which the manifest proves mechanically below; whoever records must be the seat, which no file can prove and the seat's own dated record does. Both are proposals until the seat register (#94) names people.

### The runner

One suite under `tests/security/`, beside the P0.7 design's bypass package, that runs the rows in the order above against one pinned revision, in an environment holding the lab Logto instance with the P0.3 design's synthetic objects, a database migrated at that revision with the P0.5 design's two tenants provisioned by its command, the P0.7 design's baseline database built by its harness, and the sink of the P0.11 design. What the runner does that the designs' own test suites do not:

- **Pins the revision.** A gate run, the kind that writes a manifest, refuses to start on a working tree with uncommitted changes or on a commit that is not on a protected branch's history (control 7), and writes the commit's identifier into the manifest before the first row; a pull-request run, which every pull request performs, runs the same rows on the pull request's head and writes no manifest.
- **Reads the matrix from a file.** `tests/security/matrix.yaml` lists the rows above, each with its controls by design and number and its evidence additions; a control the file names must exist as a test the runner can find by identifier, and a row the file omits, or a control it names that the suite lacks, fails the run before any row (control 1).
- **Requires the red run.** Row 6's baseline is a separate, earlier run the runner performs first on the harness's database, and the manifest carries its identifier and its red result; a run in which the baseline was green, skipped or absent is refused (control 2), which is the manual's stop signal, "the bypass test is absent, skipped or cannot be made to fail".
- **Reads back every record.** After each row, the P0.10 design's read contract under the row's tenant key, or the test-held elevation for platform events, gives the record the row expects; the runner asserts it and its fields, and counts decisions against records as that design's proof does (row 7).
- **Scans what it wrote.** The audit tables, the sink and the logs are scanned with the P0.12 design's scanner pattern classes and the token shape the P0.10 design's scrubber adds, after the last row (row 9), and the manifest's own artifacts are scanned before it is written (control 8).
- **Refuses domain data.** Before the first row, the module registry, the migrations and the seeds are searched for any table, row or fixture naming a policy, a client, a claim or a premium; a hit fails the run (control 6); the same rule is asked of the P0.2 design's migration lint for P0 (question 9), which is the manual's stop signal, "insurance-domain data on the substrate".
- **Writes one manifest and no gate.** The manifest is the run's only output; the runner has no path that writes to `badf/` or to the register.

### The manifest

A file under `evidence/security-proof/<run id>.json`, validated against `schemas/security-proof-manifest.json`, the P0.2 design's places for both; the validator is asked of the P0.2 design's "Validate records" job (question 9) so that a manifest that binds less than the condition requires cannot be merged:

| Field | Content | The condition it serves |
|---|---|---|
| `run_id`, `started_at`, `finished_at` | The run's identity and UTC times | AGENTS.md section 9, "execution time" |
| `source_revision`, `branch` | The pinned commit and the protected branch it is on | "bound to a source revision" |
| `workflow`, `workflow_run_id` | The workflow file and the run identifier, or the verifier's command line and host if run by hand, which the manifest says it was | "workflow" |
| `environment` | The environment's name and, for each component, its identity and version: PostgreSQL, Logto, the runtime, the pooler and gateway if any, the sink | "environment and tool versions" |
| `tool_versions` | The test runner's, the linters', the SDK's and the migration tool's versions | "tool versions" |
| `verifier` | The identity that executed: for a workflow run, the host's actor identity, taken by the runner and never typed; for a by-hand run, the identity the verifier names, which the manifest marks as declared and the seat confirms; and the role it held | "executed by someone who did not implement it" |
| `implementers` | The host identities that authored or merged the pull requests whose commits lie between the previous manifest's revision and this one, or since the platform repository's first commit when no manifest exists, read from the host's pull-request records so that they are the same kind of identity the workflow's actor is and never a free-text commit string | The same, mechanically |
| `baseline_run` | Row 6's red run: its identifier, its result and the database it ran on | The stop signal |
| `previous_run` | The identifier of the run this one reruns, if any, so that a flake is two manifests that name each other | Control 10 |
| `rows[]` | Per row: its controls by identifier, each control's exit status and artifact references, the row's evidence additions, the records read back with their hashes, and the row's verdict | "P0 negative-test evidence"; "an audit record for every row" |
| `counts` | Decision attempts by outcome against records and alerts, from row 7 | The P0.10 design's proof |
| `scans` | Each scan's target, patterns and result | Row 9; control 8 |
| `register` | The status of ADR-002, ADR-003 and ADR-004 as read from this guide's register, `docs/architecture/ADR_REGISTER.md`, at the guide commit the platform repository's `badf/` pins, which the P0.2 design carries there; the guide commit is recorded beside the statuses | The gate's third condition, reported and never supplied |
| `declared_coverage`, `declared_non_coverage` | What the run covered and what it did not, in the words of the designs' evidence contracts | AGENTS.md section 9 |

The validator refuses a manifest whose `verifier` appears in `implementers` (control 3), whose binding fields are missing or empty (control 4), whose `baseline_run` is absent or green (control 2), whose `rows[]` lacks one of the eleven rows the schema itself enumerates, so that a row dropped from the matrix file is still missing, or holds a row without a read-back record (controls 1 and 5), or whose artifacts match a scan pattern (control 8). It does not read the register's statuses as a pass or a fail: they are reported, and the gate's record is the seat's.

### Independence, mechanically

"The proof was run by the implementer" is the manual's fourth stop signal, and "A self-run proof is a claim". The design's test is the manifest's two fields: `verifier`, the host's actor identity for a workflow run, or a declared identity for a by-hand run that the seat must confirm; and `implementers`, the host identities behind the pull requests in the manifest's range, as the table defines them. Their intersection must be empty, and the validator refuses otherwise. What this cannot prove is that the verifier holds the role the Work Package named, which is the security risk owner's to see; the manual's row says the seat must have seen "The full matrix executed by someone other than the implementer, bound to a source revision, with an audit record for every row", and the manifest is what the seat sees.

Two further rules keep the run the verifier's own: the verifier runs from a clean checkout of the pinned revision in an environment the implementers cannot write to during the run, which is an operations matter this design assumes (question 3); and a rerun after a failure is a new run with a new manifest, never an edit of the old one, so that a flake is visible as two manifests (control 10).

## Evidence contract

A control run records, per [`AGENTS.md`](../../../AGENTS.md) section 9; a record missing a field is not evidence:

| Field | Content for the proof |
|---|---|
| Repository and commit SHA | The platform repository and the commit whose runner, matrix file, schema and validator ran; for the proof itself, the pinned revision under proof, which the manifest carries |
| Command or workflow identity | The workflow file and run identifier of the proof run, and of the baseline run |
| Execution time and environment | Start and end, environment name, and every component's identity and version as the manifest's `environment` and `tool_versions` list them |
| Exit status | Per row, per control within it, for the baseline run, for the validator and for each scan |
| Artifact or output reference | The manifest itself under `evidence/security-proof/`, the two runs' outputs it references, the read-back records with hashes, the scans' outputs, and for controls 1 to 8 the fixture and the refusal it produced |
| Verifier role | The security reviewer role executing, named in the manifest as `verifier`; the security risk owner as the seat that read the manifest, named in the seat's own gate record and not by the runner |
| Declared coverage | The rows run, the controls within them, the tenants, the tables and routes the run touched |
| Declared non-coverage | The pooler, the gateway and the observability stack until chosen; every measurement the designs mark as such; the ADRs' acceptance; the gate's record |
