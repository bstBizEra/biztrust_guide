## Scope and non-scope

**In scope.** Three things the manual's row asks for, and the rule that makes them checkable:

1. **Where secrets live and how the application reads them.** One store outside Git and outside the application's configuration files; one interface through which every process obtains a secret by name; a configuration model that separates configuration, which is versioned in the repository, from secrets, which never are.
2. **The rotation exercise**, run and recorded, for two credentials: the PostgreSQL application role's password and the Logto machine-to-machine client secret the API uses to call Logto's management interface. The exercise is a procedure with a measurement, not a statement.
3. **Least-privilege evidence per role and per environment**: the database roles the platform uses, what each may and may not do, and the proof that the application role cannot bypass row-level security; the Logto application's scopes; the CI workflow's permissions.
4. **What may never be in Git**, as a list a secret scanner can be held to, with the scanner seen failing a synthetic secret before the rule is trusted.

**Non-scope**, each with its owner:

- Tenant-scoped provider credentials, such as an insurer's or payment provider's API key held for one tenant: those carry `tenant_id` and belong to ADR-009's adapter boundary and the P1 and P2 designs that first need them; this design gives them a place in the inventory's classes and nothing more.
- Encryption of data at rest and key management for it: ADR-019 for what residency and retention require, and the P0.6 tenancy data model for where keys are referenced.
- Hosting, region and the choice between a self-hosted store and a cloud service: the map's fog item on hosting and ADR-019; this design is written so that either shape satisfies its interface.
- The repository's charter, CI skeleton and branch rules: P0.2's design; this design assumes them (section 8, question 6).
- Secret scanning as part of the P3 pipeline, DAST and penetration testing: the hub's security track and P3B.1; this design places one scanning gate at the repository boundary because P0 cannot wait for P3.
- User passwords and session secrets: Logto's, under ADR-002; the platform never stores a user credential.

## Authorization-sequence step

P0.12 is outside the tenant authorization sequence of [`FLOWS.md`](../FLOWS.md) section 3; it protects four of its steps:

| Sequence step | What P0.12 protects there |
|---|---|
| Organization token from Logto | The API's own machine-to-machine client secret, with which it calls Logto's management interface to read memberships and organizations; a leaked secret would let a caller impersonate the platform to Logto |
| API boundary, token verification | Nothing secret: signature verification uses Logto's public JSON Web Key Set. This design records that the verification keys are public so that no one stores them as secrets, and that the issuer and audience values are configuration, versioned in the repository |
| Trusted tenant context and row-level security in PostgreSQL | The application role's credential, and the least-privilege shape of that role: row-level security binds only if the role that sets the tenant context cannot bypass it. The role's password is the credential the rotation exercise rotates |
| Audit and observability | The credentials the audit sink and the telemetry collector accept; the store's own request log, which is the evidence that a secret was read by whom and when |

## Interfaces and data shapes

### The secret source

Every process obtains a secret through one interface, owned by the platform-configuration module, which no domain module may bypass:

```text
SecretSource
  get(name) -> { value, version, rotated_at, source }
  subscribe(name, handler)         handler runs when `version` changes
```

- `name` is a path in the inventory below, never a raw key of the store; the store's paths are the source's own configuration.
- `version` and `rotated_at` are what the store reports for the secret; they are logged, `value` never is.
- `source` names which store answered: the runtime store, or the local development file source described below. A process log line at start says which source is active, so a production process running on the local source is visible.
- Authority: any module inside the process may call `get`; nothing outside the process can. The process authenticates to the store with a per-environment, per-workload identity whose own bootstrap credential is the one exception handled under bootstrap material.
- The interface is the exit path: replacing the store is a new implementation of `SecretSource`, not a change to any consumer.

### Configuration versus secrets

| Kind | Where it lives | Example |
|---|---|---|
| Configuration | Versioned files in the repository, one per environment, plain text, reviewed like code | Logto issuer, audience, JSON Web Key Set URL; database host and name; telemetry endpoint |
| Secret reference | Inside configuration, as a name only | `secret://postgres/app-role`, `secret://logto/api-client` |
| Secret | The store; never in the repository, never in an environment file that is committed, never in a container image | The application role's password; the Logto client secret |

The configuration loader resolves every `secret://` reference through `SecretSource` at process start. A configuration value that looks like a secret, by the same patterns the scanner uses, fails the loader (negative control 3).

### The secret inventory

A versioned table in the repository, one row per secret, with no values. It is the list the rotation exercise and the least-privilege review are held to.

| Field | Meaning |
|---|---|
| `name` | The `secret://` path |
| `class` | `bootstrap`, `runtime`, `provider`, `ci` (below) |
| `environment` | One of the environments the platform runs in; a secret is never shared across two |
| `consumer` | The workload identity that may read it |
| `owner_role` | The role that rotates it and answers for it |
| `rotation_period` | The interval after which an unrotated secret is a finding |
| `last_rotated` | Reported by the store, not typed by hand; blank means never |
| `evidence_ref` | The most recent rotation exercise's evidence record |

The classes:

- **Bootstrap**: the one credential a workload needs before it can reach the store. Held outside the store by the deployment mechanism, never in Git, and listed here so that its rotation is also exercised.
- **Runtime**: what the platform needs to run: the application role, the Logto client, the audit and telemetry credentials.
- **Provider**: external counterparties' credentials, platform-level only in P0; tenant-scoped rows arrive with ADR-009's designs and carry `tenant_id`.
- **CI**: tokens the workflows use; issued to the workflow, least-privileged, short-lived where the platform supports it.

### Database roles

The roles PostgreSQL would hold, as the least-privilege shape P0.6 and P0.7 build on; the names are placeholders the P0.6 design may rename:

| Role | May | May not | Credential class |
|---|---|---|---|
| `app_role` | Connect; run the application's queries under row-level security; set the tenant context the application resolved | Own any table; bypass row-level security (`NOBYPASSRLS`); create or alter schema; read another environment's database | runtime, rotated by the exercise |
| `migration_role` | Own the schema; run reviewed migrations from CI | Serve application traffic; hold a long-lived credential in any process | ci, issued per migration run |
| `audit_writer` | Insert audit records | Update or delete them; read business tables | runtime |
| `store_root` | Rotate `app_role`'s credential on the store's behalf | Anything else; be used by a person | bootstrap, held by the store only |

The property the proof turns on is the second column of the first row: `app_role` has no path around row-level security, so the trusted tenant context is binding. P0.7's negative controls prove the policy; this design's control 2 proves the role.

### The rotation exercise

A procedure run against a synthetic environment with synthetic Tenant A and Tenant B data, recorded per section 6:

1. Read the secret's `version` and `rotated_at` through `SecretSource`; record them.
2. Trigger rotation at the store (for a Vault-shaped store, the rotate-role call the research documents; for a cloud store, its rotate call).
3. Read again; `version` must have changed and `rotated_at` advanced.
4. Measure, do not assume, what happened to open sessions: connections opened before the rotation, connections opened during the window, and the first connection after. The research records that no primary source states PostgreSQL's behaviour for existing sessions after a password change, so the exercise's record carries the observed behaviour with timestamps.
5. Confirm the process re-read the secret on the subscription and reconnected, and that no request failed for want of a credential, or record how many did and for how long.
6. Confirm the store's request log holds the read, the rotate and the re-read, attributed to the workload identity.

The same steps apply to the Logto client secret, with step 2 performed in Logto and step 4 measuring which tokens the token endpoint accepts before, during and after; the mechanics of rotating a Logto machine-to-machine secret are not in the research and are question 3.

### Environments

P0 needs three: a developer's machine, CI, and one shared development environment; the ladder P3A.1 adds later starts from them. Each has its own store namespace or instance, its own inventory rows and its own workload identities; a credential that opens two environments is a finding.

The developer's machine uses the local file source: an encrypted file the developer decrypts with a personal key, holding development-only secrets, named in the inventory with `environment = local`. A committed encrypted file is permitted; a committed plaintext secret is not, and the scanner treats the two differently by the file's declared format, not by guessing.

## Negative controls

Each control is seen failing before the protection exists and passing after; the verifier for any control that feeds the `BT-G1` matrix is not the implementer.

| # | Threat or defect | Condition | Expected denial or failure | Seen failing at |
|---|---|---|---|---|
| 1 | A secret reaches Git | A branch adds a file containing a synthetic credential in each of the scanner's pattern classes, plus one committed plaintext `.env` | The repository's scanning gate fails the check run and blocks merge; the encrypted local file in its declared format passes | Before the gate exists: the branch merges clean |
| 2 | The application role can escape row-level security | As `app_role`: `SET ROLE` to an owner, `ALTER TABLE`, a query with row-level security disabled on a protected table, `CREATE SCHEMA` | Every statement is refused by PostgreSQL; the refusals are logged | Before the role is shaped: at least one statement succeeds |
| 3 | A secret hides in configuration | A configuration file carries a value matching a secret pattern instead of a `secret://` reference | The loader refuses to start the process and names the key, not the value | Before the loader rule: the process starts |
| 4 | A rotation strands the platform | The exercise rotates `app_role`'s password while synthetic traffic runs against Tenant A and Tenant B | New connections succeed with the new credential; the process re-reads and reconnects; the observed failure window, if any, is recorded with its duration | Before subscription and reconnect exist: connections fail until restart |
| 5 | An old Logto client secret still works | The exercise rotates the client secret in Logto | The token endpoint refuses the old secret after rotation and accepts the new; tokens issued before rotation behave as measured and recorded | Before the exercise: unknown; the first run is the baseline |
| 6 | A secret is read without a record | The store's request log sink is made unavailable, then a read is attempted | The store refuses the read rather than serving it unlogged, for a store with that property; for a store without it, the design records the gap as a finding against the candidate | Before the audit device is enabled: the read succeeds silently |
| 7 | One credential opens two environments | The shared development environment's `app_role` credential is presented to the CI database | Refused | Before per-environment roles: accepted |

## Evidence contract

A rotation exercise or a control run records, per [`AGENTS.md`](../../AGENTS.md) section 9; a record missing a field is not evidence:

| Field | Content for P0.12 |
|---|---|
| Repository and commit SHA | The platform repository and the commit whose configuration and inventory the run used |
| Command or workflow identity | The workflow file and run identifier, or the procedure's step numbers for a manual exercise |
| Execution time and environment | Start and end, environment name, Node.js and PostgreSQL versions, the store's version |
| Exit status | Per control and per rotation step |
| Artifact or output reference | The store's request log extract for the run, the inventory row's `evidence_ref`, the measured session behaviour for control 4 with timestamps, and for control 1 the check run that failed |
| Verifier role | The named role that ran or observed the control; for controls 2 and 6, which feed the `BT-G1` matrix, not the implementer |
| Declared coverage | Which secrets, roles and environments the run covered |
| Declared non-coverage | Secrets and environments not covered, and any control whose baseline could not be seen failing |

## Technology candidates

The store is the one technology this epic turns on, and the ADR register has no row for it. Under the pack's rule a technology with no ADR row is not a candidate but a question, so this table names none and question 1 asks for the row. The research compared four options; they are listed as findings the ADR would decide between, with the exit path the research documents for each.

| Researched option | Rotation shape found | Audit shape found | Exit path found | Standing |
|---|---|---|---|---|
| HashiCorp Vault Community | Dynamic roles with leases; static roles rotated on a period or schedule | Every request logged, values hashed; refuses service when no audit device can write | Raft snapshot, usable by a Vault-compatible engine only | Not a candidate until an ADR row exists; BSL 1.1 licence clause to re-read if secrets management were ever offered to tenants |
| OpenBao | The same engine shape; `rotation_period` required, no cron schedule found | The same audit properties, plus an HTTP audit device | Raft snapshot, same wording | Not a candidate until an ADR row exists; MPL 2.0 |
| SOPS with age | Rotates the file's data key only; no database rotation | Optional decrypt log | Plaintext by decryption | Not a runtime store; a fit for bootstrap material and the local file source, pending the same ADR |
| AWS Secrets Manager with KMS | Rotation by Lambda; the only option whose documentation states that open connections are not dropped | CloudTrail events, including rotation events | Per-secret retrieval; no bulk export found | Not a candidate until an ADR row exists and ADR-019 answers residency |

Two further technologies this design needs have no ADR row and are questions, not candidates: the secret scanner behind control 1, and the local encrypted-file format behind the developer source. The application framework and package manager are ADR-001's candidates as the stack decision names them.

## Open questions and dependencies

1. **The secrets store has no ADR.** The register's twenty decisions do not include it, and the pack forbids naming a candidate without a row. Waits on: a new decision ticket on the [ARCH-001A map](https://github.com/bstBizEra/biztrust_guide/issues/91), which the map's charting decision 4 makes the contract map's to add, and which waits like the rest of that map on the waiver (#92). `ASSUMED` meanwhile: a Vault-shaped store, since Vault and OpenBao share the request-log, static-role and rotate-role shapes the exercise's steps name; the steps are written so that a cloud store satisfies them too.
2. **Residency.** Whether a cloud store may hold a Lao tenant's secrets is ADR-019's, `BLOCKED_BY_S01`. `ASSUMED` meanwhile: the store is self-hosted beside PostgreSQL, so the design carries no region.
3. **Logto client secret rotation.** The Logto research covers organizations and machine-to-machine roles, not how a client secret is rotated or whether two secrets can be valid at once. `UNVERIFIED`; waits on a research addition to #136's file or a new research ticket, resolvable by an agent from Logto's official documentation. `ASSUMED` meanwhile: a single secret per application, replaced rather than overlapped, so control 5 measures a cut-over.
4. **PostgreSQL session behaviour after a password change.** No primary source states it; the exercise measures it (control 4). Not blocking; the record is the answer.
5. **Hosting and environment.** The map's fog item; the three P0 environments are `ASSUMED` to run wherever the platform repository's CI and one shared development environment can reach a store.
6. **The repository layout.** P0.2's design is not landed. `ASSUMED`: a pnpm workspace with `.github/workflows/` as the manual's row places this epic, one configuration directory per environment, and the inventory as a versioned file beside them.
7. **The scanner and the local file format.** Both need an ADR row or a decision the accountable architecture owner records; `ASSUMED` meanwhile: a scanner with pattern classes for the credential types in the inventory, run as a required check, and an encrypted-file format whose decrypted content the same scanner can read.
8. **Who records the exercise.** The manual's monitor section proposes the security risk owner for `BT-G1`; the rotation exercise's verifier is a role named per Work Package below, and no seat is filled (#94).

No item is `UNKNOWN_BLOCKING`: the design proceeds on its assumptions and each is reversible by the decision it names.
