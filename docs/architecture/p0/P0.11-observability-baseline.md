## Scope and non-scope

**In scope.** The three signals every request emits, the identifiers that join them, and the proof that one request can be put back together from them:

1. **The identifiers and how they travel**: the W3C `trace-id` as the one identifier that crosses process boundaries, and the platform's request, tenant, correlation, causation, workflow and contract identifiers as attributes on every span and log record, since the research's first decision-relevant fact is that "the conventions leave no slot for them".
2. **The conventions adopted**: the stable HTTP and database span conventions and the resource attributes, by name and requirement level as the research tables them, and the platform's own attribute namespace.
3. **The log record**: the OpenTelemetry Logs data model's fields as the platform's structured log shape, with the tenant-safe attribute set and the rule for what never appears.
4. **The metrics**: the HTTP server duration histogram with exemplars, and three platform counters the landed designs already need.
5. **Sampling**: what is kept and by whose decision, and why the audit record and not the trace is the guaranteed evidence.
6. **What is forbidden**: the attributes no signal carries, from the specification's Opt-In posture and ARCH-001 section 15, and the two places they are enforced.
7. **The collector topology**: recorded as a question with the research's facts attached, since no ADR row names one.
8. **Database-side corroboration**: the request identifier carried into PostgreSQL's server log, answering the P0.10 design's question 4.
9. **The proof**: one request reconstructed end to end, as a test given only a request identifier.

**Non-scope**, each with its owner:

- The audit record, its integrity and its retention: the P0.10 design; telemetry is not evidence, and a trace that is sampled away leaves the record intact.
- Service-level objectives, alert routing, on-call and the telemetry floor at production scale: the Operate stage and P3D.1, which PLAN-001 says "scales" this baseline; this design fixes the signals and their joins, not the objectives.
- The HTTP conventions that assign the request identifier and continue `traceparent`: the P0.8 design; this design fixes what the signals carry of them.
- The event envelope's `traceparent`: the P0.9 design; a consumer's span continues the starting trace as that design fixes.
- The telemetry credential and endpoint: the P0.12 design's inventory and configuration rows.
- Security scanning and the pipeline's own telemetry: the hub's security track and P3's pipeline.
- The SDK, the collector and the backend as products: questions 1 to 3, pending an ADR row.
- The Operate floor's other levels: domain-level, "every material state transition, emitted as a business fact rather than inferred from logs", is the P0.9 design's events; integration-level, the outcome, latency and provider reference of every external call, is ADR-009 and P2's integration designs; financial, every posting, allocation and reversal, is P2's ledger under ADR-008; audit is the P0.10 design. This design places the request-level floor and the joins.
- The hub's minimum telemetry, [`index.html`](../../../index.html) section "Operations": "Security events and authorization denials" are the decision metric below and the P0.10 record; workflow backlog and retry health are the outbox gauge below and ADR-010's runtime; "Cost by tenant, product and environment" is not a signal attribute, since no metric carries a tenant here, and is derived from usage records by the Operate stage's cost management in P3.

## Authorization-sequence step

P0.11 implements no step of the tenant authorization sequence in [`FLOWS.md`](../FLOWS.md) section 3; it makes every step of it observable, and the manual's note is its reason: "so the proof run can be reconstructed from its own trace".

| Sequence step | What P0.11 does there |
|---|---|
| Protected request, validated edge request | The API's `SERVER` span starts or continues the trace the P0.8 design's middleware decided, with the request identifier, the route template and the contract version as attributes; a log record at the request's start carries the same `TraceId` and `SpanId` |
| Verify signature, issuer, audience and expiry; resolve tenant, membership, scope and authority | Each check is an `INTERNAL` span under the server span; a refusal leaves the span's status `Unset`, since a 4xx is not an error for a `SERVER` span, and sets the caller-facing code as `error.type`; the tenant attribute is set only once the P0.4 resolver has mapped the caller's own tenant, never from the route or a header |
| Set trusted tenant context and execute command | Every statement is a `CLIENT` span with the database conventions' attributes, the tenant attribute inherited from the request, and PostgreSQL's `application_name` carrying the request identifier so the server log corroborates the span |
| Record action and outcome; record denied decision | The P0.10 record's `trace_id` is the span's; the decision counter the P0.10 design defines is the metric below; a log record at the request's end carries the outcome, the status and the duration |

The proof's rule is the P0.10 design's: the record is the anchor, and telemetry is found from it. Given a request identifier, the record gives the trace identifier, the trace gives the spans, the spans give the log records and the metric exemplars, and nothing about the request has to be searched for by content.

## Interfaces and data shapes

### The identifiers and how they travel

| Identifier | Where it lives | Rule | Source |
|---|---|---|---|
| `trace-id` | `traceparent` on the request and the event; `SpanContext.TraceId`; `LogRecord.TraceId`; the exemplar's `trace_id`; the P0.10 record's `trace_id` | "the only identifier the specifications guarantee to propagate across process boundaries"; a valid incoming header is continued, an invalid one ignored and a new trace started, as the Propagators API requires that `Extract` "MUST NOT throw an exception and MUST NOT store a new value in the Context" | The research's section 3 and fact 1 [S1, S2, S3] |
| `span-id`, parent | `SpanContext.SpanId`; `LogRecord.SpanId` | "If SpanId is present TraceId SHOULD be also present" | [S12] |
| Request identifier | Attribute `biztrust.request.id` on every span and log record of the request; the P0.8 design's `X-Request-ID`; the P0.10 record's `request_id` | A BizTrust attribute, since the conventions leave no slot; set by the first middleware and inherited by every child span through the context | The research's fact 1 |
| Tenant identifier | Attribute `biztrust.tenant.id` on every span and log record after the P0.4 resolver has mapped it; the P0.9 design's `tenantid` | Opaque, never a name; set from the resolved tenant only; absent before resolution and on a denial that resolved none | The research's fact 3; ARCH-001 section 15 "cross-tenant information" |
| Correlation, causation, workflow | Attributes `biztrust.correlation.id`, `biztrust.causation.id`, `biztrust.workflow.id`, as the P0.10 record and the P0.9 envelope carry them | BizTrust attributes; never in Baggage on an untrusted hop, since the Baggage API is built so that entries can be cleared "To avoid sending any name/value pairs to an untrusted process" | The research's section 6 [S21] |
| Route template, contract version | Attributes `http.route` and `biztrust.contract.version` | The route template of the P0.8 design, "MUST be low cardinality; not the raw path"; the contract's `info.version` | [S4]; the P0.8 design |
| Service identity and revision | Resource attributes `service.name`, `service.namespace`, `service.instance.id`, `service.version`, `deployment.environment.name` | Required or recommended as the research tables them; `service.version` is the commit the P0.10 record carries as `source_revision`, "the convention's slot for a build or commit identifier" | The research's section 4.4 [S8, S9, S10] |

Two rules follow. The platform's own attributes live in one namespace, `biztrust.*`, listed in the shared observability package under `packages/observability/`, owned by the SRE role as the manual's persona for observability and set by the P0.8 design's middleware under the identity-access module's owner, with their type, meaning and the design that introduced each, so that a scan can allow-list them; and no signal carries an actor identifier at all: the actor is in the P0.10 record, found by the request identifier, because the research records that the conventions' identity attributes are "Development-stability and flagged as PII" and that even a pseudonymous one "is nonetheless linkable PII".

### The conventions adopted

The HTTP server span, the HTTP server metric and the database client span as the research tables them from the stable conventions [S4] to [S6], with the requirement levels as the conventions define them [S7]:

| Span or metric | Attributes the platform populates | Attributes the platform never populates |
|---|---|---|
| `SERVER` span, named `{method} {http.route}` | `http.request.method`, `url.path` with sensitive segments scrubbed, `url.scheme`, `http.response.status_code`, `http.route`, `error.type` on error, `server.address`, `server.port`, `client.address`, `user_agent.original` and `network.protocol.version`, the network facts the research lists as AU-3's "source of the event" and not personal data under ARCH-001 section 15's rule, subject to ADR-019 (question 3), and the `biztrust.*` attributes above | Every `http.request.header.<key>` and `http.response.header.<key>`, since "including all headers poses a security risk"; the body sizes; `url.query`, which the convention lists as Conditionally Required and this design departs from: the query's key names are recorded as `biztrust.query.keys` with no values, which is what the P0.4 design's control 7 needs to record a tenant carrier and what pagination needs to be seen, and no value is exported since a query may carry what a caller should not have sent |
| `http.server.request.duration` histogram, unit `s`, the convention's buckets | `http.request.method`, `url.scheme`, `http.response.status_code`, `http.route`, `error.type`, `network.protocol.version`, with an exemplar carrying `trace_id` and `span_id`, "the metric a P0.11 reconstruction joins to the trace" | `server.address`, `server.port`, `user_agent.synthetic.type`, the Opt-In set |
| `CLIENT` span per statement, named `{db.query.summary}` | `db.system.name`, `db.namespace`, `db.collection.name`, `db.operation.name`, `db.query.summary`, `db.query.text` for parameterized statements only, `db.response.status_code` and `error.type` on failure, `server.address`, the `biztrust.*` attributes inherited | `db.query.parameter.<key>`, which "SHOULD NOT be captured by default since values may contain PII or sensitive details"; `db.response.returned_rows`; any non-parameterized text, which the data-access layer the P0.7 design names as a candidate is written not to issue |
| `INTERNAL` spans for the P0.3 checks, the P0.4 resolution and each module command | The span name as the check's or command's name, `biztrust.error.code` on a refusal with the caller-facing code of the P0.8 design, never the audit reason code, which is the P0.10 record's and has another name so that the two are never confused | The token, any claim, any body |

Status follows the convention: a 4xx "is not an error for a SERVER span" and a 5xx "SHOULD set status `Error`"; a refusal of the P0.3 chain or the P0.4 resolver is therefore a span with status `Unset` and `error.type` set, which is why the research's table reads that on a span "success is inferred, not asserted", and why the outcome is asserted in the P0.10 record and not here.

### The log record

Structured logs are the OpenTelemetry Logs data model's records [S12], emitted through the Logs Bridge API the research reads the overview as recommending "when the application can be changed", so that each record carries `Timestamp`, `ObservedTimestamp`, `TraceId`, `SpanId`, `TraceFlags`, `SeverityText`, `SeverityNumber`, `Body`, the `Resource`, the `InstrumentationScope` and `Attributes`:

| Field | Rule |
|---|---|
| `TraceId`, `SpanId` | Set from the active span on every record emitted inside a request; a record with no active span, a job's or a startup line, carries neither and names its job in `biztrust.job.name` |
| `Body` | A short template with no interpolated identifier, so that a body is low-cardinality and searchable; every identifier is an attribute |
| `Attributes` | The `biztrust.*` set of the request and `error.type` on error; nothing else the allow-list does not name |
| `SeverityNumber` | The model's normalized range; `ERROR` and above only for a 5xx, a failed audit write, a failed outbox write or an unhandled exception; a refusal is `INFO`, since a denial is the system working |
| `log.record.uid` | A ULID per record, the convention's Opt-In slot the platform opts into, so that the reconstruction can order and deduplicate records |

What the log never says is the same as what the P0.10 record never says, and a scrubber with the same patterns and a different action, replacement and a count in telemetry where refusal would lose a signal, refusal in the record where loss would lose evidence, keeps it out: no token, secret, body, header value, query string, name, email or document, and no value of another tenant.

### The metrics

Three platform metrics beside the HTTP histogram, each with the attributes the landed designs already count by:

| Metric | Kind | Attributes | Source of the need |
|---|---|---|---|
| `biztrust.decision.count` | Counter | `outcome` (`allow`, `deny`, `error`), `biztrust.error.code` for a deny, the caller-facing code and never the audit reason | The P0.10 design's counter, which "counts every decision attempt by the outcome it answered"; the metric exports that counter's value and that design's proof reads the counter directly, so its acceptance does not wait on this package |
| `biztrust.audit.write_failure.count` | Counter | `table` | The P0.10 design's fail-closed alert |
| `biztrust.outbox.backlog` | Gauge, per source | `source` | The P0.9 design's relay alert, which raises FLOWS section 16's "Retain outbox and alert on backlog" |

No metric carries a tenant attribute: a per-tenant series is a cardinality and a cross-tenant disclosure the research's fact 3 warns against, and a per-tenant question is answered from the audit record or the outbox table, not from a metric.

### Sampling

| Rule | Basis |
|---|---|
| The API decides its own sampling and never adopts an untrusted caller's `sampled` flag, continuing the caller's `trace-id` and `parent-id` but setting the flag by its own policy | The Recommendation's security section as the research reads it: a public API that continues any incoming sampled trace can be overwhelmed with tracing overhead, so vendors keep "checks and balances" against such callers [S1]; the rule is a duty this design adds to the P0.8 design's middleware, which fixes only the valid and invalid cases, and asks of that design's next version (question 7) |
| In every P0 environment, the lab, the proof run and the tests, the sampling rate is one: every span is kept, so that the proof run "can be reconstructed from its own trace" | The manual's ordering note |
| In production the rate is P3D.1's and the Operate stage's to set; whatever it is, an unsampled request keeps its log records and its audit record, which is why the record and not the trace is the guaranteed evidence | The research's field 3: "an unsampled request has logs and audit only"; the P0.10 design |
| Tail-based sampling, keeping every trace that ended in error, is `UNVERIFIED` as a collector capability, since the research records the deployment pages returned 404 and makes no statement on it | The research's unverified items |

### What is forbidden, and where it is enforced

The list, from the specification's Opt-In posture the research reads and ARCH-001 section 15: request and response bodies, which "are not attributes at all"; every header, which is Opt-In and never opted into; `url.query` and `url.full`'s credentials; `db.query.parameter.<key>`; any actor identifier, name, email or document; any token, secret or inventory name of the P0.12 design; any identifier of a tenant other than the request's own; and any `biztrust.*` attribute the package's list does not name.

Two enforcement points, since the research's fourth fact is that the collector's redaction "is Beta for traces and Alpha for logs and metrics, so P0.11 should treat it as defence in depth behind application-side scrubbing":

1. **The application**, first: the instrumentation is configured with no header capture and no query capture, the `biztrust.*` attributes pass an allow-list in the shared package before a span or record is exported, and the P0.12 design's log scan and the P0.10 design's scrubber patterns run over every attribute value; a value that matches is replaced by `REDACTED`, the convention's own token, and counted (control 7).
2. **The collector**, second, if one exists: the `redaction` processor with `allowed_keys` equal to the package's list and `blocked_values` equal to the scan's patterns, as the research records the processor supports, ordered first in each pipeline since "The order of the processors in a pipeline determines the order of the processing operations"; the second of the two points, a question until an ADR row exists (question 2), and a measurement of what it catches that the application missed (control 10).

### Database-side corroboration

The P0.10 design's question 4 asks whether PostgreSQL's own log corroborates a record. This design's answer: the API sets `application_name` on each transaction to the service name and the request identifier, `<service>:<request id>`, through the same transaction-scoped `set_config` the P0.6 design uses for the tenant key, whose third argument set to true means "the new value will only apply during the current transaction" [P2], and the server's `log_line_prefix` carries `%a`, the "Application name" escape [P1]. The parameter "can be any string of less than `NAMEDATALEN` characters (64 characters in a standard build)" and "Only printable ASCII characters may be used" [P1], which a service name of a few characters and a UUID satisfy. A server log line then names the request whose session wrote it, which the research records as "the only conventional slot for carrying an application-side identifier into the server log" [S27]. Which lines the server writes is the platform's setting: `log_statement` stays at its default, `none`, and `log_min_duration_statement` at its default, "`-1` (the default) disables logging statement durations" [P1], because "Logged statements might reveal sensitive data and even contain plaintext passwords" [P1] and the Operate stage forbids sensitive data in telemetry; a successful statement therefore writes no line. What is logged is the statement that fails: `log_min_error_statement` at its default `ERROR` means "statements causing errors, log messages, fatal errors, or panics will be logged", and `log_parameter_max_length_on_error` at its default, "Zero (the default) disables including bind parameters in error messages" [P1], keeps the bound values out. The corroboration is therefore of errors, which is where it matters: the P0.7 design's isolation denial is a policy error the server logs with `%a` naming the request (control 9), and a request that fails nothing leaves the server silent, which the reconstruction records as such. pgAudit is not adopted: the research records that it "is best-effort and not transactional" and "It is not possible to reliably audit superusers with pgAudit", so it would corroborate and not evidence, and it is P3's question (question 5).

### The proof

A test in `tests/observability/`, given a request identifier and nothing else, reconstructs the request from four sources and asserts the joins; the request is the P0.4 design's control 4, Tenant A's token on Tenant B's route, chosen because it exercises the chain, the resolver, a denial and its record without touching a business row:

1. From the request identifier, the P0.10 record in `audit.decision` under Tenant A's key, since the mismatch is recorded under the caller's own tenant, through the read contract as the P0.10 design reads that table: `trace_id`, `outcome`, `reason_code`, `route`.
2. From `trace_id`, the trace: one `SERVER` span with `biztrust.request.id` equal to the identifier, `http.route` equal to the record's `route`, `error.type` equal to the caller-facing code, and its `INTERNAL` children in order, the chain's checks then the resolver, the last with `error.type` set; `CLIENT` spans for the resolver's reads of the tenancy and membership tables and for the audit record's own transaction, each with `db.collection.name` naming one of those tables, and none naming a business table, which is the record's "no business query" made visible from the trace.
3. From `trace_id`, the log records: every record of the request carries it, the first at the request's start and the last at its end, ordered by `log.record.uid`, none carrying an attribute outside the allow-list.
4. From the histogram, an exemplar whose `trace_id` is the trace's, in the bucket the span's duration falls in; the proof runs its request alone in a quiet lab, since which measurements a reservoir keeps under load is `UNVERIFIED` and question 11's measurement.
5. From the server log, no line for the chosen request, since none of its statements failed and statement logging is off; the corroboration of a request that does fail a statement is control 9's, run beside the proof.

The test fails if any join is missing, if any attribute is outside the allow-list, or if any value matches the scan's patterns. The manual's row is the test's acceptance: "One request reconstructable across all three signals".

## Evidence contract

A control run records, per [`AGENTS.md`](../../../AGENTS.md) section 9; a record missing a field is not evidence:

| Field | Content for P0.11 |
|---|---|
| Repository and commit SHA | The platform repository and the commit whose instrumentation, allow-list, scrubber and reconstruction test ran; the same value the signals carry as `service.version` |
| Command or workflow identity | The workflow file and run identifier for the observability test job |
| Execution time and environment | Start and end, environment name, runtime versions, the SDK's and, if any, the collector's versions, PostgreSQL version and its `log_line_prefix` |
| Exit status | Per control and for the reconstruction |
| Artifact or output reference | The reconstruction's four sources for the chosen request, the spans, records and exemplar with values as exported, the server log lines for control 9, the sink scans for controls 3 to 7 with the patterns used, the scrubber's counter, and the collector's output for control 10 if it ran |
| Verifier role | The named role that ran or observed each control, not the implementer; the security reviewer role for controls 3 to 8; the SRE role for controls 1, 2 and 9 and the reconstruction |
| Declared coverage | Which routes, signals, attributes and patterns the run covered |
| Declared non-coverage | The collector and the backend, production sampling, tail-based sampling, pgAudit, and telemetry retention |

## Technology candidates

| Candidate | Candidate for | ADR and register status | Research or source | Exit path if rejected after use |
|---|---|---|---|---|
| W3C Trace Context, `traceparent` and `tracestate`, as the trace propagation | The identifier that crosses process boundaries | ADR-005, `DRAFT_REQUIRED`, under which ARCH-001 section 11 places it | The research's section 3 [S1] | Another propagation format behind the same middleware; the `biztrust.*` attributes and the record's `trace_id` column are unchanged |

Five things are not candidates.
