## Scope and non-scope

**In scope.** The shape every HTTP contract of the platform takes, and the check that refuses one that departs from it:

1. **The OpenAPI version and layout**: the version pinned, the four family documents and the shared components the contract names, and the one place the version changes.
2. **The canonical rules**, each made concrete: the base URI and the tenant segment, the bearer token, `X-Request-ID`, `traceparent`, `Idempotency-Key`, `ETag` and `If-Match`, and the two content types.
3. **Authority and provenance in every resource**: the component every representation carries, mirroring the P0.6 design's baseline columns, and the rule that no representation asserts an authority it cannot reference.
4. **The error shape**: problem details under RFC 9457, with the extension members the platform adds and the rule about what `detail` never says.
5. **Versioning and the breaking-change policy**: the path version, what may change within it, how a change is classified, and how deprecation is carried.
6. **The lint ruleset and the CI step**: the rules a contract must pass, the tool that runs them, and the deliberately broken contracts that prove the step can fail.

**Non-scope**, each with its owner:

- What a token must contain and how it is validated: the P0.3 design; this design fixes only that every route declares the bearer scheme and its scopes.
- Which tenant a request is about and how a mismatch is refused: the P0.4 design; this design fixes the segment's place in the path and the contract rule that no request body carries `tenant_id`, which that design assumed of this one.
- Event contracts, the AsyncAPI baseline and the CloudEvents envelope: P0.9 ([#145](https://github.com/bstBizEra/biztrust_guide/issues/145)).
- Traces, logs and metrics, and what `traceparent` joins: P0.11 ([#146](https://github.com/bstBizEra/biztrust_guide/issues/146)); this design fixes only that the header is accepted, propagated and echoed as the research's section 3 reads the Recommendation.
- The gateway, its policies and the derived contract it would import: no ADR row names a gateway, so it stays the question the P0.3 design left on the map (this design's question 3).
- The resources themselves, parties, clients, risks and the rest of the contract's representative list: P1's designs; P0's contract carries the tenancy, identity and audit routes the P0 designs need and no business resource.
- The money, date and timestamp representations beyond the baseline table's one line each: ADR-008, ADR-014 and ADR-015 (question 10).

## Authorization-sequence step

P0.8 implements no step of the tenant authorization sequence in [`FLOWS.md`](../FLOWS.md) section 3; it gives the sequence's requests and refusals their shape, and the manual's note is that the contract conventions are "Independent of the security chain".

| Sequence step | What P0.8 does there |
|---|---|
| Protected request, validated edge request | Every request carries the bearer token in `Authorization`, an `X-Request-ID` the API issues when the caller sent none, and a `traceparent` the API continues or starts; the route names the tenant in its path and nowhere else |
| Deny with problem details | Every refusal of the P0.3 chain and the P0.4 resolver, and every other error, is an `application/problem+json` document of the shape below, with the code the refusing design gives the caller and never the token or another tenant's data |
| Set trusted tenant context and execute command | A mutating command carries `Idempotency-Key` and, on an existing resource, `If-Match`; the contract declares both, and the API refuses a documented mutation that lacks them before any business code runs |

The contract's sentence, its section 8, is the rule for identifiers: "An organization or tenant identifier in a URL, header, query string or request body is requested context only. It must match the authenticated and authorized context."

## Interfaces and data shapes

### The version and the layout

The `openapi` field of every document is `3.2.0`, the version ARCH-001 section 11 proposes and ADR-005 decides. The research records that 3.2.0 is published, Appendix A dated `2025-09-19`, that `latest.html` resolves to it, and that the OAI states a 3.1 document "will work without modification after updating the version number"; the research's fifth building block is the rule this design adopts: pin `openapi: 3.2.0`, and treat the field as "a contract property changed only by ADR". What 3.2 costs today is in the research's tool table: Redocly CLI states support, Spectral has no `oas3_2` format, openapi-generator states 3.1 as beta, and no gateway checked states 3.2, which is why the gateway artefact is a question and not a layout item.

The layout is ARCH-001 section 11's tree, under the `openapi/` directory the P0.2 design reserves:

```text
openapi/
├── biztrust-insurance-api.yaml     P1 and later
├── biztrust-payment-api.yaml       P2 and later
├── biztrust-partner-api.yaml       P2 and later
├── biztrust-admin-api.yaml         P0: the tenancy, identity and audit routes the P0 designs need
├── components/
│   ├── common.yaml                 Provenance, Authority, identifiers, the standard headers and parameters
│   ├── errors.yaml                 the problem schema, the problem types, the error responses
│   ├── money.yaml                  the baseline's decimal string and currency code
│   ├── pagination.yaml             the cursor page
│   └── insurance.yaml              P1 and later
└── fixtures/                       the deliberately broken contracts, one per lint rule
```

Every document carries `$self`, which 3.2 adds "to allow users to define the base URI of the document, used to resolve relative references", and the research's sixth building block reads the multi-document guidance as supporting this layout "provided every document has an OpenAPI Object or Schema Object at its root". `info.version` is the contract version the P0.10 design's record carries as `contract_version`, in the form `major.minor.patch`, with `major` equal to the path version below.

### The canonical rules

| Rule, from ARCH-001 section 11 | Shape in the contract | Where it is enforced |
|---|---|---|
| Base URI `/api/v1` | Every path begins `/api/v1`; a tenant route continues `/tenants/{tenant_id}/`, the segment the P0.4 design assumed of this design and compares against the token's mapped tenant; a route with no tenant segment is platform-level and P0 declares only the provisioning and platform-audit routes there | The lint: a path outside `/api/v1`, or a route the document marks tenant-level without the segment, fails |
| `Authorization: Bearer` | One security scheme, `bearerToken`, `http` with `scheme: bearer`, applied to every operation with the operation's scopes; no operation is unsecured | The lint: an operation without `security` fails; the P0.3 chain refuses at runtime |
| `X-Request-ID` | A request header the caller may send and the API always returns; the API issues one, a UUID version 7, when none was sent, and records the caller's under `client_request_id` when one was, never trusting it as its own; the value is the P0.10 record's `request_id` and the problem document's `instance` | The API's first middleware, in the API entry point under `services/` of the P0.2 design's tree, owned by the identity-access module's owner role with the P0.3 chain it precedes; the contract's common parameter and response header |
| `traceparent` | Accepted on every request and continued or started as the research's section 3 reads the W3C Recommendation: a valid header is propagated with `parent-id` set to the current operation; an invalid one is ignored and a new trace started; no personal or sensitive value is ever placed in `traceparent` or `tracestate`; the `trace-id` is the P0.10 record's `trace_id` | The API's first middleware; P0.11 owns what the trace carries |
| `Idempotency-Key` | Below | Below |
| `ETag` and `If-Match` | Below | Below |
| Route template | Every operation's path as the document declares it, with `{tenant_id}` and every other parameter as a template; it is what the P0.10 design's record carries as `route`, never the raw path or query | The lint; the middleware records the matched template |
| `application/json` | The one success content type; every 2xx with a body declares it | The lint |
| `application/problem+json` | The one error content type; every 4xx and 5xx declares it with the problem schema | The lint; control 8 at runtime |
| Identifiers, dates, timestamps, money | As the baseline table reads: identifiers as strings, UUID version 7 "instead of UUIDv1 and UUIDv6 if possible" [R4] where an ordered identifier helps and the P0.6 design's uuid otherwise; dates `YYYY-MM-DD`; timestamps RFC 3339 in UTC; money as a decimal string with an ISO currency code, the shape `components/money.yaml` holds | The schemas' `format` and `pattern` |

### Authority and provenance in every resource

Every resource representation the contract returns embeds two component objects from `components/common.yaml`, so that ARCH-001 section 15's reconstruction fields and the domain model's invariant for a distribution product version, "Cannot claim insurer authority that its source does not grant", read here as the rule every representation follows, are the same shape everywhere:

```text
Provenance {
  aggregate_version   integer          the P0.6 design's aggregate_version; the ETag below
  recorded_at         RFC 3339 UTC     record time, set by the database
  created_at, updated_at  RFC 3339 UTC  the baseline's audit timestamps
  created_by, updated_by  identifier   the resolved actor, never a name
  legal_entity_id     identifier | null   the acting legal entity, where the resource has one
  effective_from, effective_to, effective_timezone   where the fact has valid time; ADR-015's representation
  supersedes_id       identifier | null
  source_system, external_reference   string | null   ARCH-001 section 15's fields, from the aggregate's own table where a fact originated outside BizTrust, which P1's designs add to their tables; null in P0
  contract_version    string           the info.version the representation was produced under, from the API and not the row
}
Authority {
  authority_profile_ref   identifier | null   an accepted profile's identifier, never its text
  authority_status        one of: none, referenced   P0 returns none on every resource, since no authoritative act exists
}
```

Three rules: `tenant_id` appears in a representation as a read-only field, so that a caller can see which tenant a resource belongs to, and never in a request body, which fails contract validation before the P0.4 resolver runs, as that design assumed of this one; `Provenance` is read-only, written by the platform and refused in a request body; and `Authority.authority_status` is `none` until ADR-013 names what `referenced` requires, so that no P0 representation can be read as an authoritative act.

### `Idempotency-Key`

The convention follows the shape of the IETF HTTPAPI working group's draft, "The Idempotency-Key HTTP Header Field", which on the date checked was an expired Internet-Draft, revision 07 of 2025-10-15, and is cited as the shape the platform adopts and not as a standard [R3]; what is the draft's and what is BizTrust's is kept apart:

| Rule | Source |
|---|---|
| Every operation the contract marks as a mutation, `POST` and `PATCH` on P0's routes and every command the FLOWS record's template describes, declares the `Idempotency-Key` request header as required; a request without it is refused with a problem of type `idempotency_key_missing` and status 400 | The draft: "If the Idempotency-Key request header is missing for a documented idempotent operation requiring this header, the resource SHOULD reply with an HTTP 400 status code." [R3, 2.7] |
| The key is the caller's, "a unique value generated by the client which the resource uses to recognize subsequent retries of the same request" [R3, 2]; the API stores it with a fingerprint of the request body and the response it produced | The draft, section 2 |
| Its scope is the tenant, the route and the key together, so that two tenants' keys never meet; the scope's inclusion of `tenant_id` is the position the P0.7 design assumed of ADR-012 (its question 3) | BizTrust's; ADR-012 decides (question 2) |
| A retry with the same key and the same fingerprint returns the stored response, "the result of the previously completed operation, success or an error" [R3, 2.6], with a response header `Idempotent-Replayed: true` and no second write | The draft's SHOULD; the replay header is BizTrust's |
| A retry with the same key and a different fingerprint is refused with type `idempotency_key_reused` and status 422 | The draft: "If there is an attempt to reuse an idempotency key with a different request payload, the resource SHOULD reply with a HTTP 422 status code." [R3, 2.7] |
| A retry while the original is still running is refused with type `request_in_flight` and status 409 | The draft: "The request was retried before the original request completed. The resource SHOULD respond with a resource conflict error." [R3, 2.6] |
| The key and its stored response are kept for a period ADR-012 decides; the draft allows that "The resource MAY require time based idempotency keys to be able to purge or delete a key upon its expiry" [R3, 2.3] | ADR-012 (question 2) |

The FLOWS record's template asks every transition for "Scope, key and replay response"; the three rows above are the answer every P0 command gives, and a later command that needs a different scope says so in its own row.

### `ETag` and `If-Match`

Every representation of a mutable resource carries an `ETag` whose value is the resource's `aggregate_version`, an entity tag being "an opaque validator for differentiating between multiple representations of the same resource" [R2, 8.8.3], quoted as a string the caller returns unchanged. Every `PATCH`, `PUT` and `DELETE` on an existing resource declares `If-Match` as required, the field RFC 9110 gives a conditional request for "thereby preventing the 'lost update' problem" [R2, 13.1.1]; a request whose `If-Match` does not equal the current version is refused with type `version_mismatch` and status 412, which "indicates that one or more conditions given in the request header fields evaluated to false when tested on the server" [R2, 15.5.13]; a request without `If-Match` on such a route is refused with type `precondition_missing` and the status question 7 assumes. This is the FLOWS template's "Expected version / `If-Match` behavior" row, answered once for every P0 command.

### The error shape

Every 4xx and 5xx response is `application/problem+json` [R1], with RFC 9457's five members and the platform's extension members, which "Clients consuming problem details MUST ignore any such extensions that they don't recognize" [R1, 3.2] lets the contract add:

```text
Problem {
  type       URI, https://biztrust.example/problems/<code>; "When this member is not present, its value is assumed to be 'about:blank'" [R1, 3.1], so it is always present, as are the other four
  status     the HTTP status, "the HTTP status code ... generated by the origin server for this occurrence of the problem" [R1, 3.1]
  title      "a short, human-readable summary of the problem type" [R1, 3.1]; one per type, from errors.yaml
  detail     "a human-readable explanation specific to this occurrence of the problem" [R1, 3.1]; what it never says is below
  instance   urn:uuid:<X-Request-ID>, "a URI reference that identifies the specific occurrence of the problem" [R1, 3.1]
  code       extension: the caller-facing code, the last segment of type, from errors.yaml
  request_id, trace_id   extensions: the same identifiers the P0.10 record carries, so that a caller's report finds the record
  errors[]   extension, for validation problems only: { pointer, code } per failed field, never the value that failed
}
```

The codes in `errors.yaml` are the caller-facing ones the landed designs fix: the P0.3 chain's codes, which "name the check and never the token"; the P0.4 design's one code for its three denials, `tenant_denied`, since the specific reason "goes to the audit record; the caller sees one denial"; the P0.7 design's isolation denial mapped to the same denial the application gives; and this design's `idempotency_key_missing`, `idempotency_key_reused`, `request_in_flight`, `version_mismatch`, `precondition_missing`, `validation_failed`. A caller-facing code is not an audit reason code: the P0.10 design's registry holds the reasons, and the mapping from reason to caller-facing code is the refusing design's, written in `errors.yaml` beside the type. The refusals this design introduces, and the replay of control 6, are decisions the P0.10 design's registry does not yet list, and its writer "refuses the record" for an unlisted code; this design asks that design's next version to add `idempotency_key_missing`, `idempotency_key_reused`, `request_in_flight`, `version_mismatch`, `precondition_missing`, `validation_failed` and `replayed` as reason codes with this design as their owner (question 11). All five of RFC 9457's members are present on every problem document; `detail` is never empty.

**What `detail` never says.** RFC 9457's security consideration is the rule: "Risks include leaking information that can be exploited to compromise the system, access to the system, or the privacy of users of the system." [R1, 5]. No problem document carries a token, a secret, a stack trace, a query, a file path, another tenant's identifier or data, or the value of a field that failed validation; and, as the RFC reads it, `detail` "ought to focus on helping the client correct the problem, rather than giving debugging information" [R1, 3.1]. The framework's own error pages and default JSON errors are replaced for every status, so that no path answers outside the shape (control 8).

### Versioning and the breaking-change policy

| Rule | Basis |
|---|---|
| The path version, `/api/v1`, is the major version; a breaking change ships only under a new path version, and two versions are served together from the older one's deprecation to its `x-biztrust-sunset` date, the period between them being ADR-005's to fix (question 1) | ARCH-001 section 11's base URI |
| Within a version, additive change only: a new optional field, a new operation, a new enum value the contract marks as extensible; the classification is mechanical, `oasdiff breaking <base> <head>` in CI fails the pull request on what oasdiff reports as breaking, which the research's fourth building block records as the one tool checked that "states it diffs 3.2 constructs" and whose severities are "derived from a single reviewed model" | The research's building block 4 |
| A severity the team disputes is pinned in the repository with `--severity-levels`, by a pull request that says why, never by a label on the pull request | The research's building block 4; the P0.2 design's proposal that no override label exists |
| Deprecation is carried twice: `deprecated: true` on the operation, parameter or security scheme, the native marker 3.2 carries, and an extension `x-biztrust-sunset` with an RFC 3339 date, because the research records that AWS API Gateway drops `deprecated` on import and Azure API Management drops `x-` extensions, so the policy is enforced in CI and not in a gateway | The research's building blocks 1 and 2 |
| Extensions are `x-biztrust-*` only, listed in `components/common.yaml` with their meaning: `x-biztrust-stability` (`experimental`, `stable`), `x-biztrust-sunset`, `x-biztrust-tenant-level` (`tenant`, `platform`); the lint refuses any other `x-` key | The specification's rule the research quotes: "The field name MUST begin with `x-`" and `x-oai-` and `x-oas-` are reserved |
| A contract for a gateway, if one is ever chosen, is a derived artefact produced by an Overlay, never the source edited by hand, since no gateway checked states 3.2 | The research's building block 3 and decision-relevant fact 5; question 3 |

### The lint ruleset and the CI step

The linter runs the tool's own rules for OpenAPI 3.2 and a BizTrust ruleset, L1 to L9 each with a fixture that breaks it, and L10 proven by a pull request rather than a fixture, since a file in a fixtures directory has no base to diff (control 2). The tool is a candidate below; the rules are this design's, and any linter that can express them serves:

| # | Rule | What it refuses |
|---|---|---|
| L1 | `openapi: 3.2.0` and `$self` on every document | Another version; a document without `$self` |
| L2 | Every path under `/api/v1`; every operation marked `x-biztrust-tenant-level: tenant` has `{tenant_id}` as its first segment after `/api/v1/tenants/` | A path outside the base; a tenant route without the segment |
| L3 | Every operation has `security` naming `bearerToken` with at least one scope | An unsecured operation |
| L4 | No request body schema declares a property named `tenant_id`, `Provenance` or any of its fields, and every request body schema closes itself with `additionalProperties: false`, so that an undeclared field fails validation; no operation declares a query or header parameter named `tenant_id`, which the P0.4 design reads only to record | A body that could carry a tenant or write provenance; an open schema; a tenant carrier in the query or a header |
| L5 | Every resource response schema includes `Provenance` and `Authority` | A representation without them |
| L6 | Every `POST` and `PATCH` declares `Idempotency-Key` required; every `PATCH`, `PUT` and `DELETE` on a resource path declares `If-Match` required, and every success response that carries a representation returns `ETag` | A mutation without the headers |
| L7 | Every 4xx and 5xx response is `application/problem+json` with the `Problem` schema; every 2xx with a body is `application/json` | Another content type; an error without the schema |
| L8 | Every operation has an `operationId`, a `summary` and a tag whose `kind` the document's tag list declares | An unnamed or untagged operation |
| L9 | Only `x-biztrust-*` extensions, each listed in `common.yaml` | Any other `x-` key |
| L10 | `oasdiff breaking` against the base branch reports nothing, or the severity file pins the report | A breaking change within a version |

The CI step is one job, "Contract lint", that this design asks the P0.2 design's next version to add to its skeleton after "Typecheck and lint" and before "Boundary check", running L1 to L9 over `openapi/` and L10 against the pull request's base, the job owned by the data reviewer role as the P0.2 design's migration lint is; and one more run of the same job over `openapi/fixtures/`, expecting a failure per fixture, so that a green lint on the fixtures is itself a failure (control 1). The manual's row is the step's acceptance: "a deliberately broken contract fails CI".

## Negative controls

Each control is seen failing before the protection exists and passing after; the verifier is not the implementer. The environment holds the P0 admin document with the tenancy routes, the fixtures, and the synthetic tenants.

| # | Threat or defect | Condition | Expected denial or failure | Seen failing at |
|---|---|---|---|---|
| 1 | The broken contract passes | The fixtures run under the lint job; then a fixture is edited to pass | Each fixture fails its rule by name; the edited fixture makes the fixture run itself fail, since a passing fixture is a defect | Before the job: CI is green with every fixture in the tree |
| 2 | A breaking change merges | A pull request removes a response property from the admin document | L10 fails the pull request naming the change and its severity | Before L10: the pull request merges |
| 3 | A tenant in the body | A request body schema with `tenant_id` is added to a fixture; separately a runtime request carries `tenant_id` in its body on a valid route | L4 fails the fixture; at runtime contract validation refuses the body before the resolver, the P0.4 design's control 6 | Before L4: the schema lints; before the runtime validation: the field reaches the command |
| 4 | A mutation without a key | `POST /api/v1/tenants/{tenant_id}/business-units` from `user_a_synthetic` with no `Idempotency-Key` | 400, type `idempotency_key_missing`; no row written | Before the rule: the unit is created, and a retry creates a second |
| 5 | A key reused with another payload | The same key sent twice with two different bodies | The second answers 422, type `idempotency_key_reused`; one unit exists | Before the fingerprint: the second body is applied under the first key |
| 6 | A retry replays | The same key and body sent twice | The second answers the first's stored response with `Idempotent-Replayed: true`; one unit exists; the P0.10 records show two allows, the first with reason `allowed` and the second with reason `replayed` (question 11) | Before the store: two units |
| 7 | A stale version | `PATCH` on a business unit with `If-Match` holding the previous `aggregate_version` after another caller's update | 412, type `version_mismatch`; the resource unchanged | Before the check: the later write overwrites the earlier |
| 8 | An error outside the shape | A route made to throw an unhandled exception in the test build; a request to an unknown path; a malformed JSON body | Each answers `application/problem+json` with the `Problem` schema and a code; no stack trace, path or framework page | Before the handler: the framework's default error body |
| 9 | A leaking `detail` | The P0.3 design's control 1 request and the P0.4 design's control 4 request, with the responses scanned | No token fragment, no Tenant B identifier, no field value in any member; `instance` equals the request identifier | Before the rules: the default message echoes the header or the route's tenant |
| 10 | The other linters | The admin document run under Spectral and vacuum as the research records them | Not a protection: a measurement of which rules each runs on a `3.2.0` document, recorded as the baseline for the research's unverified item that Spectral's `oas3` rules run and its `oas3_1` rules do not | Not a protection: the measurement is the record |

Controls 1 and 2 are the manual's acceptance; controls 3 to 7 are the FLOWS template's idempotency and concurrency rows and the P0.4 design's body rule; controls 8 and 9 are RFC 9457's security consideration; control 10 is a measurement.

## Evidence contract

A control run records, per [`AGENTS.md`](../../AGENTS.md) section 9; a record missing a field is not evidence:

| Field | Content for P0.8 |
|---|---|
| Repository and commit SHA | The platform repository and the commit whose documents, fixtures, ruleset and middleware ran |
| Command or workflow identity | The workflow file and run identifier for the contract lint job, the fixture run and the runtime tests |
