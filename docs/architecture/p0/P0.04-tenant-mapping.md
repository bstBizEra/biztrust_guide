## Scope and non-scope

**In scope.** What turns a validated token into a tenant the request may act for, and what refuses it:

1. **Where the mapping lives**: on the BizTrust side, in the tenant table's organization column the P0.6 design reserves, one organization to one tenant, and nowhere in Logto.
2. **Who may change it**: the tenancy module's provisioning commands, under platform-level authority, never a member of the tenant and never a request.
3. **The resolver**: the step that takes the organization identifier and subject P0.3's chain validated and answers with a tenant context or a denial, with the four outcomes the ticket names, known, unknown, disabled and mismatched, and a fifth the contract requires, membership inactive.
4. **The mismatch path**: how the tenant a request is about is conveyed, how it is compared with the token's tenant, and how a tenant identifier in a header, query or body is ignored or denied without disclosing anything.
5. **The lifecycle**: creation with provisioning, re-creation of an organization, suspension and closure of a tenant, and what a token issued before any of those still gets.
6. **The five tests** and their negative controls, which are the `BT-G1` matrix's context and tampering rows.

**Non-scope**, each with its owner:

- Token validation, signature to scope: the P0.3 design; the resolver trusts nothing that has not passed that chain.
- Provisioning itself, the creation of a tenant and its organization, roles and first members: P0.5; this design fixes what provisioning must write and the authority it runs under.
- Business authorization beyond membership, resource scope, approval authority and the authority agreement: `AUTHORIZATION_BASELINE.md`, ADR-013 and P1. The resolver answers "which tenant, and is the subject a live member"; it does not answer "may the subject do this".
- Roles and permissions inside a tenant, and the template-wide role vocabulary against per-tenant authority (the research's gap 4): ADR-013 and the authorization baseline; the resolver reads the token's scopes only to hand them on.
- Row-level security policies: P0.7; this design sets the transaction's tenant key the P0.6 design defines and P0.7 enforces.
- The audit record's shape: P0.10; this design names the fields a denial or a tampering observation gives the record and leaves the record's shape, storage and controls to P0.10.
- Logto's deployment and the Management API's credential: ADR-002 and the P0.12 design.
- The route conventions in full: P0.8; this design proposes only the tenant segment.

## Authorization-sequence step

P0.4 is the fifth step of the tenant authorization sequence in [`FLOWS.md`](../FLOWS.md) section 3, "Resolve tenant, membership, scope and authority", for its first two parts, and the rule the flows record states beneath the sequence: the API must not copy an untrusted tenant identifier directly into a database session variable, and the authenticated organization, the BizTrust tenant mapping and the requested resource scope must be reconciled first.

| Sequence step | What P0.4 does there |
|---|---|
| Business authorization resolves tenant, membership, scope and authority | Maps the token's organization to a tenant, checks the tenant's status and the subject's membership, compares the tenant the request is about with the token's tenant, and hands the tenant context and the scopes to business authorization; refuses on any of the five outcomes below |
| Set trusted tenant context and execute command | Sets the transaction's tenant key (the P0.6 design's `app.tenant_id`) to the mapped tenant's identifier and never to anything a request supplied |
| Deny with problem details, and the audit record | Every refusal answers with problem details that name the outcome and disclose nothing about any tenant other than the caller's, and writes an audit record with a reason code (P0.10) |

The contract's sentence is the design's first rule: "An organization or tenant identifier in a URL, header, query string or request body is requested context only. It must match the authenticated and authorized context."

## Interfaces and data shapes

### Where the mapping lives

The research answers the question its gap 3 raises: Logto's organization "is a membership-and-permission boundary, not a data boundary", the application "must partition its own data by `organization_id`" (decision-relevant facts), and the custom-claims script that could read `customData` is, on a self-hosted instance, "equivalent to granting code execution on the Logto host" (F11). The mapping is therefore BizTrust's, in one place:

| Where | What | Who writes it |
|---|---|---|
| `tenancy.tenant.identity_organization_id` (the P0.6 design) | The Logto organization identifier, unique, nullable until provisioning writes it | The tenancy module's provisioning command, under platform-level authority (below); never a member, never a request, never a Logto callback |
| `tenancy.tenant_organization_history` | Every organization identifier a tenant has ever had, with `retired_at`, `recorded_at` and the provisioning record that retired it; registered platform-level like `tenancy.tenant`, a fourth table in the tenancy schema that the P0.6 design's next version lists | The same command, on re-creation; append-only; read by the resolver to answer unknown for a retired identifier (control 8) |
| Logto's organization `customData` | Nothing that decides a tenant's identity. It carries the BizTrust tenant identifier for a human reading the Logto Console and, at `0.2`, for the P0.5 design's adoption read alone, which finds what an interrupted provisioning run created; no code path treats it as authority (Open questions, question 4) | Provisioning, as a mirror and as that read's key |

The mapping is one to one: one organization is one tenant and one tenant is one organization at a time. Logto allows a user to belong to many organizations and to hold "a single identity while accessing different workspaces (organizations)" (F9); BizTrust reads that as one token per tenant, since every organization-context token is for exactly one organization (the research's decision-relevant facts), and never as one request for two tenants.

### Who may change it

Platform-level authority, not tenant-level: the tenancy module's provisioning commands run under a grant recorded for the operator's provisioning action, the same authority the P0.5 design will detail, and every change writes an audit record naming the actor, the old and new organization identifiers and the provisioning record. A member of Tenant A, however senior their role in the organization template, has no command that touches the mapping; the organization template's roles are Logto's and tenant-wide (F3), and no organization role maps to a BizTrust platform authority.

### Membership on the BizTrust side

The token proves that the subject was a member of the organization when Logto issued it: membership and MFA "are enforced at token issuance" (the research's decision-relevant facts, reading F7). It proves nothing about now; the research's gap 1 is that no official page states whether a token survives the member's removal or the organization's deletion, and the P0.3 design's question 8 assumes it does until `exp`. The contract's list asks for an "active BizTrust tenant and membership", so the resolver checks a BizTrust-side record:

| Table | Columns beyond the P0.6 baseline | Who writes it |
|---|---|---|
| `identity_access.membership` | `subject`, the Logto user or application identifier from the token's `sub`; `status`, one of `active`, `suspended`, `removed` and, at `0.2`, `pending_identity`, a member whose Logto-side half the P0.13 design's identity administration job has not yet applied; `source`, how the membership arose (provisioning, invitation, just-in-time and, at `0.2`, administration, the P0.13 design's surface), read by P0.4-B's reconciliation report; the baseline's `effective_from` and `effective_to` carry the membership's valid time | The identity-access module's commands under the tenant's own administration (P0.13 later) and under provisioning (P0.5); removal is a status change with a record, never a deletion |

Logto's membership and BizTrust's are reconciled, not duplicated: a member removed in BizTrust is denied on the next request whatever the token says; a member removed in Logto stops getting tokens, and the BizTrust record is updated by the same administrative action or by a reconciliation that the P0.5 design places. Which side is authoritative for granting is ADR-003's (Open questions, question 1); this design fixes only that BizTrust's status is checked on every request.

### The resolver

Owned by the tenancy module and called by the API service's pipeline after P0.3's chain and before any module's contract; its inputs are what the chain validated, `organization_id`, the subject and the scopes, plus the route's tenant segment, which the pipeline reads from the contract-declared path and which the chain never touches; nothing else:

```text
resolve(organization_id, subject, scopes, route_tenant)
  -> TenantContext { tenant_id, membership_id, scopes }
   | Denial { reason_code }        the code goes to the audit record; the caller sees one denial
```

At `0.2` the resolver has a second caller: `GET /api/v1/me`, the platform-level route the P0.8 design's next version declares for the P0.13 design's surface, scoped to the token's own organization and carrying no tenant segment. The resolver runs the same five outcomes with `route_tenant` absent, so the mismatch outcome cannot arise; it answers the same `TenantContext` and, for this route alone, the tenant's name beside it, which the API's response carries and the context does not, for a known, active tenant with an active membership, or the one denial; the surface learns its tenant from this answer and never derives it from the organization (the P0.13 design's question 4).

| Outcome | Condition | Answer | Audit reason code | The `BT-G1` row |
|---|---|---|---|---|
| Known | `organization_id` maps to a tenant whose status is `active`, the subject's membership is `active` and inside its effective period, and `route_tenant` equals the mapped tenant or is absent, as it is on a platform-level route | Tenant context; the transaction's tenant key is set to the mapped tenant | none | Tenant A can access authorized Tenant A data |
| Unknown | `organization_id` maps to no tenant, or to a retired identifier in the history table | Denial | `tenant_unknown` | Missing organization context, its unmapped half; the absent-claim half is P0.3's check 6 |
| Disabled | The mapped tenant's status is `suspended`, `closed` or, at `0.2`, `provisioning`, a tenant the P0.5 design's command has not yet activated | Denial | `tenant_disabled` | The context failure row, with the tenant's status recorded |
| Membership inactive | The tenant is active but the subject's membership is not `active`, which at `0.2` includes `pending_identity`, or is outside its effective period | Denial | `membership_inactive` | Inactive membership |
| Mismatched | The tenant the request is about differs from the mapped tenant | Denial | `tenant_mismatch` | Tenant A requests Tenant B URL |

Three properties hold across the denials. The caller's problem details carry one code, `tenant_denied`, and nothing else: an unknown, a disabled and a mismatched tenant produce the same status, the same shape and the same code, so that a probe cannot learn whether another tenant exists or is active; the specific reason code is written to the audit record only. Membership inactive is a fact about the caller's own tenant and may say so. No business query runs before the outcome is known, so the database is never asked about another tenant's rows. And every denial writes an audit record with the reason code, the subject, the organization identifier, the requested tenant, and the request and trace identifiers, which is the matrix's "recorded without data leakage". One answer is not a denial and the one-code rule does not govern it: when the audit record cannot be written, the P0.10 design's fail-closed rule answers an error rather than the decision's outcome, carrying none of the denials' code, so that a silent audit outage cannot hide behind a refusal; the three denials' rule stands for every denial that is recorded (the P0.10 design's question 7).

### The mismatch path

The research's gap 2 is that Logto's documentation says `organization_id` must "align with the request context" but not how the context is conveyed. This design proposed the convention at `0.1` and the P0.8 design declared it at its own `0.1`; at `0.2` the convention is that design's, quoted here:

- **The tenant a request is about is the route's tenant segment**, `/api/v1/tenants/{tenant_id}/...`, declared in the API contract for every tenant route, and nothing else. A route with no tenant segment is platform-level, which at `0.2` P0 has two of, the provisioning route and `GET /api/v1/me`; any other route without one is a defect the contract lint catches, since the P0.8 design's rule L4 refuses an operation that declares a `tenant_id` parameter in a query or a header and its rule L2 requires the segment on every route the document marks tenant-level.
- **The segment is compared, never trusted.** The resolver compares the segment with the mapped tenant; on a difference it denies with `tenant_mismatch`. The transaction's tenant key is set from the mapping, so even a resolver defect that let a mismatched request through would set the caller's own tenant, not the segment's.
- **A tenant identifier anywhere else is never an input.** No header, query parameter or body field feeds the resolver or the tenant key. The API contract declares no `tenant_id` field in any request body, so a body carrying one fails contract validation before the resolver runs, which is the matrix's "deny"; a header or query parameter carrying one is read only to be recorded, never consumed as input, which is the matrix's "ignore untrusted value", and its presence with a value that differs from the mapped tenant is written to the audit record as a tampering observation, which is the matrix's "tampering outcome recorded" and what the P0 manual calls evidence of tampering, not input.
- **The database is the last line.** A row written under the caller's tenant key with another tenant's identifier in it is refused by P0.7's `WITH CHECK` policy, so the mismatch path has two independent refusals for a write and the matrix's row "Tenant A injects Tenant B body/header ID" has both halves.

### The lifecycle

| Event | What happens to the mapping | What a token issued before it gets |
|---|---|---|
| Provisioning (P0.5) | The organization is created through the Management API by BizTrust's own provisioning command, as the research reads Logto's guidance to wrap Management API calls in the application's own layer (F10); the identifier is written to the tenant; the first membership is written | No token exists yet |
| Rename | Nothing: the tenant's name and the organization's name are independent; neither is a key | Unchanged |
| Re-creation of the organization | The old identifier is moved to the history table with `retired_at`; the new one is written; both by one provisioning command with one audit record | A token for the retired identifier resolves as unknown from that moment |
| Suspension | The tenant's status becomes `suspended`; the mapping is unchanged | Denied as disabled from the next request, whatever the token's `exp` |
| Closure | The tenant's status becomes `closed`; the mapping is unchanged and never reused | Denied as disabled; the organization's deletion in Logto, if any, is a separate administrative act whose cascade the research reads in the schema (F12) and whose effect on issued tokens is `UNVERIFIED` (gap 1) |
| Member removal | The BizTrust membership status becomes `removed` with its record | Denied as membership inactive from the next request, whether or not Logto still honours the token |

At `0.2` each row that changes a membership or a tenant's status publishes the event the P0.9 design declares for it, a tenant suspended or closed and a membership changed, written to the publishing module's own outbox in the same transaction as the change, so that no event leaves without its transaction; the provisioning row's event is the P0.5 design's (the P0.9 design's question 12).

The status vocabulary is this design's, as the P0.6 design says the lifecycle fixes it: `active`, `suspended` and `closed`, with `provisioning` reserved for the transition into `active` that P0.5 defines, and at `0.2` denied as disabled until that transition, as the P0.5 design's control 4 has it.

## Negative controls

Each control is seen failing before the protection exists and passing after; every control feeds the `BT-G1` matrix and is run by a verifier who is not the implementer. Tokens are obtained from the P0.3 lab.

| # | Threat or defect | Condition | Expected denial or failure | Seen failing at |
|---|---|---|---|---|
| 1 | Known tenant, the positive control | `user_a_synthetic`'s token for Tenant A's organization on a Tenant A route | Tenant context; the transaction's key is Tenant A's; Tenant A's synthetic rows returned and no other tenant's | Not a protection: the positive control, recorded as the baseline every denial is measured against |
| 2 | Unknown organization | A valid token whose `organization_id` is an organization the lab created but never mapped | Denied, `tenant_unknown`; no business query; audited | Before the resolver: the request proceeds with no tenant, or with a tenant derived from the route |
| 3 | Disabled tenant | Tenant B suspended in the tenancy table; `user_ab_synthetic`'s token for Tenant B's organization on a Tenant B route | Denied, audited as `tenant_disabled`; the same status, shape and code as control 2's response | Before the status check: Tenant B's rows returned |
| 4 | Mismatched tenant | `user_a_synthetic`'s token for Tenant A on a Tenant B route | Denied, audited as `tenant_mismatch`; the transaction's key is never Tenant B's; no Tenant B row read; the response is the same status, shape and code as control 2's | Before the comparison: Tenant B's rows returned under Tenant A's token, or Tenant A's rows returned on Tenant B's route |
| 5 | Membership inactive | `user_a_synthetic`'s membership set to `removed` in BizTrust while the token is still inside `exp` | Denied, `membership_inactive`; audited | Before the membership check: the request proceeds on the token alone |
| 6 | Tenant identifier in the body | A valid Tenant A request whose body carries `tenant_id` = Tenant B's | Refused by contract validation before the resolver; audited as tampering | Before the contract rule: the field reaches the command and P0.7's `WITH CHECK` is the only refusal |
| 7 | Tenant identifier in a header or query | A valid Tenant A request carrying `X-Tenant-ID: <Tenant B>` and `?tenant=<Tenant B>` | Not an input; the request proceeds as Tenant A; the audit record notes the differing header and parameter | Before the rule that no code path takes them as input: a code path sets the key from one |
| 8 | Retired organization | A token for Tenant A's previous organization identifier, after re-creation | Denied, `tenant_unknown` | Before the history table: the old identifier still resolves, or nothing resolves and the reason is not recorded |
| 9 | Token after removal in Logto | `user_a_synthetic` removed from the organization in Logto while a token is inside `exp`; the request repeated | Measured, not asserted: whether Logto's resources still accept the token is `UNVERIFIED` (the research's gap 1); the BizTrust membership check is what denies, and the record says which layer refused | A measurement, not a protection: recorded as a baseline; the design's own protection is control 5 |

Controls 2 to 7 are the matrix's missing-organization-context, inactive-membership, Tenant B URL and injected-identifier rows.

## Open questions and dependencies

1. **ADR-003 decides the mapping and which side grants membership.** Waits on: [#104](https://github.com/bstBizEra/biztrust_guide/issues/104) on the contract map, behind the waiver (#92). `ASSUMED` meanwhile: the mapping lives in BizTrust and is written only by provisioning; membership is granted in Logto and mirrored to a BizTrust record that is checked on every request, so that removal on either side denies.
2. **The tenant segment convention.** The research's gap 2; answered at `0.2` by the P0.8 design: `/api/v1/tenants/{tenant_id}/` on every tenant route, compared and never trusted, with no other carrier read, and its lint rule L4 refusing a tenant carrier in a body, a query or a header. Waits on: ADR-005 for the path form, as that design's question 4 says. `ASSUMED` meanwhile: the segment as the P0.8 design declares it.
3. **Tokens after removal or deletion.** The research's gap 1, `UNVERIFIED`; waits on control 9's record. `ASSUMED` meanwhile: a token survives until `exp`, which is why the BizTrust membership and status checks run on every request.
4. **A mirror in `customData`.** The research's gap 3; waits on ADR-003. `ASSUMED` meanwhile: the mirror is a convenience for a human reading the Logto Console and no code reads it for authority; at `0.2` one code path reads it, the P0.5 design's adoption read, which searches organizations only when that tenant's last run stopped inside its organization step and adopts one whose `customData` carries the tenant identifier and whose name is the request's, to find what that run created; it decides nothing about a tenant's identity, which stays on the BizTrust side (the P0.5 design's question 10); if ADR-003 wants Logto to deny issuance for a closed tenant through the claims script, that is a self-hosting decision with the host-execution cost the research names.
5. **Template-wide roles against per-tenant authority.** The research's gap 4; waits on ADR-013 and the authorization baseline. `ASSUMED` meanwhile: the resolver hands scopes on and reads none of them; BizTrust's own entitlements sit beside the template, not inside it.
6. **The status vocabulary and its transitions.** Waits on: the P0.5 design for the provisioning transition and the tenancy module's commands for the rest. `ASSUMED` meanwhile: `active`, `suspended`, `closed`, with `closed` never reused and never a deletion.
7. **Reconciliation between Logto's membership and BizTrust's.** Waits on the P0.5 design. `ASSUMED` meanwhile: the same administrative action writes both, and a reconciliation job reports differences without changing either.
8. **Machine identities' membership.** The research reads that an M2M application must be associated with the organization (F8). Waits on: ADR-003 and the P0.12 design's row for the API's machine-to-machine application, whose scope set that design marks assumed. `ASSUMED` meanwhile: an application's membership record is written by provisioning like a user's, with `subject` the application identifier, and is checked the same way; the P0.5 design's step 3 writes that row, so the assumption is carried by a landed design and waits only on ADR-003.

No item is `UNKNOWN_BLOCKING`: the design proceeds on its assumptions and each is reversible by the decision it names.
