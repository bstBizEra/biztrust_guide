## Scope and non-scope

**In scope.** The policies that make the P0.6 design's tables refuse another tenant's rows, and the proof that they do so even when the application is wrong:

1. **The policy shape per table**: the four commands, the `USING` and `WITH CHECK` expressions, permissive only, generated from the same template as the table.
2. **How the tenant key reaches the policy** under connection pooling, and what the design can and cannot claim about poolers.
3. **`FORCE ROW LEVEL SECURITY`** on every tenant-owned table, so that the owner is filtered too.
4. **The fifteen documented leak paths**, each assigned to one of three fates: closed by design with the check that proves it, accepted with a named check, or owned elsewhere.
5. **The application-bypass test**, the P0 manual's equivalent of the whole phase in one row: a path that skips application authorization and is still refused by the database, seen failing before row security is on.
6. **The cross-tenant proof rows** the research's fourth decision-relevant fact names, insert with conflict, update with returning, upsert against another tenant's key, delete, and bulk import, which the `BT-G1` (label B) matrix's read, write and delete denial row names.

**Non-scope**, each with its owner:

- The tables, roles, tenant key definition, migration convention and ownership tests: the P0.6 design; this design adds the policies and the policy checks to them and changes none of them.
- Setting the tenant key from the mapping and refusing a mismatched request before any query: the P0.4 design; this design proves what happens if that refusal is bypassed.
- The security proof's matrix as a whole, its verifier and its evidence binding: `P0.SECURITY-PROOF.md` (#148), which this design feeds with the rows below.
- Business authorization, roles and permissions: the authorization baseline and ADR-013; row security is one layer, and the baseline's rule stands: "No single layer substitutes for another. A gateway allow is not domain authorization, and an application allow is still constrained by RLS."
- Column-level access, which the research records that row security does not protect (leak 14): the P1 designs that first need a hidden column, through column grants.
- Backups, restores and logical replication, which run outside row security by design (leak 13): P3's disaster-recovery epic and ADR-019; this design fixes only which role runs them, how a dump by any other role fails loudly, and the audit that role's sessions carry.
- The connection pooler's selection: the P0.6 design's open question; this design says what must be measured on whichever pooler is chosen.

## Authorization-sequence step

P0.7 is the sixth step of the tenant authorization sequence in [`FLOWS.md`](../FLOWS.md) section 3, "Set trusted tenant context and execute command", on its database side, and the branch beneath it, "RLS denies", with its record:

| Sequence step | What P0.7 does there |
|---|---|
| Set trusted tenant context and execute command | The key the P0.4 design set for the transaction is what every policy compares; the command runs as `app_role`, which the P0.6 design leaves no path around the policies |
| RLS denies | A read of another tenant's rows returns nothing; a write of a row that would belong to another tenant errors; both without cross-tenant disclosure |
| Record isolation denial | A `WITH CHECK` error is caught by the data-access layer, mapped to the same denial the application would have given, and audited with a reason code (P0.10); at `0.2` that layer also takes a savepoint before every business statement, so that the P0.10 design's write contract can roll the statement back and keep its record in the same transaction (the P0.10 design's question 7); a filtered read that returns nothing is not an error and is recorded by the application's own authorization, which should have refused first |

The manual's rule for this epic is the design's test: the row that proves RLS is independent of the application is the one where the application check is bypassed in a test path and the database still refuses, and if that row cannot be made to fail before the policies exist, the phase stops.

## Interfaces and data shapes

### The policy shape per table

Every tenant-owned table of the P0.6 design's template carries four policies, generated into the table's own migration by the policy template kept under `db/policies/`, where the manual's row lands the policies, so that a table cannot exist without them; the ownership test T3 the P0.6 design assigns to this epic asserts their presence per granted command:

```text
CREATE POLICY <table>_tenant_select ON <schema>.<table> FOR SELECT
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid);
CREATE POLICY <table>_tenant_insert ON <schema>.<table> FOR INSERT
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
CREATE POLICY <table>_tenant_update ON <schema>.<table> FOR UPDATE
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
CREATE POLICY <table>_tenant_delete ON <schema>.<table> FOR DELETE
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

Pseudo-schema, not an implementation; the rules it encodes:

- **No role clause.** Every policy applies to every role, the owner included, because every table is forced (F3) and the owner is `NOBYPASSRLS`; a policy naming `app_role` alone would leave the owner default-denied on its own tables, since "If no policy exists for the table, a default-deny policy is used" (F1), which is not what the P0.6 design's control 3, a migration under the owner filtered by the key, intends. The owner therefore reads and writes tenant rows only with a key set, one tenant per transaction, and a backfill that touches every tenant loops over the tenants and sets the key per transaction (question 9).
- **Permissive, one per command, and nothing else.** "If there are no `PERMISSIVE` policies, then access is denied" (F4), so a table with row security enabled and no policy denies everything, which is the P0.6 design's enablement rule; a restrictive policy is never used, so that the four policies are the whole of what a table allows.
- **`USING` filters, `WITH CHECK` errors.** "Existing table rows are checked against the expression specified in `USING`, while new rows that would be created via `INSERT` or `UPDATE` are checked against the expression specified in `WITH CHECK`", and "When a `WITH CHECK` expression returns true for a row then that row is inserted or updated, while if false or null is returned then an error occurs" (F4). A read of another tenant is silence; a write into another tenant is an error the application must catch.
- **The `UPDATE` policy carries both.** "The `USING` expression determines which records the `UPDATE` command will see to operate against, while the `WITH CHECK` expression defines which modified rows are allowed to be stored back into the relation" (F4), so a row cannot be moved between tenants by changing its `tenant_id`.
- **The policy reads the row and the key, nothing else.** The research's fifteenth finding is the rule: "the policy expressions consider only the current values in the row to be accessed or updated. This is the simplest and best-performing case", and consulting other tables "can create race conditions that could allow information leakage" (F15, leak 10). A policy lint, kept with the template, refuses any policy text containing a sub-select or a function call other than `current_setting`.
- **A missing key sees nothing.** With `missing_ok`, a missing setting yields null (the P0.6 design), the comparison yields null, and "if false or null is returned then the row is not visible" (F4).
- **The platform-level tables are the first exception.** At `0.2` the P0.6 design lists five: `tenancy.tenant`, `tenancy.tenant_organization_history`, `tenancy.provisioning_run`, `tenancy.platform_outbox` and `tenancy.platform_inbox`. Each carries a select policy `USING (true)` and no update or delete policy for `app_role`; the P0.4 design's resolver reads the first two by organization identifier before any key exists, and no contract returns a row of the tenant or the history table to a caller; what an operator's job reads back from a run, an outbox or an inbox row is the design that owns it to say, and is not a tenant's read. Their write policies name the role that writes each, as the P0.6 design's `0.2` roles table has it: `provisioning_role` inserts and updates `tenancy.tenant` and `tenancy.provisioning_run`, inserts `tenancy.tenant_organization_history` and `tenancy.platform_outbox`, and holds nothing else; `app_role` inserts and updates `tenancy.platform_inbox`, the claim its consuming handler writes, and holds no write privilege on the other four. The role was a proposal at `0.1`; the P0.6 design lists it at its own `0.2` (question 10).
- **The audit tables are the second exception.** `audit.decision` and `audit.platform_event` carry a select and an insert policy and no update or delete policy at all, so that no role can change or delete a record even if a privilege were granted by mistake; the P0.10 design's protection table is where that rule lives and this design names the exception (the P0.10 design's question 7).
- **`row_security` stays on** for every role but one. It is `off` only on `backup_role`'s connections, where it has no effect because that role holds `BYPASSRLS` (F2); `pg_dump` sets it off by default, so a dump by any other role errors rather than filters: "If the user does not have sufficient privileges to bypass row security, then an error is thrown" (F14). The owner is not that role: a forced table applies its policies to the owner (F3), so the owner's dump errors too, unless the `pg_dump` sentence that "superusers and the owner of the table being dumped always bypass RLS" (F14) holds for a forced table, which the documentation leaves `UNVERIFIED` and control 9 measures. This departs from the P0.6 design's sentence that backup and audit export run as the owner with `row_security = off`, which under forcing errors on every tenant-owned table; that design's next version restates the backup path as this one.
- **Owners.** The policy template and the lint belong to the tenancy module; the bypass entry point belongs to the security test package under `tests/security/`, where the manual's row lands the tests; the error mapping belongs to the API service's data-access layer, which the P0.4 design already places in the pipeline.

### The tenant key under connection pooling

The P0.6 design fixes the key as transaction-scoped through `set_config('app.tenant_id', <uuid>, true)`, because a session-level `SET` "will persist until the end of the session, unless overridden by another `SET`" (F7, leak 11). What this design adds is what can and cannot be claimed about poolers:

| Pooling mode, in this design's words; any pooler's own names and behaviour are `UNVERIFIED` until read from its documentation (F8) | What the transaction-scoped key gives | What must be measured |
|---|---|---|
| No pooler, or a pool the application owns and never shares a connection across transactions | The key ends with the transaction; a reused connection carries no key into the next | Control 4 of the P0.6 design on the application's own pool |
| Session pooling, one client per server connection for the session | The same; the key never outlives its transaction whatever the session does | The same control on the pooler |
| Transaction pooling, a server connection per transaction | The key is set inside the transaction and ends with it, which is the only mode this design is written for | That the pooler hands the connection to the next transaction with no key, which the documentation does not describe (F8, `UNVERIFIED`) |
| Statement pooling, if a pooler offers it | Refused as a mode by this design: it gives the key and the query no transaction to share, and the key is transaction-scoped | Not measured |

The design does not name a pooler, since none has an ADR row and none was researched (the P0.6 design's open question 4); it names the mode it is written for and the measurement that admits a pooler.

### `FORCE ROW LEVEL SECURITY`

Every tenant-owned table is created enabled and forced in the same migration step, as the P0.6 design's enablement rule states, because "Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`" (F3), and the owner "can also switch RLS off at will" (leak 2). The owner is `migration_role`, which runs migrations and nothing else; forcing is what makes a migration that queries tenant rows under the owner filtered like any other session, and control 3 of the P0.6 design proves it. This design adds the check that no migration disables or unforces row security on an existing table: the migration lint of the P0.2 design refuses `DISABLE ROW LEVEL SECURITY` and `NO FORCE ROW LEVEL SECURITY` outside a migration that drops the table.

### The fifteen leaks, each with a fate

The research lists fifteen paths by which policies can be bypassed or inferred around, each with the documentation sentence that establishes it. The ticket asks which are closed by design and which are accepted with a named check; this table answers, and names the check or the owner for each.

| # | Leak, as the research names it | Fate | The check, or the owner |
|---|---|---|---|
| 1 | Superuser and `BYPASSRLS` roles read and write every tenant's rows | Accepted with a named check | `app_role`, `migration_role`, `provisioning_role` and `store_root` are `NOSUPERUSER` and `NOBYPASSRLS` (the P0.6 design's T5, extended to every role); exactly one role, `backup_role`, holds `BYPASSRLS`, connects only from the backup job, holds no application privilege, and every one of its sessions is audited (P0.10); the check is a role test, T9, that no other role holds the attribute |
| 2 | The table owner bypasses policies unless forced, and can disable them | Closed by design | Every table forced; the P0.6 design's T2 and T4; the migration lint's refusal of disabling |
| 3 | Whole-table commands, `TRUNCATE` and `REFERENCES`, are not filtered | Closed by design | The privileges withheld from `app_role`; T5; control 8 of the P0.6 design |
| 4 | Existence of another tenant's values leaks through unique, primary-key and foreign-key checks | Closed by design, with a named exception register | `tenant_id` in every unique and foreign key and surrogate keys everywhere; T6. A constraint that must be global, if one is ever needed, is listed in a register the data reviewer keeps, with its leak accepted and its reason |
| 5 | Error-against-filter differences on `RETURNING` and `ON CONFLICT` are observable | Accepted with a named check | The data-access layer maps every `WITH CHECK` and policy error to the one denial the application gives, so a caller sees no difference between "no such row" and "another tenant's row"; control 6 below; this design assumes, for ADR-012 to decide (question 3), that idempotency keys include `tenant_id`, so that an `ON CONFLICT` never targets another tenant's key |
| 6 | Plan shape, run time and optimizer statistics are covert channels | Accepted with a named check | The API returns no plan, no query timing and no count of rows a policy filtered, which this design asks the P0.8 design to carry into the contract; run time is observable from outside and no contract closes it, so the channel is recorded as accepted in the security proof with that residue named |
| 7 | `LEAKPROOF` functions and argument-free functions run before the policy filter | Closed by design | No function marked `LEAKPROOF` except by a reviewed migration; the P0.6 design's T7 |
| 8 | Views owned by a privileged role apply the owner's policies | Closed by design | `security_invoker = true` on every view over tenant-owned tables; T7 |
| 9 | `SECURITY DEFINER` functions reach rows the caller cannot | Closed by design | None in a tenant-owned schema; an exception, if one is ever needed, passes the data reviewer's review with `search_path` set as the research quotes, "write `pg_temp` as the last entry in `search_path`" (F11), and execute revoked from `PUBLIC`; T7 |
| 10 | Policies that consult other tables can be raced | Closed by design | The policy shape reads the row and the key only; the policy lint |
| 11 | A stale session-level key on a reused connection is honoured | Closed by design, with a measurement | The transaction-scoped key; the P0.6 design's control 4 on the chosen pooler |
| 12 | `BEFORE ROW` triggers rewrite the row before the policy sees it | Closed by design | No such trigger writes `tenant_id`; T8 |
| 13 | Backups, restores and replication run outside row security | Owned elsewhere, with a named check here | Only `backup_role` produces a dump, and a dump by any other role errors (control 9); no logical replication exists in P0, and one that is ever created connects as a `BYPASSRLS` role under the same audit, since a `NOBYPASSRLS` publisher role with `row_security` off halts on the first policy (F13); the rest is P3's and ADR-019's |
| 14 | Columns are not protected by row security | Owned elsewhere | Column grants, in the P1 design that first needs a hidden column |
| 15 | `COPY FROM` is unsupported on a row-security table, pushing bulk loads to a non-filtered path | Closed by design, with a measurement | `COPY FROM` is refused on a row-security table (F12), which control 10 records; an import is written as `INSERT` statements, "Use equivalent `INSERT` statements instead" (F12), run as the owner one tenant per transaction with the key set, so that it is filtered like any session; whether a `BYPASSRLS` role may `COPY FROM` such a table is `UNVERIFIED` and no import uses one; the check is that no application code path issues `COPY` |

### The application-bypass test

The P0 manual's section 04 names the row that makes the proof mean something: a test path in which the application's own authorization check is switched off, and the database refuses on its own. The design fixes what that path is, so that it cannot be confused with a real one:

- **A test-only entry point**, present only in the security test package under `tests/security/`, that takes a tenant key and a statement and runs the statement as `app_role` with the key set, skipping the P0.4 resolver and every business authorization; it does not exist in any deployable artifact, and a boundary rule this design asks the P0.2 design's next version to add refuses its import from any non-test path (question 8).
- **Seen failing first.** A table with row security enabled and no policy denies everything (F1), so the red run cannot be the migrations' own state. The harness builds a baseline database from the same migrations and, as the owner, disables row security on the tenant-owned tables of that database alone: "Disabling row security does not remove any policies that are defined on the table; they are simply ignored. Then all rows in the table are visible and modifiable, subject to the standard SQL privileges system" (F1). The migration lint does not read the harness, which is not a migration, and the baseline database is dropped after the run. The bypass path then selects under Tenant A's key and Tenant B's rows come back; that run is recorded as the failing baseline, and the harness returns its identifier as an output, which the security proof's manifest carries in its `baseline_run` field (the security proof's question 9). The same run on the migrated database, enabled, forced and with the policies, returns Tenant A's rows and none of Tenant B's, and the assertion carries that positive half too. If the baseline cannot be made to fail, because the harness could not disable row security or because the key is not what the test set, the phase stops, as the manual's stop signal says.
- **Every write path in the matrix.** The same entry point runs the research's write paths under Tenant A's key against Tenant B's rows: an insert of a row with Tenant B's `tenant_id`; an update that changes a Tenant A row's `tenant_id` to Tenant B's; an insert with `ON CONFLICT DO UPDATE` whose conflict target is a Tenant B key; an update with `RETURNING`; a delete of a Tenant B row; and a bulk insert of mixed-tenant rows. Each has an expected outcome from the research: an error for the checks where "an error is thrown" (F4, F5, F6), silence for the filters, and a policy error rather than a silent skip for `ON CONFLICT`, since "the `INSERT` is never silently avoided" (F6).

## Negative controls

Each control is seen failing before the protection exists and passing after; every control feeds the `BT-G1` matrix and is run by a verifier who is not the implementer. The database holds the P0.6 design's synthetic Tenant A and Tenant B rows.

| # | Threat or defect | Condition | Expected denial or failure | Seen failing at |
|---|---|---|---|---|
| 1 | The application bypassed | The bypass entry point selects from `legal_entity` under Tenant A's key with no `WHERE` | Tenant A's rows only; zero Tenant B rows; no error | On the baseline database: both tenants' rows returned |
| 2 | Cross-tenant insert | The bypass path inserts a `business_unit` with Tenant B's `tenant_id` under Tenant A's key | A `WITH CHECK` error; no row written; the error mapped to the standard denial and audited | On the baseline database: the row is written |
| 3 | Row moved between tenants | The bypass path updates a Tenant A `business_unit` to set `tenant_id` to Tenant B's | A `WITH CHECK` error; the row unchanged | On the baseline database: the row moves and vanishes from Tenant A's view |
| 4 | Cross-tenant delete | The bypass path deletes a Tenant B `business_unit` by its identifier under Tenant A's key | Zero rows affected, no error; Tenant B's row intact | On the baseline database: the row is deleted |
| 5 | Upsert against another tenant's key | The bypass path inserts with `ON CONFLICT DO UPDATE` whose conflict target names a Tenant B row's unique key | An error, "the `INSERT` is never silently avoided" (F6); no row of either tenant changed | On the baseline database: Tenant B's row updated |
| 6 | The error-against-filter channel | A caller with Tenant A's context issues, through the real API, a write whose `RETURNING` or `ON CONFLICT` path would error on a Tenant B row | The same denial shape and status as a plain "not found"; the audit record carries the policy error's reason code | Before the mapping in the data-access layer: the raw policy error reaches the caller and names the path |
| 7 | A policy that consults another table | A migration adds a policy whose `USING` contains a sub-select | The policy lint refuses the migration, naming the policy | Before the lint: the policy applies |
| 8 | Row security disabled by a migration | A migration issues `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` on a tenant-owned table | The migration lint refuses it; if run by hand as the owner, the P0.6 design's T2 fails at the next run | Before the lint: the table opens |
| 9 | A dump by the wrong role | A dump is attempted as the owner and as `app_role` with `pg_dump` at its default, `row_security` off; then as `backup_role` | The first two error rather than producing a partial file (F14); if the owner's dump succeeds on a forced table, that is the `UNVERIFIED` sentence measured and recorded, and forcing does not close leak 13 for the owner; `backup_role`'s dump succeeds and contains every tenant, and its session is audited | On an unforced table in the baseline database: the owner's dump succeeds with every tenant and no audit record |
| 10 | Bulk import as the application | A test path attempts `COPY FROM` as `app_role` and as the owner on a tenant-owned table | Refused: `COPY FROM` "is not supported for tables with row-level security" (F12) | Not a protection: a measurement of documented behaviour, recorded as a baseline; the design's own check is that no application code path issues `COPY`, held by the boundary lint |

Controls 1 to 5 are the `BT-G1` matrix's rows "Tenant A cannot read, create, update or delete Tenant B protected data" and "An application-level authorization bypass test remains blocked by RLS"; control 6 is the tampering row's audit half; controls 7 to 9 are this design's own checks, and control 10 is a measurement.

## Open questions and dependencies

1. **ADR-004 decides the tier, the key mechanism, the owner and bypass policy and the forbidden operations.** Waits on: [#105](https://github.com/bstBizEra/biztrust_guide/issues/105) on the contract map, behind the waiver (#92). `ASSUMED` meanwhile: the policy shape, the forcing rule and the leak table above are the proposal that ticket reads; if it decides otherwise, this design is revised under a new version.
2. **The pooler and its mode.** Waits on: the pooler's selection, which is the P0.6 design's question 4, and the measurement record on the pooler chosen; `UNVERIFIED` until then (F8). `ASSUMED` meanwhile: transaction pooling or none, and no pooled deployment before the P0.6 design's control 4 record exists for the pooler chosen.
3. **Idempotency keys and `ON CONFLICT`.** Waits on: ADR-012 ([#111](https://github.com/bstBizEra/biztrust_guide/issues/111)), which decides the key scope; the research's sixth finding makes an `ON CONFLICT` against another tenant's key an error, not a silent skip. `ASSUMED` meanwhile: every idempotency key and every conflict target includes `tenant_id`, so the path is never taken across tenants, and control 5 proves what happens if it is.
4. **The global-constraint register.** A constraint that must be unique across tenants, if one is ever needed, reopens leak 4 for that value. Waits on: the data reviewer role of the first design that asks for one. `ASSUMED` meanwhile: none exists; the register is empty and its existence is the check.
5. **The policy lint.** No research names a tool that checks policy text. Waits on: the P0.7 Work Package's review, and ADR-004 for the rule it enforces. `ASSUMED` meanwhile: a script under `scripts/` beside the P0.2 design's migration lint, refusing sub-selects, function calls other than `current_setting`, and disabling or unforcing statements.
