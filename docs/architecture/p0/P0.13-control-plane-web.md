## Scope and non-scope

**In scope.** The screens a human uses to exercise the tenant authorization sequence, designed so that the surface is a client of the sequence and never a claim about it:

1. **The surface's place and its one rule**: an experience under `apps/control-plane/` that holds no database connection, no module import and no administrative credential, and reaches the platform only through the admin API of the P0.8 design.
2. **Login and tenant selection**: sign-in through Logto, the user's organizations listed, one selected, an organization token obtained for it, and the tenant that token maps to learned from the API and never assumed.
3. **Member administration, roles, business units and branches** within the selected tenant: the BizTrust-side changes as commands of the tenancy and identity-access modules through the API, and the Logto-side half of a membership or role change as a request the platform's identity administration job applies, since the surface may not hold the Management API credential.
4. **Security settings, sessions and device revocation**: the tenant's MFA requirement and a member's Logto sessions, administered the same way, and the surface's own session, which is its own to end.
5. **Tenant configuration**: the tenant's name and settings on the BizTrust side, and its branding in Logto through the job.
6. **The audit viewer**: the P0.10 design's read contract under the tenant's key, showing the tenant's own records and recording every read.
7. **The denial paths as the user sees them**: a wrong tenant selected, a revoked session, a member removed mid-session, an expired token, an absent scope, each rendered as the sequence's refusal and never worked around.
8. **What is never on the surface**: any function that touches a client, a policy, a claim or a premium, refused by a lint on the surface's routes before the stop signal has to be raised.

**Non-scope**, each with its owner:

- Isolation, tenant mapping, token validation and their proofs: the P0.3, P0.4 and P0.7 designs and the security proof; the ticket's rule (#185) is that the surface's negative controls are "usability of the denial paths" and "not isolation", and the manual's that the surface is "not evidence that isolation holds".
- The roles' meaning beyond the baseline's review matrix, and any authority to bind, pay or claim: ADR-013 and P1's designs; in P0 the surface's roles are the tenant administrator and the auditor of the baseline's matrix as scopes the P0.3 chain checks, and no P0 role grants an insurance act.
- The platform auditor's cross-tenant view under the P0.10 design's elevation, and any operator console: P3's operations epics; this surface serves a tenant's members within their tenant and nothing above it (question 7).
- Provisioning a tenant, which the P0.5 design's operator-invoked command does; the surface never creates a tenant, and that design's question 2 keeps its own assumption, a job run from a reviewed request file, since no P0 screen submits one.
- A support surface through which an engineer finds a request's actor, which the P0.11 design's question 6 leaves here: none in P0; a tenant's own auditor finds the actor in the audit viewer below, and a platform support surface is P3's, under the P0.10 design's elevation (question 7).
- Invitations by email and just-in-time joining through enterprise single sign-on, which the research records Logto offers (F10): a later version of this design, after ADR-002 decides the hosting model, since each needs Management API or connector configuration the platform does not hold at runtime (question 5). The P0.5 design's question 5, how a member comes to exist as a Logto user, is answered by that deferral: in P0 an operator creates the user in Logto's console, which the research records beside the Management API as where organizations and members are made (F10), before an administrator adds them.
- The UI's design system, accessibility and localization: the guide's UX record, `UX-001` in the contract family, under the doctrine ticket ([#158](https://github.com/bstBizEra/biztrust_guide/issues/158)).
- Broker, partner and insurance experiences: P1 and later, under `apps/` beside this one and never inside it.

## Authorization-sequence step

P0.13 implements no step of the tenant authorization sequence in [`FLOWS.md`](../FLOWS.md) section 3; it is the actor, "User or service", at the sequence's head, made a human with a screen, and every arrow from the actor is a request the surface sends and every arrow back is a response it renders.

| Sequence step | What P0.13 does there |
|---|---|
| Request API token with organization context; signed token | The surface signs the user in through Logto, lists the organizations the user's identity claims name, and on selection obtains an organization token for the selected one, the one kind of token the P0.3 chain accepts |
| Protected request; deny with problem details | Every screen's data and every action is a request to the admin API of the P0.8 design under that token, with the tenant the API mapped in the route; a refusal arrives as problem details with one caller-facing code, which the surface renders as the sequence's answer and never retries around |
| Record action and outcome | The surface writes nothing to the audit tables; what a member did is the API's record, and the audit viewer reads it back through the P0.10 design's contract, which records the reading too |

The contract's sentence of section 8 is the surface's one constraint on identifiers: "An organization or tenant identifier in a URL, header, query string or request body is requested context only. It must match the authenticated and authorized context." The surface puts the tenant in the route, as the P0.8 design fixes, and nowhere else.

## Interfaces and data shapes

### The surface's place and its one rule

The surface is an experience under `apps/control-plane/`, the manual's candidate directory, in the Next.js and React package the stack decision names as a preference. The P0.2 design's rule 5 lets an experience "import modules' contracts and `packages/*`"; this design takes less than the rule allows: the control plane imports `packages/*` only, never a module's contract, because a contract call runs in the calling process and would bypass the P0.3 chain, the P0.4 resolver and the API's audit, which is exactly what the surface must never do. The surface is therefore a client of the admin API over HTTP, `biztrust-admin-api.yaml`, the family the P0.8 design's question 8 assumed for P0's routes and this design confirms as the one it calls, with a client generated from that document by a tool no ADR row names (question 11), so that a request the contract does not declare cannot be sent. The surface also serves the problem type documents the P0.8 design's question 5 leaves to it: one read-only public page per code of `errors.yaml` at the type URI, carrying the code's title and no tenant's data. The rule is a departure from rule 5's allowance, narrower and not wider, and this design asks the P0.2 design's next version to record it as the control plane's own (question 8).

Three things the surface does not hold, each an inventory fact the P0.12 design's controls can check: a database credential; a module import; and the Management API credential, which that design classes as administrative and permits "read only during an exercise, never by a running process". The surface's two secrets are runtime-class in that design's inventory: its Logto application secret, for the sign-in flow, and its session cookie secret, since the SDK "uses cookies to store encrypted session data by default" and the page says to "ensure that the value is at least 32 characters long" [L1].

### Login and tenant selection

| Step | What happens | Source |
|---|---|---|

| List organizations | The surface requests the organizations scope, so that the identity token carries the `organizations` claim the page names [L1]; the research reads that "a user can be a member of multiple organizations" and that the switcher pattern is to list them and, on selection, "call the SDK method `getOrganizationToken(organizationId)`" (F9) | [L1], F9 |
| Select a tenant | On selection the surface requests the one token the P0.3 chain accepts, the organization-level API resource token of the research's model 3, obtained with the API's resource and the organization together (F6); the `getOrganizationToken` call the quick start shows [L1] returns the research's model-2 organization token, whose audience is the organization and not the API, which the chain refuses, and the SDK call that takes both the resource and the organization is not shown on the page and is `UNVERIFIED` (question 11); "Each time they switch, the app fetches a new organization token" (F9) | [L1], F6, F9 |

A user who is a member of two tenants, `user_ab_synthetic`, sees both in the list and holds one at a time; switching fetches a new token and repeats "Learn the tenant". The surface keeps no tenant identifier in a cookie or local storage beyond the current selection, and that selection is re-resolved on every page load.

### Member administration, roles, business units and branches

The baseline's matrix, "a review baseline, not an accepted entitlement configuration", gives the tenant administrator `F` on "Manage members and roles" and "Manage tenant configuration" and `R` on "Read audit evidence", and the auditor `F` on the last; those two roles are P0's, as scopes the P0.3 chain checks on the routes below, and no other column of the matrix has a P0 screen.

Every change has a BizTrust-side half and, where Logto must change too, a Logto-side half. The BizTrust-side half is a command of the tenancy or identity-access module through the API, authorized by the sequence and effective at once. The Logto-side half is a request, since the surface and the API service may not hold the Management API credential; the request is a record the identity administration job applies in its run, the same command family as the P0.5 design's provisioning run and the same position on the credential, that design's `ASSUMED` one, that the run "reads the credential from the store at its start and holds it for the run's duration only", which this design shares and asks the P0.12 design to admit (question 2). The job applies only a request whose BizTrust-side half the sequence already authorised and recorded, runs under the same platform-level grant as a provisioning run, and writes an audit record for every application naming the request, so that the Logto-side half is never an action the sequence did not see:

| Action | BizTrust-side half, immediate | Logto-side half, applied by the job |
|---|---|---|
| Add a member | A membership row for the subject with `status = 'pending_identity'` and `source = 'administration'`, a status and a source this design adds to the P0.4 design's vocabulary (question 3) | `POST /api/organizations/{id}/users` with the subject, then `POST /api/organizations/{id}/users/roles` with the subject and the role from the shared template, the two calls of the P0.5 design's step 4 [L4]; the job then sets the row `active`; the subject must already be a Logto user, invitations being non-scope |
| Remove a member | The membership row set `removed`; the P0.4 design's lifecycle denies as membership inactive from the next request, "whether or not Logto still honours the token" | `DELETE /api/organizations/{id}/users/{userId}`, "Remove user member from organization" [L4]; the token's fate after removal is the research's gap 1, `UNVERIFIED`, and the P0.4 design's control 9 measures it |
| Change a role | The membership's scopes changed for the P0.3 chain's check 7, effective at once | The organization roles replaced with `PUT /api/organizations/{id}/users/{userId}/roles`, "Update roles for a user in an organization" [L4] |
| Add, rename or close a business unit or branch | A command on `tenancy.business_unit`, the P0.6 design's table, under the tenant's key; no Logto half | None |

The request records are rows of a tenant-owned table on the P0.6 template, `identity_access.administration_request`, with the requesting membership, the action, its status, `requested`, `applied` or `failed`, a vocabulary asked of the P0.6 design with the table (question 6), the job run that applied it and the audit record's identifier; the surface shows a change as pending until the job applies it. The job's run in the P0 lab is on demand, as the P0.5 design's is; when and how it runs in production is P3's operations epic's (question 2). Business units and branches are BizTrust-only and need no job.

### Security settings, sessions and device revocation

| Setting | Where it lives | How the surface changes it |
|---|---|---|
| MFA required for the tenant | Logto's organization, whose table carries `is_mfa_required` (F11), and which the research reads as enforced at token issuance with membership (F7) | A request the job applies with `PATCH /api/organizations/{id}`, "Update organization" [L4] |
| A member's active Logto sessions | Logto, through `GET /api/users/{userId}/sessions` and `DELETE /api/users/{userId}/sessions/{sessionId}`, the operation the reference summarizes as "Revoke a specific user session by its ID, optionally revoking associated target grants and tokens" [L2] [L3]; what a session is, the reference does not define, `UNVERIFIED` (question 9) | The list is read by the job into the request record on demand; revocation is a request the job applies, with `revokeGrantsTarget=all` so that every application's grants go with the session [L3] |
| A member's own surface session | The encrypted cookie [L1] | Sign-out ends it at once; a revoked Logto session is seen when the next token refresh fails, which is control 2 |
| A member's own MFA factors and personal access tokens | Logto, whose users group lists MFA verifications and personal access tokens [L2] | Not administered from this surface in P0; a member manages their own through Logto's own pages, which ADR-002's hosting decision places (question 5) |

The surface's rule for revocation is the P0.4 design's: the BizTrust-side removal is what denies, immediately, and the Logto-side revocation is hygiene that follows; a screen never says a member is gone because Logto said so, only because BizTrust's membership says so.

### Tenant configuration

The tenant's name and its settings on the BizTrust side are a `tenancy.tenant_setting` table this design asks the P0.6 design's next version to list (question 6), keyed by tenant and setting name, holding identifiers and small values and never a document; the surface changes them by a command under the tenant's key. Branding and colour are Logto's organization fields (F11) and go through the job like MFA, with `PATCH /api/organizations/{id}` [L4]. A domain of the tenant's own is P3's and a question of ADR-002's hosting model; P0 has none.

### The audit viewer

The viewer is the P0.10 design's read contract, `query(tenant, filter) -> records`, called under the tenant's key with the auditor's or the administrator's scope, and nothing more: it shows the tenant's own records with the evidence contract's fields as the record carries them, filters by time, actor, outcome and reason code, and follows a record's `request_id` to nothing outside the tenant. Every query the viewer makes is itself a record with `resource_type = audit_record`, as that design fixes, so that the viewer's use is in the evidence it views. A record's `requested_tenant_id` may name another tenant, since it is what the member's own request carried; the viewer shows it as the identifier the member sent and resolves it to no name. The platform auditor's view across tenants is not this viewer (question 7).

### The denial paths as the user sees them

| Path | What the API answers | What the surface does |
|---|---|---|
| A wrong tenant selected: a Tenant A route reached with a token for Tenant B's organization | `tenant_denied`, the P0.4 design's one code | Shows that the route belongs to another tenant than the one selected, offers the switcher, and renders no data of either tenant on that screen |
| A revoked session: the Logto session revoked while the surface's cookie lives | The next token refresh fails at Logto | Returns to sign-in with a plain sentence that the session ended; the cookie is cleared |
| A member removed mid-session | `membership_inactive` from the next request | Leaves the tenant's screens, shows that the membership ended, offers the switcher if other tenants remain, and signs out if none |
| An expired token | The SDK refreshes; if the refresh fails, as above | Refreshes silently; the page notes that React Server Components "cannot write cookies", so refresh from a server component may recur per request [L1], which control 10 measures |
| An absent scope: an action the member's role lacks | `scope_missing` from the P0.3 chain | Does not show the action's control when the scope is absent from the token, and when the API refuses anyway, renders the refusal and never retries |
| A validation failure, a missing idempotency key, a stale version | The P0.8 design's problem types | Renders `errors[]` against the fields, resends with the key the client generates, reloads the resource on `version_mismatch` |

Each path is rendered from the problem document's `code` and never from its `detail`, which the P0.8 design keeps for the client's developer, and no path shows another tenant's identifier or name.

### What is never on the surface

A lint over the surface's routes and components refuses any route, component, contract call or string naming a client, a policy, a claim, a premium, a quote, a bind or a payment, from a list kept with the lint; the manual's stop signal is the reason, "A P0 package that creates a policy, a client or a premium has left the phase", and the lint is the check that raises it before a human must (control 7). The surface's generated client is built from the admin document alone, so a route of the insurance, payment or partner families cannot be called even by mistake.
