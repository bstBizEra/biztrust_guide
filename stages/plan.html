Delivery lifecycle · Plan

Plan

Plan converts a frozen architecture into units of work that can be authorized, executed and verified independently. The unit is the Work Package, and its quality determines everything downstream — a vague plan produces unverifiable work no matter how good the engineering is.

Most delivery failures attributed to execution are planning failures wearing execution's clothes. An acceptance criterion nobody can check does not become checkable because a capable engineer implements it.

THE RULE THIS STAGE EXISTS TO ENFORCE

No ticket, no work. One Work Package has one objective, bounded scope and acceptance criteria that a command can settle.

01

Preconditions

Entry criteria

Architecture is frozen for this scope

Not for the whole system — for the part this work touches. Planning against an unfrozen boundary produces work packages that are invalidated by a decision taken later.

An accepting authority is named

A specific role that will authorize execution and later accept the result. If nobody can be named, the work has no destination and planning it wastes the effort.

The risk tier is assigned

Risk determines how much verification the work must carry. Assigning it after the work is done invites assigning it to match the evidence that happens to exist.

What each of the four tiers obliges is set out on the risk-tier schedule.

04

The hard part

Writing criteria that can fail

A criterion is measurable when two people running the same command would agree on whether it passed. Test each one by asking what its failure would look like.

Measurable

  • "A cross-tenant read returns denied, proven by a test that is shown failing when the policy is removed"
  • "The validator returns PASS on the committed tree, and the SHA measured equals the pushed head"
  • "Every mutating path declares an idempotency key, asserted by parsing the interface file"
  • "A deliberately broken link causes the build to fail — control recorded"

Not measurable

  • "Tenant isolation works correctly"
  • "The code is well tested"
  • "Performance is acceptable"
  • "Documentation is updated"
  • "Three tests exist" — a count of artifacts, not a measurement of behaviour
State the expected value before running the check

Where a criterion asserts a number, compute it once at planning time and confirm the assertion holds. This catches expectation-versus-tolerance mismatches while they are still cheap, rather than at the boundary between the engineer and the reviewer.

05

Permission

Authority records

Authority is granted explicitly, bounded, and expires. Unknown or conflicting authority is not permission.

Granted

The specific actions permitted, by whom, and for what scope.

Withheld

Named prohibitions. Silence about an action is not permission to take it.

Expiry

When the grant lapses. An open-ended grant becomes a standing licence nobody remembers issuing.

Reserved acts

Actions no agent performs regardless of grant — merging, authorizing a demand, deploying to production, or any irreversible action outside explicit scope.

When authority is ambiguous, stop

Record the blocker and halt the affected action. Proceeding on an assumed grant is the failure mode that governance exists to prevent, and it is indistinguishable from correct behaviour right up until it is not.

06

Sizing

Decomposition

  • One objective per package. If the outcome needs the word "and", it is two packages
  • Sized to be reviewable. A change nobody can hold in their head is accepted on trust, which is not acceptance
  • Ordered by dependency, not by appetite. Sequence what unblocks the most work, not what is most enjoyable to build
  • Enabling work is named, not smuggled. If a change requires plumbing first, that plumbing is in scope explicitly or it is its own package
  • Findings become packages. A gap surfaced mid-flight gets its own package with its own criteria — never an opportunistic fix, never an unactioned comment
THE SEQUENCING TEST

Plan the work the deadline actually needs first. A lifecycle built in narrative order will schedule the urgent thing last, behind stages it does not use.

07

Lifecycle

Package states

A Work Package moves through declared states. Only an authorized transition advances delivery, and validation success is never itself a transition — passing tests does not authorize deployment any more than a green build authorizes a merge.

The eight states below are the whole machine, declared by AGENTS.md §8 and listed as the state enum of schemas/session-checkpoint.schema.json — a declaration the pages restate: since WP-035 tests/test_checkpoints_match_schema.py validates every committed checkpoint against that schema, so a state outside the enum fails the suite, but no gate reads the state it finds. The home page restates the same eight; neither page defines its own. Only ENGINEERING_READY has ever been written by the running system — it is the recorded value in badf/current-state.json and in every session checkpoint — so treat the two states after it as declared but not yet exercised.

StateMeansAdvanced by
DRAFTBeing written; fields still incompleteThe planner, once every required field is present
READYComplete and reviewable, but not yet permitted to startReview of scope and criteria
AUTHORIZEDExecution is permitted, within a recorded and expiring grantThe authorizing role, explicitly
IN_PROGRESSWork is under way against this package aloneThe implementing agent
VALIDATINGEvidence is being produced and independently checkedEntering Assure
ENGINEERING_READYEvidence is complete; awaiting a human decisionThe verifier
ACCEPTEDA human has recorded acceptanceThe accepting authority, never an agent
CLOSEDRetained: the package is finished and its evidence and learning are recordedClosing the tracker item, after acceptance

Exceptional states — BLOCKED, WAIT_FOR_AUTHORITY, RECOVERY_REQUIRED, REJECTED, CANCELLED — are recorded outcomes, not failures of process. A package sitting in WAIT_FOR_AUTHORITY with a written reason is functioning correctly; one silently stalled in IN_PROGRESS is not.

The recorded state and the tracker must agree

When the machine-readable state and the issue tracker disagree about what is active, an agent resuming from evidence stops — correctly. Reconcile the divergence rather than working around it, and record which source was wrong.

10

Halt

Stop conditions

  • An acceptance criterion has no command that could falsify it, and is still being called a criterion
  • Authority is absent, ambiguous, expired, or inferred from an unrelated approval
  • The architecture this plan depends on is not frozen for the relevant scope
  • Scope has grown during planning because an adjacent change was convenient
  • No accountable human owner can be named
  • Two packages claim overlapping ownership with no coordination record
