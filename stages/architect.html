Delivery lifecycle · Architect

Architect

Architect turns requirements into contracts that can be violated. A statement nothing could contradict is prose, however carefully it is worded — and prose does not constrain an implementation that disagrees with it.

The stage exists to stop implementation from silently becoming the architecture. It is not finished when a document is long. It is finished when someone can name, for each commitment, what a violation would look like and which check would catch it.

THE RULE THIS STAGE EXISTS TO ENFORCE

Freeze what is expensive to retrofit and cheap to hold now. Defer everything else, and say that it was deferred.

01

Preconditions

Entry criteria

All four must hold. Architecture work started before them produces decisions nobody can evaluate.

Requirements exist and are bounded

Define has produced requirements and a risk tier. (Work Package acceptance criteria come later, from Plan, and are derived from those requirements — the two are not the same artifact.) Architecting an unbounded problem produces an unbounded contract, which is the failure this stage is meant to prevent.

The decision is genuinely open

If the technology is already chosen and funded, this is ratification, not a decision. Record it as such. An ADR written backwards from a foregone conclusion trains readers to skip the alternatives section.

Constraints are known and written

Regulatory, jurisdictional, currency, data-residency and tenancy constraints. A constraint discovered after the freeze invalidates the freeze rather than adjusting it.

Someone can accept the output

Name the role authorized to accept this architecture before writing it. A contract frozen in a repository that disclaims authority over the system it governs, accepted by nobody, is a document rather than a contract.

03

Judgement

The freeze discipline

Freezing is expensive. A frozen boundary becomes a contract amendment rather than a refactor, so freeze narrowly and deliberately.

Freeze

  • Anything that changes the shape of stored data — ownership keys, version pinning, immutability
  • Anything a later migration cannot undo cheaply
  • Anything whose violation is a legal or financial problem rather than a defect
  • Interfaces other teams or tenants will build against

Defer, and record the deferral

  • Seams no code has crossed yet — they are hypotheses until something runs across them
  • Decisions with no forcing function this quarter
  • Anything you would freeze only to feel finished
  • Technology choices a later stage will make with better information
Deferral is an output, not an omission

Write what was deferred and what would trigger revisiting it. A silent gap and a deliberate deferral read identically six months later, and only one of them was a decision.

04

The test of an invariant

Invariant criteria

An invariant is a claim that something is always true. The claim is only useful if its violation is detectable.

Name the check

Every invariant states the command, query or introspection that would catch a violation. If none exists, it is a convention — enforce it in review and stop calling it an invariant.

Prefer structure to intent

A constraint the database enforces beats a rule the code intends. A missing grant beats a code review that remembers.

Count them honestly

A register where most entries cannot fail trains readers to skim the few that can. Fewer, checkable entries outperform a longer list.

Separate the invariant from the mechanism

"Posted journals are append-only" is the invariant. "The application role holds no UPDATE grant" is one mechanism for it. The mechanism may change; the invariant should not.

Hard invariants are never traded for convenience

Where an invariant protects money correctness, identity, tenant isolation or a human approval gate, it is not subject to the cost argument that trims everything else. Trim effort and surface; never correctness or safety.

05

Recording decisions

ADR discipline

Write an Architecture Decision Record when a decision is contested, consequential and hard to reverse. Writing one for a decision nobody disputed produces documentation, not a record.

SectionWhat belongs there
StatusProposed, accepted, superseded — with the date and the accepting role

06

Authority over data

Systems of record

Every authoritative datum has exactly one owner. Ambiguity here is not a documentation gap; it is a future reconciliation incident.

  • For each datum, name the one system that is authoritative and the systems that hold copies
  • Where an external party is authoritative, the internal record is explicitly a representation, not the fact
  • A representation must never be presented in the interface as though it carried the authority of the original
  • Cross-domain direct mutation is prohibited; modules exchange contracts, not table access
THE DISTINCTION THAT MUST SURVIVE

An operating record of a request is not a confirmation that the request was granted. Where the two are conflated, the interface will eventually tell someone they are covered when they are not.

08

Transition

Exit gate

Architect exits to Plan when every condition holds. Acceptance is recorded explicitly; a stage does not advance because nobody objected.

09

Halt

Stop conditions

  • No role is authorized to accept the architecture being written
  • A constraint surfaces that would invalidate a decision already frozen
  • An invariant cannot be given a detection mechanism, and is still being called an invariant
  • The contract asserts a capability is implemented, secure or production-ready without linked evidence
  • Two systems claim authority over the same datum and neither will yield
  • Implementation has already begun and is defining the architecture in practice
