Delivery lifecycle · Assure

Assure

Assure is where a change stops being an assertion and becomes evidence. The implementing agent has claimed the Work Package is done. This stage decides whether that claim survives contact with a command.

Assure does not ask whether the code looks correct. It asks a narrower and more answerable question: for each acceptance criterion, which command was run, against which commit, and what did it print? A criterion no command can check is a defect in the plan, and the package is returned to Plan — not waved through here.

THE RULE THIS STAGE EXISTS TO ENFORCE

Silence is never evidence of completion, and a passing check that has never been observed to fail is not a check.

01

Preconditions

Entry criteria

All four must hold. If any fails, Assure has not started — the change returns to the prior stage rather than entering a queue.

Criteria are measurable

Every acceptance criterion on the Work Package names a command, a file, or an observable output. "Works correctly" is not a criterion. If a criterion cannot fail, it cannot pass.

The change is committed and pushed

The commit SHA is known and matches the remote. Untracked files are invisible to git-based checks and to diff-scoped guards, so a green run taken before git add proves nothing about what shipped.

CI has run, and you know which revision it ran

Not against the branch name, not against a rebased predecessor. Name which revision is authoritative before you check: a pull-request workflow on GitHub runs against a synthetic merge commit of the head into the base, not against the head itself — so record the head SHA, the run's own SHA, and which of the two the criterion is asserted over.

Declared non-coverage exists

The implementing agent states, in writing, what this change does not verify. A verification with no stated limit is the least trustworthy kind, because it cannot be wrong.

02

What gets run

Six assurance layers

Run every layer that applies to the change. Skipping a layer is a decision that is recorded, not an omission that goes unmentioned.

Assurance layers, in ascending cost
LayerQuestion it answersApplies when
L1 · Repository validationIs the repository internally consistent — contracts parse, links resolve, required files present?Every change, without exception
L2 · Unit and integrationDoes the code do what its tests say, and do the parts compose?Any executable change
L3 · Contract testsDo request and response match the published API contract, rather than the implementation's opinion of it?Any change to a public or inter-module interface
L4 · Isolation testsIs access denied where it must be denied? Cross-tenant read, missing organization context, tampered tenant identifier, expired token, wrong audience, database policy.Any change touching authentication, tenancy or data access
L5 · Invariant conformanceDo the structural invariants still hold — by introspecting the schema and the contract, not by reading the code?Any migration, schema change or new endpoint
L6 · Operational readinessIf this reaches production, can it be observed, alerted on, and reversed?Anything intended for release

Treat layers 4 and 5 as the ones to justify skipping in writing, because they are the cheapest to omit and the most expensive to omit wrongly. A unit test of an authorization helper proves the helper; only a request that crosses the real boundary proves the boundary. Where a control is meant to run in a deployed process, exercise it in that process — an in-memory test of the same function is necessary and not sufficient.

03

The discipline

Controls

This is the part of Assure most easily skipped, because nothing visibly breaks when it is. Diligence catches nothing reliably; controls do.

Before you trust a new check

Make it fail on purpose. Record the failing output. Then restore the tree and record the pass. A check whose failure mode you have never seen is a check whose aim you have not verified — it may be watching the wrong file, the wrong field, or nothing at all.

  • Break the thing the check exists to catch
  • Observe and record the failure
  • Restore, and confirm the restore is byte-identical
  • Record the pass, citing the same commit

Absence claims need a positive control

"No cross-tenant read occurred" and "the query never ran" produce identical output. Any check that reports an absence must carry, in the same invocation, a case it is known to detect — otherwise a broken instrument and a clean result are indistinguishable.

  • A zero that agrees with your expectation ends the search early
  • A stale checkout returns PASS against fewer controls than you think
  • An exit code is a claim about the work, not the work
State the expected magnitude first

Before running a count, say what number you expect. A result that silently agrees with a prior belief is the one least likely to be examined, and the one most likely to be measuring the wrong thing.

04

What is produced

Evidence manifest

Assure produces one artifact: a manifest binding each acceptance criterion to the evidence that discharges it. Evidence that is not bound to a revision is not evidence.

Repository

Repository identity and the commit SHA the check ran against, confirmed equal to the pushed head.

Command

The exact command or workflow identity, including tool version. Not a description of it.

Environment

Where it ran and when, with the timezone stated. A local rendering can cross midnight and change the calendar day.

Exit status

The status and the material output, quoted rather than summarized. Errors, failures and denials pass through raw.

Verifier

The role that ran it. The implementing agent may produce evidence; it may not accept its own.

Coverage

What was checked, and explicitly what was not. The non-coverage line is the one a reviewer reads first.

Control record

For each new check: the failing output observed on purpose, and the restored pass, both citing the same revision. Without this the discipline below has nowhere to land, and "we tested it" and "we watched it fail" become the same claim.

Deferred findings

The Work Package identifiers raised for anything found outside this scope.

Keep the pre-merge reading

A claim about what landed is falsifiable only if the value was recorded before it landed. Retain the measurement taken at verification time, not only the one taken afterwards.

When a fix names the tests that prove it, the verifier's job is to run the set that existed before the fix was proposed, plus the new one — not the set the fix selected.

06

Transition

Exit gate

Assure exits to Release when every condition below holds. Validation success is not deployment authority; the gate is a human decision recorded against the Work Package.

Findings become Work Packages, not in-flight fixes

A gap surfaced during verification that sits outside the current acceptance criteria is deferred into a named Work Package with its own criteria. It is never fixed opportunistically in the same change, and never left as an unactioned comment.

07

After go-live

Assurance in steady state

Assure does not end at Release. Once BizTrust is serving real traffic, the same layers run continuously, and the failure they guard against changes from "we shipped a defect" to "something drifted and nobody noticed."

Continuous

  • L1 and L2 on every merge to the protected branch
  • L5 invariant conformance on every migration, blocking
  • L4 isolation suite on a schedule, not only on change

Periodic

  • Recovery exercise: resume a Work Package from repository evidence alone
  • Re-run the full isolation suite, not the subset the last change touched
  • Re-confirm each control can still fail, by making it fail on purpose

Event-driven

  • Every near-miss records which control caught it, and which did not
  • Every escaped defect names the layer that should have held it
Objectives, incident handling and recovery drills are not here

They belong to Operate, and this page does not restate them. What stays here is verification: which layers re-run, and whether each control can still fail.

THE STEADY-STATE MEASURE

Escaped defects are the measure of this stage. Every one names a layer that ran and did not hold, or a layer that was skipped — and which of the two it was decides whether you strengthen a control or stop omitting it. The control-versus-attention ratio itself belongs to Operate.

08

Halt

Stop conditions

Stop the stage and record the reason. Do not proceed on the assumption that the discrepancy is benign.

  • Evidence cannot be bound to the source revision, or the measured SHA differs from the pushed head
  • A criterion survived Plan that verification cannot settle — return the package rather than inventing a proxy for it
  • A check passes but has never been observed to fail
  • The recorded state and the tracker disagree about what is in progress
  • A change to authentication or tenancy carries only unit-test evidence
  • The implementing agent is also the only verifier
  • Required authority is absent, ambiguous or expired
