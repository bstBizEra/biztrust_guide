Delivery lifecycle · Release

Release

Release is where a change stops being an artifact and becomes something a person can be hurt by. Everything before this stage was rehearsal.

The distinction this stage exists to hold is between a deployment that succeeded and a change that worked. A pipeline reports the first. Only a check against the running system reports the second, and the two are routinely conflated because the green tick arrives first and looks conclusive.

THE RULE THIS STAGE EXISTS TO ENFORCE

Verify the revision that is serving traffic, not the revision you intended to ship. Confirm they are the same before believing either.

01

Preconditions

Entry criteria

Assure is accepted, by a human

Evidence complete, criteria discharged, acceptance recorded. Validation success is not deployment authority; passing tests authorize nothing on their own.

Rollback has been exercised

Not designed — exercised, at least once, somewhere. A rollback path that has never been run is a plan, and plans fail in the conditions that make them necessary.

Someone is available to reverse it

Named, reachable, with the access required, for the duration of the exposure window. A release nobody can undo is a release nobody should start.

Release into a window, not into a gap in the calendar

Deploy when the people who understand the change are present and unhurried. The cheapest incident mitigation is that the person who wrote it is awake.

02

Outputs

What this stage produces

Change record

What is being released, by whom, when, the expected effect, and the signal that would prompt reversal. Written before the deployment, not reconstructed afterwards.

Deployed revision identity

The exact revision now serving traffic, recorded and compared to the approved revision. If they differ, nothing else in this stage is meaningful.

Smoke evidence

Output from checks run against the running system, bound to that deployed revision.

Exposure log

Who saw the change, at what percentage, for how long, before it went wider.

03

Limiting harm

Progressive exposure

Exposure control is the difference between a defect affecting some traffic briefly and all traffic indefinitely. It is worth the operational cost precisely because you cannot predict which release needs it.

  • Separate deploying from enabling. Ship the code dark, then turn it on. Two smaller decisions beat one large one
  • Start with traffic you can apologise to. Internal users, then a single tenant that has agreed, then a percentage
  • Define the abort signal before starting. "Error rate above X for Y minutes" — decided in advance, because during an incident everything looks like noise or like catastrophe
  • Hold at each step long enough to see the signal. A canary observed for less time than the metric's own window has been observed for zero time
  • One change per exposure. Two simultaneous changes make an aborted release ambiguous
WHAT EXPOSURE CONTROL CANNOT DO

It bounds who is affected, never whether the effect is reversible. A data change that reaches one percent of tenants has still reached them.

04

The check that matters

Verifying the deployed thing

Every check in this stage runs against the running system and is bound to the revision actually serving it. Verification against a branch, a build artifact or an intention proves something true about an object that is not in production.

Establish identity first

  • Read the revision the running system reports
  • Compare it to the approved revision, exactly
  • Stop if they differ — everything after this depends on it
  • Record the value you read, not the one you expected

Then verify behaviour

  • The critical path completes end to end
  • Authorization still denies what it must deny
  • A known-bad request is still rejected — a positive control, so success carries information
  • Telemetry from the new revision is arriving, not merely configured
An absent error is not a working system

A smoke suite that only checks for the absence of failures passes identically against a system that is serving correctly and one that is serving nothing. Include at least one check that fails when the system is down.

05

Reversal

Rollback

  • Decide the trigger in advance. Who may call it, on what signal, and within what window — agreed before the deployment starts
  • Prefer disabling to reverting. Turning a flag off is faster and less risky than redeploying, and it is available while the diagnosis is still unclear
  • Name the one-way parts explicitly. Where a data change cannot be undone, say so in the change record. Discovering it mid-incident converts a rollback into a recovery
  • Rolling back is not a failure of the release. It is the release working as designed. Treating reversal as an embarrassment is how teams learn to push through instead
06

Who is told

Communication

A release that changes what people see is a change to their working day. Tell them before it surprises them.

  • Notify affected tenants and partners before behaviour changes, not after they notice
  • Give external integrators contract changes with lead time proportional to the work they imply
  • During an incident, communicate what is known, what is not, and when the next update comes — the third is the part people actually need
  • Where a regulated obligation attaches to a change, treat the notification as part of the release, not an afterthought

09

Halt

Stop conditions

  • The deployed revision does not match the approved revision
  • Rollback cannot be performed, or nobody with the access is available
  • Smoke checks pass but no check in the suite could have failed
  • Telemetry from the new revision is absent, so the system is running unobserved
  • The abort signal was never agreed, and exposure has already begun
  • An irreversible step is about to run that the change record does not mention
