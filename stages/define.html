Delivery lifecycle · Define

Define

Define turns a validated problem into a specification someone can architect against. Its characteristic failure is quiet: a requirement nobody can tell they have met.

Nothing on this page describes software that runs. BizTrust is a planned multi-tenant platform for an insurance broker in Laos. Two obligations are settled here rather than later — data classification and risk tier — because classification costs a paragraph now and a migration with a backfill at Build, and because a tier assigned after the evidence is in can only be one that evidence satisfies.

THE RULE THIS STAGE EXISTS TO ENFORCE

Write every requirement so that someone holding the finished product could show it unmet. A requirement that cannot be failed is an aspiration with an identifier attached.

01

Preconditions

Entry criteria

All four must hold.

The problem is validated

Discover must have established whose problem this is and what evidence says it is real. Define is not where it is discovered.

The affected users can be named

Brokers, underwriting staff, claims handlers, tenant administrators, clients — named as roles, not as departments.

The tenant classes in scope are declared

A government-linked tenant may carry obligations a commercial one does not: residency, retention, disclosure, audit. Which classes are in scope changes what must be classified.

Someone is authorized to accept requirements

Name that role before the first requirement is drafted. An unaccepted register is not binding — but it is the only written thing later stages have, so it will be used whether or not anyone accepted it. Acceptance is what makes using it legitimate; naming the role late means the register is already load-bearing before anyone owns it.

03

The hard part

Writing a requirement that can be unmet

Test each requirement by writing its negation. If the negation is a sentence nobody could say about the finished product, the requirement constrains nothing. Name a subject a reader could point at, and give each one a stable identifier that Work Packages and evidence can cite.

Can be unmet

  • "A renewal falling due within thirty days must reach the assigned broker without that broker searching for it."
  • "A client's identity document number must be visible only to users of the tenant that captured it."

Cannot be unmet

  • "The system should be fast" — no subject, no threshold, no observer
  • "Onboarding must be user-friendly"
  • "The platform must be secure"
  • "Use PostgreSQL row-level security for tenant separation" — a solution wearing a requirement's clothes
A requirement written as a solution forecloses the architecture before it is designed

It looks rigorous because it names a technology, so it survives a review that only checks for vagueness. But it settles a question belonging to Architect, without alternatives and without an accepting role. Write the obligation — provable separation between tenants — and leave the mechanism there.

04

The distinction

Requirements are not acceptance criteria

THE DISTINCTION

A requirement says what must be true of the product. An acceptance criterion says what command settles whether one Work Package delivered it. Define produces requirements. Plan derives Work Package acceptance criteria from those requirements. They are not the same artifact, they are not written at the same time, and they are not owned by the same role.

Define does not produce acceptance criteria; guidance on making a criterion measurable is not repeated here, because it lives in Plan.

One obligation, in each stage's own artifact
Requirement · DefineAcceptance criterion · Plan
A client's identity document number must be visible only to users of the tenant that captured it. Reading that field as a user of a second tenant must return denied, status recorded.
Every premium figure shown to a client must carry its currency and, where converted, the rate and its date. The quotation payload must emit currency, rate and rate date for every converted amount; one missing the date must be rejected.
05

Decided now, not later

Data classification

An insurance brokerage handles identity documents, health and risk survey detail, and payment instructions. BizTrust is planned to hold all three, across tenant classes that may include a government-linked one. Classification decided here costs a paragraph; taken at Build it costs a migration and a backfill.

What each classification entry settles
PropertyWhat it fixes
ClassPublic, internal, confidential or restricted — chosen for the element, not for the screen
Residency and retentionWhere it may be stored, how long it is kept, and what happens then
ExposureWhether it may appear in logs, traces or support tooling, and who may extract it
The stricter obligation governs

Where the element's class and the tenant class disagree, take the stricter and record why. A single default cannot be correct for both, and the class it is wrong for is the one nobody is reviewing.

WHY THIS CANNOT WAIT

Encryption boundaries, log redaction and tenant isolation all sit downstream of classification, so an unclassified element handed to Architect is a decision disguised as a detail.

06

What the tier is for

Risk tier

The tier records, in advance, how much this work is worth being wrong about. Two stages require it to exist: Plan treats a blank tier as blocking, and Architect lists it among what Define must have produced. No stage yet varies its behaviour by the tier’s value. Assure selects layers by change type and never reads a tier at all.

Required to exist

Plan will not start on a package with a blank tier, and Architect’s entry criteria name it. That much is real today, and it is why the field is not optional.

Not yet graduated

Nothing downstream does more or less because a tier is high rather than low — not layer selection, not approval authority, not the rollback obligation. Three earlier entries here claimed otherwise; none was supported by any stage page, and one of them implied low-tier work may be self-verified, which Assure forbids unconditionally and lists as a stop condition. They are removed rather than softened.

The gap, stated

A tier that no stage varies on is a field, not a control. Making it one is a lifecycle change and belongs in its own work package — recorded here rather than described as though it already happened.

Assign the tier before the cost of verifying it is known

A tier chosen once the evidence is in hand can only be a tier that evidence satisfies — a property of the ordering, not of anyone’s honesty. Plan treats it as an entry condition, so a blank tier blocks planning.

07

Boundaries

What Define deliberately does not specify

Each item below belongs to a named later stage.

  • Technology, schema and interface shape — Architect
  • Work Package boundaries, sequencing and authority — Plan
  • Acceptance criteria, commands and evidence plans — derived in Plan from the requirements written here
  • Verification layers, controls and manifests — Assure
  • Service levels, incidents and cost monitoring — Operate
  • Screen-level interface design — no stage in this guide covers it — journeys fix what a user must accomplish, not how; where the how gets decided is itself undecided, and saying so beats naming a stage that never mentions it
An omission you meant and an omission you missed leave the same trace

Every item left unspecified goes in the out-of-scope register with the condition that would bring it back. Without it, a boundary you drew and a question you never reached look the same.

09

Transition

Exit gate

Define exits to Architect when every condition holds. Acceptance is an act with a date and a name against it, not the absence of a complaint.

10

Halt

Stop conditions

Halt, and write down which condition tripped.

  • A requirement cannot be given a negation anyone could observe, and nobody will withdraw it
  • A data element appears in the requirements with no classification, and the answer is "we will decide that when we build it"
  • The risk tier is blank, or is being chosen after someone knows what verifying it would cost
  • A requirement names a technology, a table or an endpoint
  • The problem has not been validated, and Define is being used to discover it
  • A tenant class is in scope whose obligations nobody present can name
  • Nobody has been named who can record acceptance of the requirement register
  • Acceptance criteria are being written here rather than derived in Plan
