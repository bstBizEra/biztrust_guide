05

Delivery lifecycle · Build

Build

Build executes one authorized Work Package. The discipline is not speed — it is keeping each change small enough that a reviewer can hold it in their head and an operator can reverse it under pressure.

A large change is not accepted; it is tolerated. The reviewer approves what they could follow and assumes the rest, and the assumption is invisible in the record. Size is therefore a correctness property, not a preference.

THE RULE THIS STAGE EXISTS TO ENFORCE

Every change traces to one authorized package, and carries the tests, telemetry and documentation it needs in the same change.

01

Preconditions

Entry criteria

The package is authorized

Not ready, not drafted — authorized, with a recorded grant that has not expired. Work begun on an unauthorized package cannot be accepted without retrospectively inventing the authority.

The criteria can be checked

Read the acceptance criteria before writing code. If one cannot be settled by a command, say so now. Discovering it at verification wastes the whole implementation.

The branch starts from current main

Pull before branching. A branch cut from a stale base produces a diff that includes other people's work and a review that cannot tell them apart.

03

How changes are made

Change discipline

  • One package per branch. Branch names carry the package identifier so the trace from change to authority survives without anyone remembering it
  • Commits are conventional and reference the package. The commit message is read by someone under pressure, months later, who was not there
  • No adjacent improvements. The tempting refactor next to your change belongs in its own package. "While we were here" is how scope becomes unreviewable
  • Findings become packages. A defect noticed mid-build is filed, not fixed, unless it blocks the current criteria
  • Update every guard in one pass. Where automated scope checks exist, editing one puts it in the diff and wakes its siblings; fix them together rather than iteratively
Verify against the tree that ships

Untracked files are invisible to change-scoped checks, so a green run taken before staging proves nothing about what was pushed. Cite the revision you measured, and confirm it equals the pushed head.

04

The risky part

Migrations

Most changes are reversible by reverting a commit. Data changes are not, and treating them as though they were is the most common route from a routine release to an incident.

Expand, then contract

Eight steps, in order — and only the first five can be undone by reversing them. See the sequence below.

Never destroy in one step

A migration that drops or rewrites in the same deployment as the code change removes the option of rolling back the code.

Backfills are jobs, not migrations

They are restartable, observable, and safe to run twice. A backfill that cannot be resumed will be run again from the start at the worst possible moment.

State the reversal explicitly

Write what rollback means for this change. Where rollback is genuinely one-way, say so at planning time, not during the incident.

  1. Add the new structure alongside the old, nullable and unconstrained.
  2. Dual-write. Deploy code that writes both, still reading the old. Skipping this is what loses data: the old structure keeps taking writes while the backfill runs, so at the read switch the new one is stale by up to every write since the backfill began — silently.
  3. Backfill the existing rows, as a restartable job.
  4. Verify. Reconcile old against new and require agreement before continuing. Switching reads onto an unverified backfill is the second most common way this fails.
  5. Switch reads to the new structure, with dual-write still on.
  6. Soak. Run on the new reads long enough to see a problem, before giving up the ability to switch back cheaply.
  7. Stop writing the old structure. Reversibility ends here — from this moment the old copy goes stale, and returning to it needs a second backfill in the opposite direction.
  8. Remove the old structure. One-way. The only reversal is a restore from backup.
Steps 1–6 are separately reversible. Steps 7 and 8 are not.

Do not let the shape of the procedure imply otherwise. Deploy steps 7 and 8 separately from the rest, and separately from each other, so the irreversible part is a decision someone makes rather than a consequence of a release.

05

Instrument while building

Telemetry as you go

You cannot add observability to an incident that is already happening. The instrumentation a change needs is part of that change, not a follow-up nobody schedules.

  • Every material state transition must emit an event carrying tenant, correlation and causation identifiers
  • Every external call must record outcome, latency and the provider's own reference
  • Errors must carry enough context to reconstruct what was attempted, without carrying sensitive data
  • Give a new failure mode a signal before a runbook, and a runbook before an alert
Detail on operating the running service lives in Operate

This section covers what to instrument while building. Objectives, alerting policy, on-call and incident handling are concentrated there so the guidance has one home and does not drift between pages.

06

Interfaces

Building to contract

Build against the published contract, not against your reading of it. Where the two differ, the contract is wrong or the implementation is — and both are worth knowing before release rather than after.

  • Request and response shapes are asserted against the contract file, not against a fixture someone wrote by hand
  • A change to a public interface changes the contract in the same package, or it is not a change to a public interface
  • Modules exchange contracts, never direct access to each other's tables
  • Provider-specific behaviour stays behind the adapter boundary the architecture defined
THE FAILURE THIS PREVENTS

An implementation that quietly redefines the contract is indistinguishable from a correct one until a second consumer arrives.

Halt

Stop conditions

  • An acceptance criterion turns out to be uncheckable — return the package to Plan rather than inventing a proxy
  • The change requires an irreversible data operation that the package did not authorize
  • Scope has grown beyond the package and the growth is not itself authorized
  • The authority granted for this package has expired
  • The contract and the implementation disagree and nobody will decide which is wrong
